# Research: Autonomous Loop Runners (the "Ralph Wiggum" family)

> Category survey of [awesome-agent-orchestrators](https://github.com/andyrewlee/awesome-agent-orchestrators),
> researched 2026-08-21 for the open-seed design study. Focus: what can live *inside* a repo
> vs. what requires an external app/daemon.

## 1. Origin: The Ralph Wiggum Technique (Geoffrey Huntley, ghuntley.com/ralph)

The entire category descends from one bash line:

```bash
while :; do cat PROMPT.md | claude-code ; done
```

Core ideas, all directly relevant to a repo template:

- **Fresh context per iteration.** The agent process exits and restarts every loop; nothing persists in conversation memory. All continuity lives in **files in the repo**: `PROMPT.md` (standing instructions + priorities), `@specs/*` (per-module technical specs, re-loaded into context every loop), `@fix_plan.md` (prioritized bullet list of incomplete work — deliberately discarded and *regenerated* periodically to prevent stale thinking), and `AGENT.md` (learned build/test commands, updated as the agent discovers things — a "learnings" file).
- **One thing per loop.** Each iteration implements exactly one feature or fixes one bug, preserving context budget so specs and plans can be fully allocated every time.
- **Deterministic stack allocation.** Feed the identical file set each loop so the model gets consistent reference material.
- **Backpressure via tests.** After each change, run tests for only the modified unit; static analyzers for dynamic languages; when spawning parallel subagents, restrict build/test validation to *one* to avoid backpressure collapse.
- **Stock-taking / anti-hallucination rules baked into the prompt:** "search with ripgrep before assuming something isn't implemented"; "full implementations only, no placeholders"; behavioral sign-posts added to the prompt after each observed failure.
- **Economics & limits:** reports a $50k contract done for $297 in tokens; ~90% effective on greenfield, weak at retrofitting existing codebases; requires a senior engineer supervising, retuning prompts, and reprioritizing the plan.

Everything below is a hardening of this loop. Notably, *the original is 100% checked-in-repo-native*: the "orchestrator" is a one-line script plus markdown conventions — the ideal shape for open-seed.

## 2. Project profiles

### 2.1 frankbria/ralph-claude-code — the faithful, hardened Ralph (Shell, 9.6k★, active)
The most direct implementation: a bash framework looping Claude Code against `.ralph/PROMPT.md`, updating `.ralph/fix_plan.md` (`- [ ]` checklists) each loop. **Repo files:** `.ralph/PROMPT.md`, `.ralph/fix_plan.md`, `.ralph/AGENT.md` (auto-maintained build/test commands), `.ralph/specs/` (+`specs/stdlib/` reusable patterns), `.ralphrc` (config incl. `ALLOWED_TOOLS` permission gate), plus state/logs (`status.json`, `metrics.jsonl`, `queue.json`). **Exit detection is its crown jewel — a dual-gate:** the loop exits only when (a) ≥2 heuristic completion indicators appear in output AND (b) Claude explicitly emits `EXIT_SIGNAL: true` in a structured `RALPH_STATUS` JSON block. Explicit signal outranks heuristics. Alternative exits: all remaining unchecked tasks live under `Optional`/`Future`/`Nice to Have` sections of fix_plan.md; 5 consecutive completion signals (anti-"almost done forever"); 5-hour API limit. **Guardrails:** `MAX_CALLS_PER_HOUR=100`, optional token/hour cap, 15-min per-loop timeout, a **circuit breaker** (opens after 3 loops with no file changes, 5 identical errors, or >70% output-length decline; half-open after 30-min cooldown), `--backup` git branch per loop with `--rollback`, `--dry-run`. Harness: tightly coupled to Claude Code CLI. 784 tests. **Steal:** dual-gate exit, optional-section semantics in the plan, circuit-breaker thresholds, AGENT.md auto-maintenance.

### 2.2 umputun/ralphex — plan-file executor with review pipeline (Go, 1.4k★, very active)
CLI running Claude Code (or codex) against a **markdown plan checked into `docs/plans/`**: `# Plan: Name`, a `## Validation Commands` section (e.g. `go test ./...`), then `### Task N` headings with `- [ ]` checkboxes. **Fresh Claude session per task**; the tool scans for the first unchecked box, executes, runs the plan's validation commands (failure halts), marks `[x]`, repeats until the agent emits `<<<RALPHEX:ALL_TASKS_DONE>>>`. Completed plans move to `docs/plans/completed/`. Then a **review pipeline**: 5 parallel review agents (quality, implementation, testing, simplification, documentation) → optional external review by codex with Claude adjudicating findings → second targeted 2-agent pass. Exit: `max_iterations` (default 50), and **stalemate detection** (`--review-patience`: N rounds with no commits ends the loop). Config layering: CLI flags > project `.ralphex/` > `~/.config/ralphex/` > embedded defaults; customizable prompt/agent files. Docker wrappers, worktree mode, web dashboard, rate-limit auto-retry. **Steal:** the plan format (validation commands *inside the plan file*), first-unchecked-checkbox scheduling, sentinel completion marker, cross-model adversarial review, completed-plans archive folder.

### 2.3 mikeyobrien/ralph-orchestrator — hat-based Ralph (Rust, 3.1k★, active)
Loops until the agent outputs a **`LOOP_COMPLETE` marker** or iteration budget is hit. Adds "hats" — specialized personas coordinating through events, with 5 built-in patterns. **Repo files:** `.ralph/specs/` with `requirements.md`, `design.md`, `implementation-plan.md`; `ralph.yml` config. **Guardrails:** "backpressure gates" (tests/lint/typecheck reject incomplete work each iteration), git checkpointing, MCP workspace scoping, human-in-the-loop via Telegram (blocking questions + proactive guidance). Supports 8 harnesses. **Steal:** the requirements/design/implementation-plan spec triple; naming backpressure gates as first-class config; role rotation ("hats") within one loop rather than multiple concurrent agents.

### 2.4 michaelshimeles/ralphy — PRD-checkbox loop (2.9k★, inactive since Feb 2026)
Node CLI (with bash alternative) running Claude Code/OpenCode/Cursor/Codex/Qwen/Droid over task lists until PRD complete. **Task sources:** `PRD.md` with `- [ ]` checkboxes (default), `tasks.yaml`, `PRD.json` (with `parallel_group` ordering for parallel worktree execution), GitHub issues, or folders of `.md` files. Retries failed tasks up to 3× with exponential backoff; `--max-iterations` cap. **`.ralphy/config.yaml`** holds project rules, test/lint/build commands, and `never_touch` boundary paths; agents are instructed not to modify the PRD, `.ralphy/progress.txt`, or worktree dirs. **Steal:** `never_touch` boundaries in checked-in config; `parallel_group` annotation in the task format; progress file the agent may append to but not rewrite.

### 2.5 subsy/ralph-tui — tracker-driven loop TUI (TypeScript/Bun, 2.4k★)
Terminal UI orchestrating the loop: SELECT TASK (highest priority from tracker) → BUILD PROMPT (templates + task context) → EXECUTE AGENT → DETECT COMPLETION → NEXT. One task per iteration. **Trackers:** `prd.json` (simple) or **Beads**, a git-backed issue tracker with dependency tracking — tasks-as-data living in the repo. Guardrails are thin: `--sandbox`, pause/resume for human review, cross-iteration progress notes. Seven harnesses supported. **Steal:** pluggable tracker abstraction over a git-backed task database with dependencies; prompt-template-per-task-type checked into the repo.

### 2.6 francescoalemanno/dex — human-gated plan → fresh-context apply → reviewer fanout (Rust, 21★, conceptually rich)
Explicitly a "maturation of the Ralph technique." **`dex plan`** has the agent draft a markdown checkbox plan, asks clarifying questions (`questions.md`), and blocks on human accept/revise/edit/reject — the agent never touches code during planning. **`dex apply`** parses checkbox tasks, picks the first incomplete one, gives it to the agent with plan context, and *kills the subprocess after each task* for fresh context. **Exit: STALEMATE rule** — stop when "four consecutive iterations leave both total and remaining plan-step counts unchanged" (progress measured *from the plan file*, not from agent claims). **`dex review`**: 5 concurrent specialized reviewers; a fixer agent verifies findings against actual code and filters false positives; up to 3 focused re-review rounds. **`dex research`**: benchmark-driven optimization loop — parses `METRIC name=value` from a benchmark command, keeps improvements, reverts regressions, feeds failures back as **dead ends** so they aren't retried. State in gitignored `.dex/` including `review-base-ref.txt` — a durable diff base captured pre-implementation so reviews survive interruption. CLI-agnostic across 8 harnesses. **Steal:** stalemate-by-plan-delta exit; fixer-validates-reviewer pattern; dead-end ledger; durable review base ref.

### 2.7 looptroop-ai/LoopTroop — council planning + Ralph recovery (TypeScript, 123★, early alpha)
Local GUI orchestrator turning tickets into PRs via OpenCode. **Planning by LLM Council:** multiple models independently draft interview questions/PRD/work breakdown, vote on each other's drafts with weighted rubrics, and synthesize a winner. Work is decomposed into **"beads"** (smallest independently implementable units), each with measurable acceptance criteria. **Execution:** one bead per iteration in a git worktree, automated tests validate; on failure, **Ralph-style recovery**: `fail → log compact failure trace → reset worktree → retry with fresh session`, carrying forward *only* the compressed error trace, never the contaminated chat. Human gates at spec, blueprint, and PR; failed manual-QA items auto-generate "QA-fix beads." Notes context degradation begins around **40% of window** ("context rot"). **Steal:** compact-failure-trace-plus-worktree-reset retry; beads with acceptance criteria; failed-QA-items-become-new-tasks.

### 2.8 sipyourdrink-ltd/bernstein — zero-token deterministic coordinator (Python, 946★, beta, very active)
The contrarian: **no model in the coordination loop.** One LLM call decomposes a goal into tasks with roles and *completion signals*; thereafter plain Python schedules: **Decompose → Spawn** (each coding task in its own git worktree) **→ Verify** (a "janitor" checks concrete signals: tests pass, files exist, lint/type clean) **→ Merge** (only verified work lands on main; failures retry or reroute to a different model/agent). Because coordination is deterministic, **runs replay byte-identically** and are provable offline: Ed25519-signed `run-receipt.json`, lineage spine, optional HMAC audit chain. **Repo files:** `bernstein.yaml` (config+plan), `templates/`, `.sdd/` workspace with per-run journals. 49 agent adapters. CI re-verifies committed demo receipts. **Steal:** completion-signals-declared-at-decomposition; deterministic scheduler (a script, not a model) as the loop driver; signed, checked-in run receipts verified by CI.

### 2.9 Keesan12/martin-loop — governance wrapper (TypeScript, 45★, active)
Governance-first: wraps any agent run in a **task contract** (objective, verifier plan, allowed/denied path globs, acceptance criteria, budget). Lifecycle: **DEFINE → PREFLIGHT → CONTROL → VERIFY → RECOVER → PROVE → ANALYZE**. Per-attempt records with cost + stop-condition evaluation; failures map to 13 canonical `FailureClass` values. **Budgets:** `--budget-usd` hard cap, soft limit, max tokens/iterations; preflight blocks attempts that would exceed policy. **Verification:** the configured verifier (e.g. `npm test`) must pass *fresh after each attempt* — completion is evidence, not agent assertion. Three-way handoff: `VERIFIED` / `STOPPED` / `NEEDS REVIEW`. Config in **`martin.config.yaml`** (checked-in policy defaults). Claude/Codex/Gemini adapters. **Steal:** the task-contract schema; budget preflight; failure-class taxonomy; fresh-evidence completion rule.

### 2.10 plasma-ai/fractal — recursive loop trees (Python, 695★, active)
Each node runs an autonomous agent loop in its own **git worktree**, iterating toward a goal defined in a **`NODE.md`** instruction file, and spawns child nodes for separable subtasks. **Hard caps per node:** `max-iters`, `max-depth`, `max-children`, `max-descendants`, timeouts, and cost ceilings `max-cost`/`max-iter-cost`/`max-step-cost`, with a **reserve budget (default 10%) held back for cleanup**; after exhaustion, restart requires explicit reauthorization. Children selectively **inherit** parent config. **Steal:** three-level cost caps (run/iteration/step), reserve-budget-for-cleanup, explicit reauthorization after budget exhaustion, NODE.md-as-recursive-prompt.

### 2.11 JesseRWeigel/toryo — trust + quality ratchet (TypeScript, 12★, experimental)
Cycle = **Plan → Research → Execute → Review**, with phases assigned to different agents via `toryo.config.json` and `specs/` markdown task files with YAML frontmatter. **Quality ratcheting**: reviewer scores each result 0–10; score ≥6.0 → `git commit`, below → automatic `git revert`, then one Ralph-style retry with QA feedback attached. All results append to `.toryo/results.tsv`. **Trust-based delegation:** rolling average score over 50 cycles yields a trust value; <0.6 supervised, 0.6–0.8 guided, ≥0.8 autonomous — high performers earn looser leashes. **Steal:** score-gated commit/revert as the atomic quality ratchet; append-only TSV scoreboard; trust tiers modulating instruction strictness.

### 2.12 mikehostetler/wreckit — backlog-to-PR pipeline (Elixir/TS, 129★, inactive since April)
Ralph loop over a roadmap: items move `raw → researched → planned → implementing → in_pr → done`. **Everything is files in `.wreckit/`:** `config.json`, `index.json` registry, and per-item folders containing `item.json` (state machine), `research.md`, `plan.md`, `prd.json`, `prompt.md` (the generated agent prompt, inspectable), `progress.log`. Fully resumable from file state; `wreckit doctor` validates/repairs broken state. PR requires human approval ("the loop automates logistics, not decision-making"). **Steal:** per-item directory with a full paper trail (research → plan → prompt → progress); explicit state-machine field in item metadata; a `doctor` command for state repair.

### 2.13 cobusgreyling/loop-engineering — the pattern book (JS, 10.5k★, very active)
Less a runner than a **methodology + checked-in conventions**, and therefore the closest cousin to open-seed. Thesis: "Stop prompting. Design the loop." **Checked-in file conventions:** `LOOP.md` (declarative loop design: pattern, cadence, skills, worktree policy, sub-agent roles, gates, MCP scopes), `STATE.md` (mutable: last run, discovered items, verification results, human decisions), `.budget.json` (per-run and daily token caps), `gate.yaml` (denylist paths, auto-merge allowlist), `run-log.json` (append-only outcomes), `skills/`, `patterns/registry.yaml`, and `.github/workflows/` that validate the loop config in CI. Seven production patterns (Daily Triage, PR Babysitter, CI Sweeper, Dependency Sweeper, Changelog Drafter, Post-Merge Cleanup, Issue Triage). **Exit conditions enumerated:** no actionable items, budget exhausted, verification gate failure, human escalation, circuit breaker, daily budget. **Autonomy tiers L1 report-only / L2 assisted allowlisted fixes / L3 unattended-with-gates.** Drift detection between `STATE.md` and `LOOP.md`. **Steal:** basically the whole file layout, the L1/L2/L3 ladder, and the gate.yaml split of denylist vs auto-merge allowlist.

## 3. Synthesis

### 3.1 The canonical loop and its variations

Every project is the same skeleton: **`while not done: (select one unit of work from a plan file) → (spawn agent with fresh context = standing prompt + specs + plan + progress) → (agent does exactly one unit) → (deterministic verification) → (update plan/progress in files) → (evaluate exit conditions)`.** The orchestrator's only real jobs are unit selection, context assembly, verification, and exit judgment. Variations along five axes:

1. **Who selects the next unit:** the agent itself (pure Ralph) vs. the harness deterministically picking the first unchecked checkbox (dex, ralphex, ralphy) vs. a tracker with priorities/dependencies (ralph-tui/Beads) vs. a zero-LLM scheduler (bernstein). The trend in mature tools is *away* from letting the model choose — deterministic selection from the plan file is cheaper and auditable.
2. **Context policy:** fresh session per *iteration* (Ralph), per *task* (dex, ralphex — the dominant pattern), or fresh-only-on-failure with compressed error carryover (LoopTroop). Consensus: conversation state is a liability; files are the memory.
3. **Verification depth:** plan-declared validation commands after each task (ralphex) → backpressure gates on every iteration (ralph-orchestrator) → multi-agent review fanout with a false-positive-filtering fixer (dex, ralphex) → cross-model external review → score-gated commit/revert (toryo) → contract-bound fresh-evidence verifier (martin-loop, bernstein).
4. **Human gates:** none (Ralph), plan approval only (dex, LoopTroop), PR approval (wreckit, LoopTroop), or graduated autonomy tiers (loop-engineering L1–L3, toryo trust levels).
5. **Topology:** flat sequential loop (most), parallel worktrees (ralphy, bernstein, ralphex), recursive trees (fractal), role rotation within one loop (ralph-orchestrator hats), multi-model councils (LoopTroop).

### 3.2 Recurring file conventions

- **Plan = markdown with `- [ ]` checkboxes**, grouped under task headings; overwhelmingly the standard. Progress *is* the diff of checkboxes — trivially reviewable in git. Enrichments: a `## Validation Commands` section in the plan (ralphex), optional sections that don't block completion, `parallel_group` annotations (ralphy), completed-plan archive folders.
- **Standing prompt file** (`PROMPT.md`, `NODE.md`, generated `prompt.md`) separate from the plan.
- **Specs directory** (`specs/`, `.ralph/specs/` with `requirements.md`/`design.md`/`implementation-plan.md`) allocated to context every loop.
- **Learnings/memory file**: `AGENT.md` (build commands and discoveries, auto-updated), `STATE.md`, dead-end ledgers (dex), compact failure traces (LoopTroop).
- **Append-only run records**: `metrics.jsonl`, `run-log.json`, `results.tsv`, `progress.log`, signed `run-receipt.json` — never rewritten, sometimes CI-verified.
- **Policy config**: `.ralphrc` / `ralph.yml` / `martin.config.yaml` / `gate.yaml` / `.ralphy/config.yaml` holding allowed tools, never-touch paths, budgets, validation commands.
- A hidden **tool state dir** (`.ralph/`, `.dex/`, `.wreckit/`, `.sdd/`, `.toryo/`) — some gitignored, some committed; wreckit's committed per-item folders give the best paper trail.

### 3.3 Failure modes these projects guard against

1. **Non-termination / "almost done forever"** → dual-gate exit (heuristics AND explicit signal), sentinel markers, stalemate detection via unchanged plan-step counts, consecutive-signal force-exit.
2. **Spinning without progress** → circuit breakers on no-file-changes/identical-errors/output decline; review-patience counters; 3-consecutive-failure aborts.
3. **Runaway spend** → USD/token/iteration/time caps at run, iteration, and step granularity; budget preflight; reserve budget for cleanup; reauthorization after exhaustion.
4. **Context rot** → fresh session per task; compact error traces instead of chat history; the 40%-of-window degradation observation; deterministic context stacks.
5. **False completion claims** → verification must produce fresh evidence bound to the run (martin-loop), concrete completion signals declared at decomposition (bernstein), tests/lint as backpressure gates.
6. **Bad or destructive changes** → path denylists (`never_touch`, gate.yaml), worktree isolation keeping main clean, score-gated commit/revert, per-loop backup branches with rollback, sandbox/VM execution.
7. **Reviewer noise** → fixer agents that verify findings against code before acting; cross-model adjudication.
8. **State corruption / non-resumability** → file-based state machines, `doctor` repair commands, durable review base refs, signed replayable receipts.

### 3.4 Five ideas most transferable to a checked-in repo template (open-seed)

1. **The plan-file contract.** Standardize a `plans/` directory: `# Plan` header, `## Validation Commands`, `### Task` sections with `- [ ]` checkboxes, `Optional:` sections that don't block completion, and `plans/completed/` archival. This single markdown convention gives you scheduling (first unchecked box), progress tracking (checkbox diffs in git history), verification (commands live *with* the plan), and completion detection (no required boxes left) — with zero external tooling.
2. **A tiny checked-in loop script with a dual-gate exit and circuit breaker.** A ~200-line `scripts/loop.sh` that: assembles context (PROMPT.md + specs + plan), invokes the harness fresh per task, requires both structured `EXIT_SIGNAL: true` and heuristic completion indicators to stop, halts on N iterations with no plan-delta or no file changes, and enforces `--max-iterations`. All of Huntley's loop plus frankbria's exit logic fits in a script any team can read and commit.
3. **Policy-as-checked-in-config**: a `guardrails.yaml` (modeled on gate.yaml + martin.config.yaml + `.ralphy` `never_touch`) declaring allowed tools, denied paths, auto-merge allowlist, per-run and daily budgets, and required verifier commands — read by the loop script and enforceable by Claude Code hooks and CI. Pair with loop-engineering's L1/L2/L3 autonomy tiers as a template-level knob.
4. **Memory files with defined mutation rules:** committed `AGENT.md` (learned build/test commands, agent-appendable), `DEADENDS.md` (failed approaches, so fresh-context sessions don't retry them), and an append-only `run-log.jsonl` the agent may append to but never rewrite; CI can verify append-only-ness. This is the whole "fresh context needs file memory" doctrine made concrete.
5. **Verification as backpressure, not epilogue:** template the ralphex/martin-loop rule that every task ends with the plan's validation commands run fresh, failure halts the loop rather than continuing, and completion requires evidence (test output) not assertion — plus an optional second-phase multi-reviewer pass implemented as checked-in reviewer prompt files, which ralphex proves can be plain customizable text files rather than product features.

**Harness-dependence spectrum** (for template positioning): pure-repo-native — original Ralph, ralphy-bash, loop-engineering patterns; thin CLI over any harness — ralphex, dex, ralph-tui, ralphy, toryo, wreckit; heavier daemon/app — LoopTroop, bernstein, fractal, ralph-orchestrator, martin-loop. The pattern extraction above deliberately draws from the left half of that spectrum: everything in ideas 1–5 can ship as markdown + YAML + a bash script + CI workflow inside a cloned template, with external runners as optional upgrades.
