## 1. byronxlg/skillfold

**Manifest (`skillfold.yaml`).** Top-level keys are exactly `skills, compose, rules, skillsDir, rulesDir, targets` (unknown keys are hard errors). From the source doc comment in `src/manifest.ts`:

```yaml
skills:                          # name -> source
  commit-helper: ./skills/commit-helper
  code-review: github:owner/repo/skills/code-review@v1.2.0
  planning: npm:skillfold/planning

compose:                         # generated skills, concatenated from others
  release-manager:
    description: Cut releases end to end.
    use: [code-review, planning]

rules:                           # name -> source of a single .md file
  code-style: ./rules/code-style.md

skillsDir: .claude/skills        # optional override (claude target only)
rulesDir: .claude/rules
targets: [claude, codex]         # default: [claude]
```

A skill entry may also be `{ source, version }` (version is appended as `@version`). Names must match `^[a-z0-9]([a-z0-9-]*[a-z0-9])?$`, max 64 chars, and be unique across skills/compose/rules. **Source grammar** (`src/source.ts`): local path; `github:owner/repo[/path][@ref]` or `https://github.com/owner/repo/tree/ref/path`; `npm:package[/skill][@version]` incl. `npm:@scope/pkg/...`. The `@ref` must come after the last `/` (so npm scopes never split); a ref is a tag, branch, or 7-40-hex SHA.

**Lockfile (`skillfold.lock`)**: YAML, committed. Verbatim from the repo's own dogfood lock plus the format comment:

```yaml
# Generated by skillfold. Commit this file; do not edit it by hand.
lockfileVersion: 1
skills:
  code-review:
    source: github:owner/repo/skills/code-review@v1.2.0
    resolved: github:owner/repo/skills/code-review@<full commit sha>
    integrity: sha256-...
  commit-helper:
    source: ./skills/commit-helper          # local: no resolved/integrity
compose:
  reviewer:
    use: [code-review, testing]
    integrity: sha256-N9pnu3ZVqxsezepfg234WhU4EnbNhUyq6LEcXCrqhBs=
rules:
  code-style:
    source: ./rules/skillfold-conventions.md
targets: [claude, codex]        # omitted when just [claude]
```

Per-entry fields: `source` (normalized manifest string), `resolved` (same source string with the ref replaced by a full commit SHA / exact npm version: absent for local), `integrity` (`sha256-<base64>` over the skill's files: absent for local, "they change freely"). Compose entries carry `use` + `integrity` of the *generated* files. Sections are alphabetically sorted; `rules:`/`targets:` are omitted when empty/default to avoid churn.

**Resolution algorithm** (`src/resolve.ts`):
- **install**: for each remote skill, reuse the lock pin *iff* the lock entry exists, its `source` string matches the manifest, and `resolved` is set; otherwise resolve the ref fresh. Writes a new lockfile every run; prunes skills that left the manifest.
- **update [names|all]**: forces re-resolution: "branches move to their new head, `latest` moves to the newest version."
- **--frozen** (CI, "like `npm ci`"): first `lockfileProblems()` must be empty (lock exists, covers exactly the manifest, sources unchanged, compose `use` lists unchanged, targets unchanged); then installs precisely the pinned revisions and errors when the fetched content hash ≠ `integrity` or a composed skill "would generate different content than the lockfile pins." Never rewrites the lockfile.
- **check**: fully offline; verifies lock↔manifest agreement, everything installed, remote content hashes match, local skills match their source dir, and composed output matches what installed inputs would generate. Missing `description` is a warning, never a failure. Exit 1 on drift: this is what their GitHub Action runs.

**Fan-out.** A target "is just a set of install locations" (`src/targets.ts`): skills are byte-identical copies per target, no symlinks:

| | project | global (`-g`) |
|---|---|---|
| claude | `.claude/skills`, `.claude/rules` | `~/.claude/skills`, `~/.claude/rules` |
| codex | `.agents/skills`, managed block in `AGENTS.md` | `~/.agents/skills`, `~/.codex/AGENTS.md` (`$CODEX_HOME`) |

`skillsDir`/`rulesDir` override claude only ("codex scans fixed conventional paths, so those stay put"). Ownership model: a directory is "managed" (safe to overwrite/prune) iff its name appears in the *previous* lockfile; anything else errors without `--force`.

**Rules sync into AGENTS.md** (`src/agentsmd.ts`): a marker-fenced managed block, byte-exact round-trip so `check` can verify offline:

```
<!-- skillfold:rules:start -->
<!-- Generated by skillfold from skillfold.yaml. Do not edit between the markers; edit the manifest and run "skillfold install". -->
<!-- skillfold:rule:code-style -->
...rule content verbatim...
<!-- skillfold:rules:end -->
```

Everything outside markers is never touched; the file is created/deleted as the block appears/empties; rules containing marker-shaped lines or non-UTF-8 are rejected. For claude, rules land as `<rulesDir>/<name>.md`.

**Composition** (`src/compose.ts`): a composed skill is a *generated* `SKILL.md` whose body concatenates the used skills' bodies in declared order, each part's headings demoted to nest under a root `# Composed Name` heading (fenced code blocks untouched); supporting files are carried over so relative paths keep working; `allowed-tools` defaults to the union of inputs' lists *only when every input declares one*. Cycle rules: `use` entries must exist in `skills` or `compose`; self-use is an error; cycle detection via DFS throws `Compose cycle detected: a -> b -> a`. Compose-of-compose is allowed (topological order). Removal of a skill still used by a compose entry is refused.

## 2. shinpr/sub-agents-skills

A single Agent-Skills-format skill (`skills/sub-agents/SKILL.md`, `allowed-tools: Bash Read`) whose script `run_subagent.py` spawns external CLIs as sub-agents. Agent definitions live in **`.agents/*.md`** (also `.txt`); filename = agent name; discovery priority: `--agents-dir` arg → `$SUB_AGENTS_DIR` → `{cwd}/.agents/`.

**Frontmatter schema** (verbatim from SKILL.md):

| Field | Values |
|---|---|
| `run-agent` | `codex`, `claude`, `cursor-agent`, `glm`, `kimi`, `grok`, `gemini`, `opencode` |
| `model` | backend-specific model name (optional) |
| `effort` | opaque, forwarded per backend; "Unsupported on `cursor-agent` and `gemini`" |
| `permission` | `read-only`, `safe-edit` (default), `yolo` |

If `run-agent` is absent: auto-detect caller environment, else default `codex`. `--cli` always overrides `run-agent`. Frontmatter parsing is deliberately flat (regex line-split, quotes stripped, no nested YAML).

**Body convention** ("Essential Structure", README):

```markdown
---
run-agent: codex
model: gpt-5.4-mini
permission: safe-edit
---

# Agent Name

One-sentence purpose.

## Task
- Action 1
- Action 2

## Done When
- Criterion 1
- Criterion 2
```

Optional sections: `## Out of Scope`, prohibited actions, `## Output Format`. The description shown by `--list` is the first non-heading body line, truncated to 100 chars. Design rules: single responsibility; self-contained (no references to other agents, no assumed prior context). The whole body becomes the sub-agent's system context.

**Backend flag translation** (`scripts/_builder.py`, verbatim: documents each third-party CLI's permission flags):

```python
_CODEX_PERMISSIONS = {
    "read-only": ("-s", "read-only"),
    "safe-edit": ("-s", "workspace-write", "-c", "approval_policy=never"),
    "yolo": ("--dangerously-bypass-approvals-and-sandbox",),
}
_CLAUDE_PERMISSIONS = {           # also used by glm and kimi
    "read-only": ("--permission-mode", "plan"),
    "safe-edit": ("--permission-mode", "acceptEdits"),
    "yolo": ("--dangerously-skip-permissions",),
}
_GEMINI_PERMISSIONS = {
    "read-only": ("--approval-mode", "plan"),
    "safe-edit": ("--approval-mode", "auto_edit"),
    "yolo": ("-y",),
}
_CURSOR_PERMISSIONS = {
    "read-only": ("--mode", "plan"),
    "safe-edit": ("--trust",),
    "yolo": ("-f", "--trust"),
}
_GROK_PERMISSIONS = {
    "read-only": ("--permission-mode", "bypassPermissions", "--sandbox", "read-only"),
    "safe-edit": ("--permission-mode", "bypassPermissions", "--sandbox", "workspace"),
    "yolo": ("--permission-mode", "bypassPermissions", "--sandbox", "off"),
}
```

OpenCode gets no flags; permissions go through env `OPENCODE_PERMISSION` as JSON (`read-only`: deny edit/bash/task/external_directory/question; `safe-edit`: allow edit+bash, deny the rest; `yolo`: `"allow"`). Base commands: codex `exec --json --skip-git-repo-check <prompt>`; claude/glm/kimi `claude --output-format stream-json --verbose -p <prompt>`; gemini `--skip-trust --output-format stream-json -p`; grok `--output-format json --verbatim -p` plus `--cwd`; opencode `run --format json --auto`; cursor-agent `--output-format json -p`. System context injection differs: claude gets `--append-system-prompt "cwd: {cwd}\n\n{system_context}"`; glm/kimi get `--system-prompt`; gemini uses env `GEMINI_SYSTEM_MD={agent_file}`; the rest concatenate `[System Context]\n...\n\n[User Prompt]\n...`. `model` → `--model` everywhere; `effort` → codex `-c model_reasoning_effort=<json>`, claude/glm/kimi `--effort`, grok `--reasoning-effort`, opencode `--variant`.

**Credentials**: GLM routes claude CLI to `https://api.z.ai/api/anthropic` with `GLM_API_KEY` → `ANTHROPIC_AUTH_TOKEN`; Kimi to `https://api.kimi.com/coding/` with `KIMI_API_KEY` → `ANTHROPIC_API_KEY` (both null out the other Anthropic vars); Cursor `CURSOR_API_KEY` kept out of argv; `CLI_API_KEY` is a legacy generic fallback. The rationale for the tiers: "Sub-agents have no stdin, so any approval prompt would deadlock the run": `safe-edit` auto-approves workspace writes while suppressing prompts.

**Parallel invocation** is natural-language, not syntax: the orchestrating agent runs multiple `run_subagent.py` processes concurrently. Output contract: JSON `{"result", "exit_code", "status": success|partial|error, "cli"}`; exit codes 124 timeout, 127 CLI missing.

## 3. The Agent Skills standard (agentskills.io)

From `docs/specification.mdx`. A skill = a directory containing at minimum `SKILL.md`; conventional optional dirs `scripts/`, `references/`, `assets/`, plus anything else. Frontmatter:

| Field | Required | Constraints |
|---|---|---|
| `name` | Yes | 1-64 chars, lowercase alnum + hyphens, no leading/trailing/consecutive hyphens, **must match the parent directory name** |
| `description` | Yes | 1-1024 chars, non-empty; what it does *and* when to use it |
| `license` | No | name or bundled-file reference |
| `compatibility` | No | ≤500 chars, environment requirements |
| `metadata` | No | string→string map for client extensions |
| `allowed-tools` | No | "space-separated string of pre-approved tools ... (Experimental)" e.g. `Bash(git:*) Bash(jq:*) Read` |

Body: "no format restrictions." **Progressive disclosure is normative structure**: (1) metadata ~100 tokens loaded at startup for all skills; (2) `SKILL.md` body loaded on activation, "< 5000 tokens recommended", "Keep your main `SKILL.md` under 500 lines"; (3) resources loaded on demand: relative paths from skill root, "Keep file references one level deep." Conformance tooling: `skills-ref validate ./my-skill` (reference parser/validator in the repo). **The spec itself carries no version number**, no spec-version field, no changelog semver; treat it as a living document.

Discovery (from the client-implementation guide: guidance, not mandate): "the Agent Skills specification does not mandate where skill directories live (it only defines what goes inside them)", but clients should scan both a client-specific dir and the **`.agents/skills/` convention** at project and user scope (`<project>/.agents/skills/`, `~/.agents/skills/`), which "has emerged as a widely-adopted convention for cross-client skill sharing." Notes: some clients also scan `.claude/skills/` "for pragmatic compatibility", ancestor dirs to git root, XDG dirs. Precedence: "project-level skills override user-level skills"; same-scope collisions: pick first-or-last-found consistently and warn. Trust: gate project-level skills on a folder-trust check. Who honors `.agents/skills/`: Claude Code, Gemini CLI, Cursor-adjacent tools, OpenCode, Databricks, Qodo, Trae, etc.; concretely, the vercel-labs `skills` CLI treats `.agents/skills` as canonical for ~19 "universal" agents and symlinks into the stragglers' native dirs.

## 4. Multica, and where `skills-lock.json` actually lives

**Correction to the earlier survey**: multica.ai/docs has **no** "playbooks" page and **no** `skills-lock.json`. Its `/docs/skills` page documents platform-hosted workspace skills: `SKILL.md` + `references/`, `templates/`, `scripts/` ("`SKILL.md` is a reserved path"); CLI `multica skill import --file ./review-helper.skill` and `multica skill refresh <skill-id>`, where refresh preserves identity and replaces content. On repos it says only: "Some AI coding tools also read project-level skills directly from the code repository, such as `.claude/skills/` or `.agents/skills/`", and Multica does *not* auto-register those.

**`skills-lock.json` belongs to Vercel Labs' `skills` CLI** (`npx skills`), verified from `vercel-labs/skills/src/local-lock.ts`:

```jsonc
// skills-lock.json: "meant to be checked into version control"
{
  "version": 1,
  "skills": {
    "<skill-name>": {
      "source": "owner/repo | npm pkg | local path",
      "sourceUrl": "original remote URL (optional)",
      "ref": "branch or tag (optional)",
      "sourceType": "github | node_modules | local | ...",
      "skillPath": "skills/pdf/SKILL.md",   // so update refetches only this skill
      "computedHash": "<sha-256 of all files in the skill folder>",
      "subagents": ["..."],                  // optional
      "wellKnownDigest": "..."               // optional
    }
  }
}
```

Design notes worth stealing verbatim from their comments: "Intentionally minimal and timestamp-free to minimize merge conflicts. Two branches adding different skills produce non-overlapping JSON keys that git can auto-merge cleanly"; skills sorted alphabetically; corrupted/old lock ⇒ silently treated as empty. Manifest is `.skills.json` (`{"skills":[{"name","remote","version":"latest"}]}`); GitHub is the registry. Install semantics: only installs to `.agents/skills/` (the canonical project-level location); agent fan-out is **symlink-first**: universal agents (19 of them) read `.agents/skills` directly, non-universal agents get symlinks from the canonical location, with `--copy` as fallback. (A separately-formatted "lockVersion: 2" scheme with `base_commit`/`requested_by`/`dependencies` circulating in blog posts is happyskills.ai's fork-format, *not* Vercel's: don't conflate.)

## 5. HumanLayer's checked-in trilogy

All three live at `humanlayer/humanlayer/.claude/commands/` (repo now archived; also distilled in `humanlayer/advanced-context-engineering-for-coding-agents`: "frequent intentional compaction", keep context 40-60%).

**`research_codebase.md`** (frontmatter `description: Document codebase as-is...`, `model: opus`). Its defining constraint, verbatim:

> ## CRITICAL: YOUR ONLY JOB IS TO DOCUMENT AND EXPLAIN THE CODEBASE AS IT EXISTS TODAY
> - DO NOT suggest improvements or changes unless the user explicitly asks ...
> - ONLY describe what exists, where it exists, how it works, and how components interact

Process: read user-mentioned files FULLY in the main context first ("WITHOUT limit/offset"); decompose; spawn parallel specialized subagents: **codebase-locator** (WHERE), **codebase-analyzer** (HOW, "without critiquing"), **codebase-pattern-finder**, **thoughts-locator**/**thoughts-analyzer** (historical context), **web-search-researcher** only on request; "Don't write detailed prompts about HOW to search - the agents already know"; wait for ALL; write to `thoughts/shared/research/YYYY-MM-DD-ENG-XXXX-description.md` with YAML frontmatter (`date, researcher, git_commit, branch, repository, topic, tags, status, last_updated, last_updated_by`) and sections `## Research Question / Summary / Detailed Findings / Code References (path:line) / Architecture Documentation / Historical Context (from thoughts/) / Related Research / Open Questions`; swap file refs for GitHub permalinks when pushed; follow-ups append `## Follow-up Research [timestamp]` + `last_updated_note`.

**`create_plan.md`** (`model: opus`): interactive and skeptical: "Question vague requirements ... Don't assume - verify with code"; "Don't write the full plan in one shot - Get buy-in at each major step." Phases: read everything fully → parallel research subagents → present findings + focused questions → propose phase structure for approval → write `thoughts/shared/plans/YYYY-MM-DD-ENG-XXXX-description.md`. Plan template (abridged verbatim):

````markdown
# [Feature/Task Name] Implementation Plan

## Overview
## Current State Analysis
## Desired End State
### Key Discoveries:
- [Important finding with file:line reference]
## What We're NOT Doing
## Implementation Approach

## Phase 1: [Descriptive Name]
### Overview
### Changes Required:
#### 1. [Component/File Group]
**File**: `path/to/file.ext`
**Changes**: [Summary]
```[language]
// Specific code to add/modify
```
### Success Criteria:
#### Automated Verification:
- [ ] Unit tests pass: `make test-component`
- [ ] Type checking passes: `npm run typecheck`
#### Manual Verification:
- [ ] Feature works as expected when tested via UI

## Testing Strategy / Performance Considerations / Migration Notes / References
````

The automated/manual split is the load-bearing idea: "**Implementation Note**: After completing this phase and all automated verification passes, pause here for manual confirmation from the human ... before proceeding to the next phase."

**`implement_plan.md`** (no model pin): "Read the plan completely and check for any existing checkmarks (`- [x]`)"; "Follow the plan's intent while adapting to what you find"; on mismatch, STOP and present `Issue in Phase [N]: Expected/Found/Why this matters/How should I proceed?`; check off items in the plan file itself via Edit; per-phase human pause with a fixed report format; "do not check off items in the manual testing steps until confirmed by the user"; resuming: "Trust that completed work is done. Pick up from the first unchecked item."

**`thoughts/` layout & sync** (`hlyr/THOUGHTS.md`): in-repo `thoughts/` is git-ignored and symlinked into a central `~/thoughts` repo: `thoughts/{alice,shared,global/{alice,shared}}` plus auto-generated `thoughts/searchable/` (read-only *hard links*, because AI tools can't always follow symlinks) and an auto-generated `thoughts/CLAUDE.md`. Sync: pre-commit hook blocks committing `thoughts/` into the code repo; post-commit hook syncs to the thoughts repo and rebuilds `searchable/`; manual `humanlayer thoughts sync -m "..."`. Commands must rewrite `thoughts/searchable/x/y.md` → `thoughts/x/y.md` when citing.

# SYNTHESIS for open-seed

## (a) Skills layout: source-of-truth + fan-out + `seed.yaml`/`seed.lock`

**Source of truth**: `seed/skills/<name>/SKILL.md`: harness-neutral, strictly spec-conformant (name==dirname, required description, ≤500-line body, `references|scripts|assets`). **Fan-out, not symlinks, into checked-in per-harness dirs**: skillfold's copy model wins over Vercel's symlink model for a *template repo*, because symlinks break on Windows checkouts, zip downloads ("Use this template"), and some CI sandboxes; drift is instead policed by an offline `check` (adapt skillfold's integrity approach). Fan targets: `.claude/skills/` (native) and `.agents/skills/` (the spec's cross-client convention). Manifest, adapting skillfold with Vercel's merge-friendliness lessons:

```yaml
# seed.yaml
targets: [claude, agents]          # agents = .agents/skills + AGENTS.md rules block
skills:
  code-review: ./seed/skills/code-review              # local (no pin)
  frontend-design: github:anthropics/skills/skills/frontend-design@v1.2.0
compose:
  reviewer: {description: Review code with tests., use: [code-review, testing]}
rules:
  conventions: ./seed/rules/conventions.md
```

```yaml
# seed.lock  (committed; local entries pin nothing, remote entries pin sha+hash)
lockfileVersion: 1
skills:
  frontend-design:
    source: github:anthropics/skills/skills/frontend-design@v1.2.0
    resolved: github:anthropics/skills/skills/frontend-design@<40-hex sha>
    integrity: sha256-<base64>
```

Adopt wholesale: skillfold's install/update/check/`--frozen` semantics; the managed-directory rule (only prune/overwrite names present in the previous lock); rules → `.claude/rules/<name>.md` plus a `<!-- seed:rules:start/end -->` marker-fenced block in `AGENTS.md` (byte-exact round-trip makes `check` offline-verifiable); compose with DAG-only `use` and cycle detection. Keep entries timestamp-free and alphabetized (Vercel) so parallel branches merge cleanly.

## (b) Agent-role definitions: `.seed/agents/*.md` dual-format frontmatter

Merge shinpr's cross-CLI schema with Claude Code's native subagent frontmatter (`name`, `description`, `tools`, `model`) so one file can be fanned into `.claude/agents/<name>.md` verbatim *and* executed by a shinpr-style runner:

```markdown
---
name: code-reviewer                 # Claude Code subagent field; == filename
description: Reviews diffs for correctness and convention drift. Use after implementation phases.
role: reviewer                      # open-seed taxonomy: researcher|planner|implementer|reviewer
run-agent: claude                   # backend: codex|claude|cursor-agent|gemini|opencode|...
model: sonnet
effort: high                        # optional, opaque, forwarded per backend
permission: read-only               # read-only | safe-edit | yolo  (default safe-edit)
tools: Read, Grep, Glob             # Claude Code native tool allowlist (ignored by runner)
---

# Code Reviewer
One-sentence purpose.

## Task
- ...

## Out of Scope
- ...

## Done When
- All changed files reviewed
- Findings listed with file:line evidence
```

Rules: flat scalars only (shinpr's parser is regex-per-line: nested YAML would silently drop fields); `permission` tiers map exactly to shinpr's tables (vendor `_builder.py`'s mappings rather than reinventing); `## Done When` is mandatory (it doubles as the reviewer's checklist and as humanlayer-style success criteria); bodies self-contained, single-responsibility. Fan-out step copies `.seed/agents/*.md` → `.claude/agents/` unchanged (Claude Code ignores unknown frontmatter keys) and leaves `.seed/agents/` as the runner's discovery dir via `SUB_AGENTS_DIR`. For a template repo, ship `claude` + `codex` backends only and leave the rest as documented extension points.

## (c) Command set: the trilogy, adapted

Ship as skills (portable across harnesses via (a)) rather than `.claude/commands/`: `research`, `plan`, `implement`, plus a small `validate-plan` (humanlayer has `validate_plan.md` too). Adaptations:

- **`/research`**: keep the documentarian constraint block ("document what IS, not what SHOULD BE") and the read-mentioned-files-first / spawn-parallel-locator-analyzer / wait-for-all ordering. Replace `thoughts/` with a committed `docs/research/YYYY-MM-DD-topic.md` carrying humanlayer's frontmatter minus the researcher-symlink machinery: drop the entire thoughts-sync/searchable/hard-link apparatus (it needs a companion CLI and a personal notes repo; a template can't assume either). Point the subagent roles at the (b) definitions: `researcher` agents are `permission: read-only`.
- **`/plan`**: keep interactive skepticism, phase-structure approval before detail, and the plan template above with the **Automated vs Manual Verification** split and per-phase human pause verbatim. Output to `docs/plans/YYYY-MM-DD-description.md`.
- **`/implement`**: keep checkmark-resume semantics, the mismatch-report format, and "don't check manual boxes until the user confirms."

**Corrections to earlier survey findings**: (1) multica does *not* own `.agents/skills` playbooks or `skills-lock.json`: the lockfile is Vercel Labs' `skills` CLI (`version: 1`, hash-per-folder), and the "lockVersion: 2 with dependencies" format floating in blogs is happyskills', a third format; (2) the Agent Skills spec is unversioned and does not standardize discovery paths: `.agents/skills/` is convention, documented only in the client-implementation guide; (3) skillfold's lock has *no* dependency graph (compose is manifest-level, not lock-level resolution), if open-seed wants skills-depending-on-skills beyond concatenation, that's novel territory none of these tools cover; (4) humanlayer's commands are markdown *prompts* with only `description`/`model` frontmatter: permission tiers there are enforced by which subagents get spawned, not by frontmatter, which is exactly the gap the (b) format closes.
