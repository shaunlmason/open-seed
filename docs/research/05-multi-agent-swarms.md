# Research: Multi-Agent Swarms

> Category survey of [awesome-agent-orchestrators](https://github.com/andyrewlee/awesome-agent-orchestrators),
> researched 2026-08-21 for the open-seed design study. Focus: what can live *inside* a repo
> vs. what requires an external app/daemon.

All 25 repos exist and were fetched. Ordered roughly by relevance to a checked-in template repo. Key for each: (a) what, (b) topology, (c) decomposition/tracking, (d) comms, (e) guardrails, (f) in-repo vs external, (g) harness, (h) maturity, (i) steal-worthy ideas.

## Deep-dive projects

### gastown (gastownhall/gastown) — Steve Yegge, ~17.7k★, Go, MIT, very active
(a) The flagship of the category: a persistent workspace ("Town" at `~/gt/`) coordinating 20-30+ coding agents across multiple repos, built around the thesis that work state must live in git, not in agent memory. (b) Deeply hierarchical with supervision tiers: the **Mayor** (a Claude Code instance with full workspace context) coordinates; **Polecats** are workers with "persistent identity but ephemeral sessions"; **Crew** are human workspaces; then a watchdog chain — per-rig **Witness** (detects stuck agents, triggers recovery), cross-rig **Deacon** ("continuous patrol cycles"), and the daemon/Boot at the top. (c) Work is tracked in **beads** (gastownhall/beads, 26.5k★), a *separate, standalone* git-distributed graph issue tracker built explicitly to replace "messy markdown task lists" for agents. Beads is Dolt-backed (versioned SQL), with `.beads/issues.jsonl` as the git-interchange/export format; hash-based IDs (`gt-abc12`) avoid merge collisions across branches/agents; `bd ready` lists unblocked issues, `bd update <id> --claim` is an atomic claim, `bd dep add` builds the dependency graph, `bd prime` injects workflow context, `bd remember` stores durable memory. Gastown bundles beads into **convoys** (batches assigned to agents) and templates workflows as TOML **formulas** instantiated into **molecules** with checkpoint recovery. (d) Comms: an internal mail system (`gt mail check --inject`) plus git itself; agents are re-primed at session start (`gt prime`). (e) Guardrails: the **Refinery**, a per-rig Bors-style bisecting merge queue — "runs verification gates on the merged stack. If green: all MRs in batch merge to main. If red: bisects to isolate the failing MR, merges the good ones"; severity-tiered escalation (P0/P1/P2) routed up the hierarchy; the GUPP propulsion principle (if there's work on your hook, you run it). (f/g) Everything of substance is *outside* the target repo: HQ workspace, Dolt DB, tmux-hosted daemons. Persistence-in-git is via **hooks = git worktrees** as durable work containers. Multi-harness (Claude Code primary; Copilot, Codex, Gemini). (h) Very mature/fast-moving. (i) Steal: the *beads model itself* (git-syncable JSONL issue graph with dependencies, atomic claims, ready-work query, hash IDs); "issues as agent memory"; convoy bundling; the three-tier watchdog concept; bisecting merge queue as the single quality funnel. Note beads is adoptable without gastown — it is the single most template-compatible piece of this ecosystem.

### loki-mode (asklokesh/loki-mode) — ~1k★, Bash+TypeScript/Bun, BUSL-1.1
(a) PRD-to-deployed autonomous SDLC: feed it a Markdown PRD/GitHub issue/OpenAPI spec, it builds, tests, and prepares deployment. (b) 41 agent roles across 8 domains that "automatically compose based on complexity" — a virtual company, not a fixed pipeline. Core loop is **RARV: Reason-Act-Reflect-Verify**, iterating "until verified completion, not just attempted work." (c) Tracking internal to `.loki/` state in the project; spec is locked with `loki spec` and a `drift-report.json` surfaces divergence from requirements. (d) Comms via the orchestration engine + an MCP server; dashboard for monitoring. (e) The standout: **eight deterministic quality gates** — static analysis; test suite; *blind 3-reviewer code review*; an *anti-sycophancy "Devil's Advocate" check*; mock-integrity detection; test-mutation detection; documentation coverage; "Magic Modules debate." It "refuses 'done' status on empty diffs or failing tests" and emits **Evidence Receipts** in `.loki/proofs/` binding facts to a specific `diff_sha256`, separating deterministic facts (exit codes, gate verdicts) from AI assessments; headline is computed from facts alone (VERIFIED / VERIFIED WITH GAPS / NOT VERIFIED), optionally GPG-signed. (f) Installed globally; run artifacts land in the project (`.loki/`). (g) Claude Code Tier 1; Cline/Codex/Aider/opencode experimental with automatic failover. (h) Heavily developed; self-admits no security audit. (i) Steal: evidence receipts (facts vs. opinions, diff-hash binding), anti-sycophancy adversarial gate, mutation/mock-integrity checks as *deterministic* gates, spec-lock + drift report. All conceptually implementable as checked-in scripts/CI.

### kodo (ikamensh/kodo) — 128★, Python, MIT
(a) Overnight autonomous coding orchestrator whose thesis is *independent verification*: claims "adding Kodo's orchestration layer solves 24% more real-world GitHub issues" than a single agent. (b) Coordinator-worker with role separation: a cheap **orchestrator** (Gemini Flash, ~$0.13/run) directs subscription-covered Claude Code agents; roles are architect (survey/review), worker_smart (Opus, complex), worker_fast (iterations), tester, tester_browser. (c) Goals decompose into **stages** — "an independently verifiable piece of a plan" — executed sequentially or in parallel via git worktrees. (d) Orchestrator tool-calls; no peer messaging. (e) The verification loop: after a worker finishes, architect + tester(s) independently review; a rejection sends work back; acceptance requires *all* reviewers. (f) `.kodo/` in the project holds config/run logs; team composition is a checked-in **`team.json`** with backend/model/system_prompt/max_turns/timeout per agent. (h) Small but focused; benchmark-driven. (i) Steal: the cheap-orchestrator/expensive-worker economics; "stage = independently verifiable unit" as decomposition rule; declarative team.json checked into the repo; accept-only-on-unanimous-reviewer-approval.

### Fusion (Runfusion/Fusion) — 1.1k★, TypeScript, MIT, early preview
(a) "AI-powered software factory": kanban app driving tasks Planning → Todo → In Progress → In Review → Done. (b) Coordinator-worker via an app; also an "agent company" of 440+ pre-built agents in 16 teams. (c) Tasks in PostgreSQL (embedded locally); each task gets its own worktree/branch `fusion/{task-id}`. Planning agent emits a **`PROMPT.md`** per task with "steps, file scope, and acceptance criteria" — the reviewed blueprint. (d) "Built-in mailbox between agents" for delegation/handoffs. (e) The **plan-review-execute-review** double gate: both the *plan* and the *implementation* are reviewed against acceptance criteria; pre-merge gates block, post-merge gates inform; per-task automation levels `off/observe/steer/autonomous`, with merges and destructive actions always requiring "explicit human confirmation." (f) Repo gets branches/worktrees + task metadata; everything else lives in the app. (h) Early but very active. (i) Steal: reviewing the *plan* as a first-class gated artifact (PROMPT.md with file scope + acceptance criteria); graduated automation levels; pre-merge-blocking vs post-merge-informational gate distinction.

### orc (spencermarx/orc) — 23★, Bash/TypeScript, active
(a) Deliberately minimal orchestration that "piggybacks" your existing CLI setup: "Your tools. Your workflow. Your rules. No daemon, no server, no lock-in." (b) Hierarchy of *orchestrators that never write code*: Root → Project → Goal orchestrators, spawning ephemeral Scouts/Planners and persistent Engineers in isolated worktrees, each with an ephemeral Reviewer. (c) **Goals** (deliverable + dedicated branch) decompose into **beads** — it literally uses Yegge's beads (`bd`, Dolt-backed) as its tracking layer. Lifecycle: "Investigate → Plan → Decompose → Dispatch → Setup → Build → Review → Deliver." (d) tmux panes + slash commands (`/orc:plan`, `/orc:dispatch`, `/orc:done`); "Markdown is the control plane." (e) Every bead is reviewed before merging to the goal branch; user escalation is configurable; conflicts escalate to the human, never force-pushed. (f) The most interesting repo-footprint decision in the set: config is committed at `.orc/config.toml` (3-tier resolution config.toml → config.local.toml), where each phase is steered by **natural-language instruction strings**, e.g. `plan_creation_instructions = "/openspec:proposal"`, `review_instructions = "/ocr:review"`, `on_completion_instructions = "Push the branch, create a PR targeting main, update the Jira ticket."` Runtime dirs (`.beads/`, `.worktrees/`, `.goals/`) are hidden via `.git/info/exclude` rather than touching `.gitignore`. (g) Auto-detects Claude Code/OpenCode/Codex/Gemini; needs tmux + bd. (h) Young, tiny, but the design is unusually clean. (i) Steal: committed TOML where every lifecycle phase is a natural-language prompt (composable with any existing slash commands/tools); orchestrators-don't-code rule; the exclude-not-gitignore trick.

### tutti (nutthouse/tutti) — 112★, Rust, MIT, v0.10
(a) "Operations layer" treating agent-team management as **infrastructure-as-code**: "Agent SDKs help you build agents. Tutti helps you run agent work." (b) Config-driven pipeline topology, not a fixed hierarchy. (c/f) The whole point is the committed **`tutti.toml`** ("org code"): `[roles]` map role→runtime (`implementer = "claude-code"`, `tester = "codex"`), `[[agent]]` entries declare name/role/**scope** globs (`scope = "src/api/**"`), and `[[workflow]]` blocks define steps of types `prompt`, `command`, `ensure_running`, nested `workflow`, `review`, `land`, with `depends_on` for parallelism. Local state in `.tutti/state/` (checkpoints, `run-telemetry.jsonl`). (d) **Typed artifact passing**: a step declares `artifact_glob`/`artifact_name`, downstream steps inject via `{{output.artifact_name.path}}`, with automatic staging into the receiving agent's worktree. (e) `land` steps enforce merge gates — GitHub PR checks green, review threads resolved, approvals present; `[permissions]` policy gates allowlist shell commands/tools for non-interactive runs. Per-agent worktrees, `fresh_worktree = true` optional. Resume via `tt run --resume <run_id>`. (g) Claude Code, Codex, Aider, OpenClaw; tmux-managed sessions. (h) Pre-1.0 but coherent. (i) Steal: this is the closest existing thing to open-seed's premise — a single committed TOML declaring roles, agent scopes, workflows, artifact contracts, and land gates. The artifact_glob→inject pattern and scoped agents are directly transferable.

### paperclip (paperclipai/paperclip) — 79.1k★, TypeScript/Node, extremely popular
(a) "The app people use to manage AI agents for work" — org control plane: "If OpenClaw is an employee, Paperclip is the company." (b) Corporate hierarchy: agents have roles, titles, reporting lines, permissions, budgets; mixed human/agent org charts with delegation both directions. (c) Ticket-based tasks in PostgreSQL with company/project/goal/parent links; tickets carry "full goal ancestry so agents consistently see the 'why,' not just a title." (d) The wake model: **heartbeats** (scheduled wake-ups where agents check assignments) + **event triggers** (assignment, @-mentions, webhooks). Claiming is "atomic checkout with execution locks" — exactly one agent per ticket. (e) Board-level approval workflows; execution policies with review/approval stages; governors can pause or terminate any agent; immutable audit log + full tool-call tracing; multi-level token/cost budgets with **hard stops**. (f) Self-hosted Node server + React UI; nothing lives in the target repo; agents configured via AGENTS.md files. (g) Provider-agnostic. (h) Most mature by adoption in this set. (i) Steal: heartbeat + atomic-claim as the idle-agent pattern (a cron/CI job that wakes an agent to `claim` the next ready ticket reproduces this in-repo); goal ancestry on every task; budget hard-stops as policy.

### shire (victor36max/shire) — 37★, TypeScript/Bun, MIT
(a) Persistent team workspaces: agents persist between sessions, communicate autonomously, build on yesterday's work. (b) Explicitly **anti-orchestrator peer mesh** — agents "collaborate on their own — no orchestrator required," discovering peers and direct-messaging. (c) No formal tracker; work accretes in each project's **shared drive** (communal filesystem per project). Scheduled one-time/recurring messages drive recurring work. (d) Inter-agent mailboxes/DMs through the platform. (e) Weak — no reviewer roles. (f) All state in `~/.shire/`; nothing committed to a target repo. (g) Abstracts Claude Code SDK, OpenCode SDK, Pi Agent SDK, Codex SDK. (h) Early, small. (i) Steal: the *persistent workspace + shared drive* framing (in a template: a committed `workspace/` dir agents treat as the team's durable artifact space), and scheduled-message-as-standup.

### ORCH (oxgeneral/ORCH) — 146★, TypeScript, MIT
(a) "Run multiple AI agents on one project — without babysitting any of them." (b) Typed teams (`orch team create --lead <agent-id>`; templates like `startup-mvp` with CTO/Backend/QA/Reviewer); orchestrator engine drives an explicit state machine. (c) `todo → in_progress → review → done`; "Every transition validated. No task gets lost. No code merges without approval." All state is **plain files**: "All state in `.orchestry/` — plain YAML, JSON, JSONL files. No database. No cloud. No Docker." Lock file prevents dual orchestrators. Tasks have priorities 1-4 and retry with exponential backoff; scope-overlap detection prevents agents colliding. (d) `orch msg send <agent-id>`, `orch msg broadcast --team`, plus a shared context store. (e) "Mandatory review step in the state machine — no code ships without your OK"; "Reject with feedback → task goes back to engineering with your notes." Isolated worktrees; main never touched until explicit approval. (f) `.orchestry/` sits in the repo (config committable, runtime state not); zero infra. (g) Adapters: Claude Code, OpenCode, Codex, Pi, Cursor, Grok, Antigravity, and a **shell adapter** ("if it runs in a terminal, it's an agent" — wrap npm test, Semgrep, curl as team members). (h) Modest but tidy. Modes: TUI, `orch run`, `orch serve` daemon, and `orch serve --once` for CI (exit 0/1). (i) Steal: file-based state machine with validated transitions and a lock file; shell-adapter idea (deterministic tools as first-class "agents" in the team); `--once` CI mode.

- **AgentsMesh/AgentsMesh** (2.3k★, Go/Rust, BUSL): control-plane/data-plane fleet manager; AgentPods in sandboxes with worktrees, kanban "Tickets," @mention channels; heavy external stack. The `.agents/skills/` dir is the only in-repo piece.
- **AutoResearch-Factory/Agon** (42★, MIT): Claude Code *plugin*; Scientist/Coder/Auditor/Reviewer closed loops for research; "all handoffs occur through filesystem artifacts, making runs recoverable and auditable"; tick commands (`/idea-tick`, `/experiment-tick`). - **SeemSeam/claude_codex_bridge** (3.4k★): terminal hub bridging heterogeneous CLI agents into A→B→C collaboration graphs; durable shared memory in a committable **`.ccb/ccb_memory.md`**; explicit command approval; circuit breakers on restarts. - **aannoo/hcom** (460★, Rust, MIT): "hook your coding agents together" — installs *hooks* into each CLI's config; activity recorded to local SQLite, messages delivered mid-turn between tool calls or wake idle agents; **file-edit collision detection** (two agents editing the same file within 30s triggers an alert); encrypted MQTT for cross-device. - **yohey-w/multi-agent-shogun** (1.4k★, Bash/YAML): Shogun(1)/Karo(1, manager+QA)/Gunshi(1, design review)/Ashigaru(7 workers) over tmux. # SYNTHESIS

**Topologies cluster into three families.** (1) **Hierarchical command**: gastown (Mayor→Polecats + Witness/Deacon supervision), orc (root→project→goal orchestrators who never code), shogun (Shogun→Karo→Ashigaru), Orkas, kodo, loki-mode, paperclip's org chart. The consistent winning refinements: a *cheap* coordinator model directing expensive workers (kodo), coordinators forbidden from writing code (orc), and a *supervision* hierarchy separate from the *work* hierarchy (gastown's watchdog chain — health monitoring is its own tier, not the manager's job). (2) **Peer mesh**: shire, hcom, buzz, ClawTeam post-spawn — agents message each other directly; simplest to run, weakest at guaranteeing anything gets finished; every mesh system compensates with either collision detection (hcom) or signed audit logs (buzz). (3) **Blackboard / ticket-claim**: paperclip, agent-kanban, AgentsMesh, 5dive, and beads-based systems — no one assigns work; agents wake (heartbeat or event) and *atomically claim* the next ready ticket. This is the most robust to agent death and the easiest to make harness-agnostic, because the coordination contract is just "the tracker" — and it degrades gracefully to a single agent. For a template repo, ticket-claim over a checked-in tracker is the natural core, with an optional lightweight coordinator layered on top.

**Git as coordination substrate** is the field's strongest convergent finding, in four distinct uses: (1) **worktree isolation** — near-universal: one agent = one worktree = one branch; naming conventions like `fusion/{task-id}` make ownership legible. (2) **Git-backed work state** — gastown's whole thesis: worktrees as persistent work containers so work persists across agent crashes, and beads storing the issue graph in versioned, git-syncable form (`issues.jsonl` interchange, hash IDs designed for merge-without-collision). (3) **Merge queue as the choke point** — gastown's Refinery (Bors-style bisecting batch verification) and tutti's `land` gates make git merge the single place quality is enforced. (4) **Footprint hygiene** — orc's `.git/info/exclude` trick keeps runtime dirs out of both history and `.gitignore` diffs; the general pattern across mature tools is *config committed, runtime state excluded*.

**Verification patterns**, in ascending strength: (1) *manager review* — cheap, sycophancy-prone; (2) *plan-gating before execution* (Fusion's reviewed PROMPT.md with file scope + acceptance criteria) — catches misdirection before tokens are burned; (3) *independent verifier agents with rejection loops* (kodo's architect+tester unanimity; loki's blind 3-reviewer panel) — key property is that the verifier shares no context with the implementer; (4) *deterministic gates* (loki's static analysis, mutation testing, mock-integrity, empty-diff refusal; tutti's CI-check land gates; ORCH's validated state transitions) — the trend in the most credible projects is pushing verification *out of LLM judgment into scripts*, with loki's Evidence Receipts (facts bound to `diff_sha256`, verdict computed from facts alone) as the endpoint; (5) *batch merge verification* (gastown's bisecting Refinery). Also notable: loki's anti-sycophancy Devil's Advocate gate — an agent explicitly prompted to argue the work is wrong.

**The five ideas most transferable to a checked-in template repo:**

1. **A git-native issue graph with atomic claims (beads pattern).** Checked-in tracker (JSONL or beads itself) with dependency edges, `ready` queries, hash-based collision-free IDs, and atomic `--claim`. This single artifact provides decomposition, tracking, memory-across-sessions, and multi-agent mutex — and it's what both Yegge projects and orc independently bet on. open-seed could ship `bd` bootstrap config or a minimal `scripts/tasks.sh` over a committed `tasks/issues.jsonl`.
2. **Lifecycle-as-committed-config with natural-language phase hooks (orc/tutti pattern).** A `seed.toml` where roles map to runtimes, agents get scope globs, and each phase (plan/decompose/build/review/deliver) is a prompt string or slash-command reference — "org code" that's diffable, reviewable, and harness-portable. Tutti's `artifact_glob` → `{{output.name.path}}` injection shows how to make handoffs typed instead of vibes.
3. **Plan-as-gated-artifact (Fusion pattern).** Require every task to produce a committed plan file (steps, file scope, acceptance criteria) that is reviewed — by human or a reviewer agent — before execution; then review implementation *against that same file*. Two cheap markdown conventions buy the biggest quality lift per token.
4. **Deterministic evidence over self-report (loki pattern).** Checked-in gate scripts + CI: refuse "done" on empty diff or red tests; write a machine-readable receipt (`proofs/<task>.json` with diff hash, test exit codes, gate verdicts) per completed task. Optionally add hcom-style hooks for file-collision detection and ORCH-style enforced state transitions in the task files.
5. **Independent verifier roles declared in the repo (kodo pattern).** A committed `team.json`/roles dir defining implementer vs. architect-reviewer vs. tester with separate prompts and a rejection loop ("all reviewers approve or work returns"), plus shogun's races-avoided files-as-mailboxes (`queue/<agent>.yaml`, content in files, only a "you have mail" nudge) if inter-agent messaging is needed without any daemon.

The overall lesson: the external-app orchestrators (paperclip, Fusion, AgentsMesh, buzz) win on supervision UX and budgets, but everything that actually determines output quality — task graph, plan gates, verifier separation, deterministic receipts, merge gates — has at least one existence proof living entirely in files, hooks, and CI inside a repo, which is exactly open-seed's lane. The closest prior art to open-seed as a whole is **tutti** (committed org-code TOML) plus **beads** (committed task graph) plus **loki's gates** (committed verification scripts); no project yet combines all three in template form.
