# os-f262585a — Lift the internal/ coverage floor so `verify` stops flaking at the 90.1% margin

## What the tree actually shows

`make check` (via `cmd/covergate -gate 90 -dir .`, aggregating `-coverpkg=./internal/...`)
reads the tree at **~90.1%** — one tenth above the gate. `seed receipt verify --run`
does its OWN separate COLD `make check` (a fresh coverage collection, not the
`check` job's), and cold collection has a few tenths of run-to-run variance. At a
0.1% margin a receipt that is green when generated can have its verify collection
draw under 90 and fail as a `receipt mismatch` — the regenerated validation
disagrees with the committed one. Observed directly on os-ad610334: commit
`b8b6335`'s verify failed while `54aac5e` (a fresh regen at the same 90.1%) passed;
every task PR (this cohort saw it on 13.2, 13.3, 13.6, 13.7) draws from the same
lottery, costing a regenerate-and-rerun each time.

The fix is not a gate change — it is real coverage. os-ad610334 already began it
(its `coverage_extra_test.go` took `internal/protections` from 89.7% to ~90.2% by
testing the forge adapter's thin paths); this card carries that across `internal/`
until a bad draw still lands ≥90.

## Design decisions (binding for this task)

**D1. Tests only. No gate, ceiling, or behavior moves.** `cmd/covergate`'s `-gate 90`
stays 90; `perf/budgets.json` is untouched; no product code changes except where a
genuinely dead branch is better deleted than tested (called out per case, not as a
habit). The aggregate rises because real, previously-unexercised paths get honest
tests — never assertion-free "coverage" tests that execute lines without checking
behavior.

**D2. Target a real margin, not the line.** Raise the `./internal/...` aggregate to
**≥90.7%** (covergate's reading), aiming for ~91%, so the cold-collection variance
(observed within a few tenths) no longer crosses 90. The acceptance check is two
explicitly cold collections — `go clean -testcache` before each, serialized with
`-p 1`, the gate's own flags (`go test ./... -coverprofile=<tmp> -covermode=atomic
-coverpkg=./internal/...`) — both reading ≥90.7%. covergate's own re-collection
rule cannot supply these: it goes cold only after a below-gate first reading, so
at the new floor two plain covergate runs would be two warm happy-path
collections.

**D3. Go where the uncovered lines are, measured first.** Per-package `-coverpkg`
survey picks the lowest-covered packages, run on the same test package set the
gate measures — `./...` with `-coverpkg=./internal/...` — because `cmd/seed`
tests that call internal packages contribute to the gate's profile, and a
`./internal/...`-only survey would rank lines against a different profile. The
known starting set is `internal/protections` (forgejo.go/observer.go error
branches — `Apply`, `putBranch`, `putTag`, `do`, `Merged`, already scoped on
os-ad610334 and carried in this session's stash), then the next lowest packages
the survey names. Effort goes to the packages that move the aggregate most per
test.

**D4. Only `./internal/...` is instrumented.** `cmd/` statements are not in
`-coverpkg=./internal/...`, so this card adds no `cmd/` tests and spends no
effort on `cmd/` coverage (a separate concern if ever wanted); the scope is
`internal/` test files. (That does not make `cmd/seed` tests invisible to the
gate: they exercise internal packages and contribute to its profile, which is
why the D3 survey runs the gate's own `./...` test set.)

**D5. Bounds.** No admission, transition, ledger, projection, spec-normative, or
executor-adapter behavior change. No plan/receipt-tooling change. New/expanded
`_test.go` files under `next/internal/**` only, plus the progress line. Independent
of any other Phase 13 card — it touches tests, not their subjects' behavior.

## Steps

1. Measure per-package coverage the way the gate measures it (one `go test -p 1
   ./... -coverprofile=/tmp/cover-survey.out -covermode=atomic
   -coverpkg=./internal/...`, then `go tool cover
   -func=/tmp/cover-survey.out`), and rank packages by uncovered statements
   weighted by size.
2. Add honest tests for the highest-yield thin paths, starting with
   `internal/protections` (the forge error branches carried from os-ad610334) and
   proceeding down the ranked list until covergate reads ≥90.7%.
3. Take the two acceptance readings, each cold: `go clean -testcache`, then
   `go test -p 1 ./... -coverprofile=<tmp> -covermode=atomic
   -coverpkg=./internal/...` and `go tool cover -func=<tmp>` — both ≥90.7% —
   and `make check` green end to end.
4. Update `next/docs/progress.md` with this card's line; note the flake and the new
   floor in `memory/LEARNINGS.md`.

## Acceptance Criteria

- Two explicitly cold collections — `go clean -testcache` before each, serialized
  with `-p 1`, the gate's own flags (`go test ./... -coverprofile=<tmp>
  -covermode=atomic -coverpkg=./internal/...`) — both report **≥90.7%**, up from
  ~90.1%. (covergate's re-collection rule cannot supply these: it goes cold only
  after a below-gate first reading, so at the new floor two plain covergate runs
  are two warm happy-path collections.)
- `go run ./cmd/covergate -gate 90 -dir .` passes (the warm happy path stays
  green).
- Every added test asserts behavior (inputs → checked outputs/errors), not bare line
  execution; no test is skipped or `t.Skip`-gated to inflate the number.
- `cmd/covergate`'s `-gate` value and `perf/budgets.json` are unchanged.
- No non-test change under `next/**` except any explicitly-justified dead-branch
  deletion; `make check` green.

## Validation Commands

- Coverage floor (warm): `cd next && go run ./cmd/covergate -gate 90 -dir .`
- Coverage floor (cold acceptance reading, taken twice): `cd next && go clean
  -testcache && go test -p 1 ./... -coverprofile=/tmp/cover-cold.out
  -covermode=atomic -coverpkg=./internal/... && go tool cover
  -func=/tmp/cover-cold.out | tail -1`
- Retention: `cd next && gofmt -l . && go vet ./... && go build ./... && go test ./... -count=1`
- Retention: `make check`

New and expanded `*_test.go` files under `next/internal/**`, a one-line
