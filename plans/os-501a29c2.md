# Plan: v2 opinionated stack template flavors — mechanism decision + the TypeScript flavor (os-501a29c2)

Design §10 Q3 fixes the v1 core as language-agnostic: "The template's only
contract with the project's stack is `make check` (the fast backpressure
command) plus the hooks. Opinionated stack variants (e.g. a TypeScript flavor
with lint/test/typecheck pre-wired into `make check`) are v2 template flavors,
never the v1 core." This card builds that mechanism and its first flavor.

The card is explicit that the mechanism decision comes **before** any flavor,
and that the decision must state how flavors interact with the template
release/update surface (`.seed/template.lock`, `seed template upgrade`, §10 Q4)
so a flavored instantiation can track template releases. Steps 1–3 settle that;
steps 4–8 build the TypeScript flavor against it.

> Revision note (review of PR #54, Codex + Copilot): the first draft claimed
> ordinary `template upgrade` merging kept installed flavors current. It does
> not, and the correction is load-bearing enough to have reshaped the
> mechanism: see "Why install alone is not an update path". The draft also
> wired the flavor's instantiation test into `scripts/validate.sh` (unbounded
> recursion, and it made the core gate network-dependent) and asserted core
> purity with a merge-base diff (vacuous on `main`, spurious on every later
> branch). Steps 3, 7 and 8 replace all three.

## Decision to be recorded (step 1)

Three candidate mechanisms, from the card's own scope list:

1. **Template variant repos** — one repo per flavor. Rejected: each variant
   becomes a fork that must independently track upstream. `.seed/template.lock`
   carries exactly one `repo` line, so a flavored instantiation would track
   either the variant (and never see core releases) or the core (and never see
   flavor updates). That breaks the §10 Q4 update surface the card requires the
   decision to preserve, and multiplies the maintainer release checklist
   (`docs/handbook.md:428`) by the number of flavors.
2. **Engine-side `seed init --flavor`** — the flavor lives in the engine.
   Rejected: the engine is a separate Go repository shipping pinned release
   binaries (§7.5, `decisions/0001-engine-repo.md`), pinned by
   `.seed/engine.lock`, which advances on its own release train independent of
   `.seed/template.lock`. Flavor *content* there would version against the
   engine, not against the template it was installed into, so
   `seed template upgrade` could never reason about it. Engine work also
   happens in the other repo, which this card is not scoped to.
3. **Flavor directory in the core template, an install step, and a recorded
   reconciliation path** — **adopted.** `flavors/<name>/` ships inside the core
   template, so there is one upstream repo and one `template.lock`, and
   `seed template upgrade` carries new flavor *payload* to the consumer like
   any other template content. Applying that payload to the files the consumer
   actually runs is a second, explicit step (step 3), because install-time
   copies are not something `template upgrade` can reconcile on its own.

   This is the template channel, and that is the right channel by §10 Q4's
   split, which `plans/os-221f5929.md` states as "plugin carrying
   capabilities, template carrying structure". A flavor is *structure*: a
   `Makefile` recipe, compiler options, a dependency set. It is the same
   reading that keeps seed workflow DAGs on the template channel there, and
   this plan adopts that framing rather than coining a second one.

## Why install alone is not an update path

The first draft of this plan asserted that `template upgrade`'s three-way merge
"carries flavor updates exactly as it carries any other template content."
That is false, and both PR reviewers caught it independently. `template
upgrade` merges by **path**. If install copies
`flavors/typescript/package.json` to `/package.json`, then a later release that
edits `flavors/typescript/package.json` updates only that path in the
consumer's repo: upstream has never owned `/package.json`, so the file the
consumer's `make check` actually runs stays at the version it was installed at,
forever. Combined with the draft's "refuse on an already-flavored repo" rule,
there was no supported way to ever apply a new payload.

Two corrections follow, and both are part of the adopted mechanism:

- **Thin root, fat flavor dir.** The install step writes as little as possible
  into paths upstream does not own, and what it does write is thin and stable.
  Everything that churns — compiler options, lint rules, the check recipe's
  body — lives under `flavors/<name>/`, where `template upgrade` merges it
  normally. Root `tsconfig.json` becomes a two-line `extends` of a base under
  `flavors/typescript/`; the root `Makefile`'s flavored recipe delegates rather
  than inlining the tool invocations. The root `Makefile` is additionally a
  path upstream *does* own, so upstream changes to it three-way merge, with
  conflicts against the flavored recipe surfacing as ordinary markers.
- **Recorded ownership metadata plus an explicit reapply verb.** The residue
  that cannot be made thin is real: npm requires dependency versions in the
  root `package.json`, and those churn. So install records what it wrote and
  at which template version, and a second verb reconciles it (step 3). Without
  the recorded base there is no honest merge to perform, only a clobber.

The honest limit to state in the ADR, rather than paper over: flavor
reconciliation is a **separate, consumer-initiated step** from `seed template
upgrade`, not an automatic consequence of it. A consumer who upgrades the
template and never runs the flavor verb keeps running their installed payload.
The docs must say this plainly.

## Interpreting "the flavor must not leak into the core"

The card's acceptance says "the unflavored template is byte-identical to today
(validate.sh green, fan-out drift check green)". Read literally, adding any
file would fail it, which would make shipping a flavor impossible under any of
the three mechanisms. The parenthetical names the checks that are meant, so
this plan reads it as: **no existing core file changes behaviour, and the
unflavored template's `make check` produces what it produces today**, with new
files (the `flavors/` tree, the install step, the ADR, docs) as additions.

The first draft tried to prove this with `git diff --quiet <merge-base> --
Makefile .seed AGENTS.md CLAUDE.md` as a permanent test. That is the wrong
instrument: on `main` after merge the merge-base is `HEAD`, so the assertion is
vacuous, and on any later branch it fails on legitimate core changes that have
nothing to do with flavors. Step 8 replaces it with two invariants that are
meaningful on every branch, forever.

## Steps

1. **Record the mechanism decision as an ADR** at
   `decisions/0002-template-flavors.md`, following the shape of
   `decisions/0001-engine-repo.md` (title, `**Date:**`, `**Status:** accepted`,
   prose). Content: the adopted mechanism, the two rejected alternatives with
   the reasons above, the thin-root/fat-flavor-dir rule and why it exists, the
   recorded-metadata reconciliation path, and the explicit statement that
   flavor reconciliation is consumer-initiated and separate from `seed template
   upgrade`. ADRs in that directory are append-only (`decisions/** merge=union`
   in `.gitattributes`): add a new file, never edit `0001`.

2. **Ship the flavor contract** as `flavors/README.md`: what a flavor is, what
   it may and may not touch, and the rule that keeps §10 Q3 true — **a flavor
   never changes the core template**; it only writes into the consumer's
   instantiation. State the required layout for `flavors/<name>/`: a
   `README.md`, a `manifest` listing the payload-file → destination-path pairs
   the install step writes, and the payload files themselves. State the
   thin-root rule as a contract on flavor authors, not just a property of the
   TypeScript flavor: a destination outside `flavors/` must be thin and stable,
   with churn kept in the flavor directory.

3. **Ship the install and reconcile steps** as `scripts/seed-flavor` (POSIX
   `sh`, the idiom of `scripts/validate.sh` and `scripts/seed-dispatch-route`):
   `seed-flavor list`, `seed-flavor install <name>`, `seed-flavor upgrade`,
   `seed-flavor status`.

   - `install` refuses (non-zero, explicit message) when `.seed/flavor.lock`
     already exists, naming `seed-flavor upgrade` as the supported path; when
     the target `Makefile` is not byte-identical to the core template's shipped
     `Makefile`; or when any destination file the manifest names already
     exists. A flavor install is a fresh-instantiation scaffold, and refusing
     with the reason plus the alternative is the honest behaviour rather than
     silently discarding the consumer's work.
   - On success `install` copies the manifest's destinations into place and
     writes **`.seed/flavor.lock`**: the flavor name, the `version` line read
     from `.seed/template.lock` at install time, and the SHA-256 of every file
     it wrote. This is the recorded base the reviewers correctly identified as
     missing. It sits beside `engine.lock`, `template.lock`, `seed.lock` and
     `backends.lock.json`, which is the established lockfile idiom; `.seed/**`
     is protected control surface, so its creation is a reviewed change.
   - `upgrade` reconciles the installed payload against the current one, per
     destination file: unchanged since install (hash matches the lock) →
     overwrite cleanly; diverged → three-way merge with `git merge-file` using
     the *installed-version payload* as the base, leaving standard conflict
     markers, exactly the surface `seed template upgrade` presents
     (`docs/handbook.md:413`). It rewrites `.seed/flavor.lock` on success,
     never pushes, never opens a PR, and reports per-file what it did.
   - `status` prints the installed flavor, its recorded template version, and
     which destinations have diverged from the lock. No network, no package
     manager, in any verb: the dependency install stays a printed follow-up the
     consumer runs.

   `scripts/**` is in `protected_paths` (`.seed/guardrails.yaml`) and owned in
   `CODEOWNERS`, so this lands as a reviewed control-surface change; that is
   expected, not a problem to route around.

4. **Ship the TypeScript flavor** under `flavors/typescript/`, the one the
   design names. Payload, honouring the thin-root rule:

   - `Makefile` (destination `/Makefile`) — the core `Makefile` with `check`
     extended so it runs `validate` and then the flavor's `typecheck`, `lint`
     and `test`, failing on the first failure. The core `check: validate`
     recipe and the `validate`/`smoke` targets are preserved verbatim; only the
     placeholder `@echo "check: add your project's lint/test/typecheck here"`
     line is replaced. The recipe **delegates** (npm scripts) rather than
     inlining tool flags, so tool-flag churn lives in the flavor directory.
     Keep the header comment's "keep it fast": `make check` is the term that
     multiplies at scale (R12).
   - `tsconfig.json` (destination `/tsconfig.json`) — thin: `extends`
     `./flavors/typescript/tsconfig.base.json` plus the project's `include`.
     `tsconfig.base.json` stays in the flavor directory and carries `strict`
     and every other option, so compiler-option churn arrives via `template
     upgrade` with no reapply needed.
   - `package.json` (destination `/package.json`) — `lint`, `test`, `typecheck`
     scripts and the dependency set. This is the acknowledged thick root file:
     npm requires it at the root, so it is what `seed-flavor upgrade` exists to
     reconcile. Prefer the lowest-dependency toolchain that satisfies the three
     verbs — `tsc --noEmit` for typecheck, node's built-in `node:test` runner
     for test — so the flavor stays fast and the churn surface stays small; a
     linter is the one dependency with no built-in equivalent.
   - A minimal passing `src/` + test pair, so a freshly flavored repo is green
     out of the box (a flavor that instantiates red teaches agents to ignore
     `make check`).
   - `flavors/typescript/README.md`: what it wires, the dependency-install
     command the consumer runs after install, and the upgrade story from step 1
     — `seed template upgrade` brings new payload, `seed-flavor upgrade`
     applies it, and the two are separate steps.

5. **Keep the offline assertions in `scripts/validate.sh`.** The parts of the
   mechanism that are pure filesystem logic run in the core gate, because they
   are fast, deterministic and need neither node nor network: `seed-flavor
   list` names `typescript`; each flavor directory has a `README.md` and a
   `manifest`; every manifest destination exists as a payload file; every
   destination outside `flavors/` is one the contract allows; the three
   `install` refusal paths refuse with the right exit and message (exercised
   against fixture directories under a `mktemp -d`, never against the repo).
   This mirrors how the backend contract tests and `seed-dispatch-route` cases
   already run there. **None of these run `make check`**, so no recursion is
   possible.

6. **Ship the flavor's integration test** as `scripts/flavor-test.sh`, wired to
   a **new `make flavor-test` target, deliberately not into `check` or
   `validate.sh`** — the same separation `make smoke` already has for
   `scripts/smoke-loop.sh`, and for the same two reasons. First, recursion: the
   test instantiates the template and runs `make check` inside it, and a
   flavored `check` runs `validate`, so wiring it into `validate.sh` would
   re-enter itself without bound. Second, determinism: it needs a dependency
   install, and §2.6 binds `make check` to be fast and deterministic. It runs
   in CI, where the network exists, as its own step. Belt-and-braces, the
   script exports a re-entry guard (`SEED_FLAVOR_TEST=1`) and returns
   immediately if it is already set.

   What it proves — the card's acceptance, mechanically. Instantiate the
   template into a temp repo the way `scripts/smoke-loop.sh` does (`git archive
   HEAD | tar -x` into a `mktemp -d`, trapped for cleanup), run `scripts/seed-
   flavor install typescript`, then:

   - assert `make check` is green on the instantiated flavored repo;
   - drop the **deliberately broken fixture** (a `src/` file that fails `tsc
     --noEmit` under `strict`) and assert `make check` exits non-zero with the
     typecheck failure in its output;
   - assert the reconciliation path: mutate a payload file in the temp repo's
     `flavors/typescript/`, run `seed-flavor upgrade`, and check the
     destination picked the change up when undiverged and produced conflict
     markers when diverged.

   Skip explicitly — an `SKIP —` line naming what was missing, exit 0 — when
   `node`/`npm` are absent **or when the dependency install cannot reach a
   registry**. The first draft covered only the missing-executable case, which
   left a host with node but no registry access failing rather than skipping.
   Probe reachability and skip on that too; never let a skip read as a pass.

7. **Prove the flavor does not leak into the core**, with two invariants that
   hold on every branch (replacing the draft's merge-base diff):

   - **Core-gate independence**, in `scripts/flavor-test.sh`: instantiate the
     template unflavored, run `make check` and capture its output; delete the
     `flavors/` tree and `scripts/seed-flavor`; run `make check` again. The two
     runs must agree. This proves the core gate does not depend on the flavor
     machinery — the property §10 Q3 actually demands — and it stays meaningful
     no matter what else changes on the branch. Being unflavored, it needs no
     node, so it runs in the offline block of step 5 rather than the gated one.
   - **Install confinement**, likewise offline: snapshot the instantiated
     tree's file list and hashes before and after `seed-flavor install
     typescript`, and assert the set of changed paths is exactly the manifest's
     destination set. A flavor that writes anything it did not declare fails
     the build.

   The one-time check that shipping *this* PR changes no core file is a review
   concern, not a permanent test: the implementation PR's diff shows it, and
   `seed pr classify` plus `CODEOWNERS` already gate the protected paths it
   touches. Note it in the PR description rather than encoding it as an
   assertion that will misfire later.

8. **Document flavors for users.** Add a subsection to `docs/handbook.md` §6
   (next to the engine-upgrade and template-upgrade bullets, the surface
   flavors interact with): what a flavor is, `seed-flavor list` / `install
   <name>`, that install is a fresh-instantiation step, and — stated plainly —
   that keeping a flavor current is `seed template upgrade` followed by
   `seed-flavor upgrade`, two separate consumer-initiated steps. Add the
   `flavors/` row to the "Where everything lives" table in `docs/handbook.md`
   §7 and to the equivalent table in `AGENTS.md` **only if** the `AGENTS.md`
   table is not inside a `seed sync`-managed block — if it is, change the
   source and regenerate, never the fan-out (`seed sync --check` would
   otherwise fail).

9. **Append the durable insight** to `memory/LEARNINGS.md` (the path-based
   nature of `template upgrade`, and the thin-root rule it forces on anything
   that copies template content into a consumer's repo) and the two rejected
   mechanisms, plus the rejected "install alone is the update path" framing, to
   `memory/DEADENDS.md`, in this task's PR, per `AGENTS.md`.

  `tsconfig.json`, `tsconfig.base.json`, linter config, minimal `src/` + test)

Modified files:

- `Makefile` — **one addition only**: the `flavor-test` target and its
  `.PHONY` entry, alongside the existing `smoke` target. The `check` and
  `validate` recipes are untouched, so the core gate is unchanged; this is the
  one core-file edit the plan makes, and step 7's core-gate-independence
  invariant is what keeps it honest.
- `docs/handbook.md` — §6 flavor bullet, §7 table row. Note for sequencing:
  `os-221f5929` also adds a §6 subsection ("Two distribution channels") and a
  §7 row, so whichever task PR lands second resolves a textual conflict there.
  Neither change is semantically contested: the flavor bullet belongs under
  the template channel that section describes.
- `memory/LEARNINGS.md`, `memory/DEADENDS.md` — appends
- `AGENTS.md` — table row **only** if not `seed sync`-managed (see step 8)

Created by the install step in a *consumer's* repo, never in this one:
`.seed/flavor.lock`.

Explicitly **not** touched: `.seed/**` in this repo (including
`guardrails.yaml`, `config.toml`, the port schema, and the engine/template
locks), `.github/**` apart from the flavor-test CI step, `CLAUDE.md`,
`seed.yaml`, `seed.lock`. `scripts/**` and `Makefile` are protected control
surface and are touched deliberately: this PR requires owner review under
`CODEOWNERS`. Task PRs never touch `plans/**`.

## Acceptance Criteria

- `decisions/0002-template-flavors.md` exists, status accepted, and records:
  the adopted mechanism, both rejected alternatives with reasons, the
  thin-root/fat-flavor-dir rule, the recorded-metadata reconciliation path, and
  the explicit statement that flavor reconciliation is consumer-initiated and
  separate from `seed template upgrade`.
- `scripts/seed-flavor list` names `typescript`; `install typescript` into a
  fresh instantiation writes exactly the manifest's destinations, writes
  `.seed/flavor.lock` recording the flavor, the template version and a hash per
  written file, and exits 0.
- `install` refuses, non-zero and with a message naming the reason and the
  alternative, when `.seed/flavor.lock` exists, when the target `Makefile`
  differs from the core template's, or when a destination already exists.
- `seed-flavor upgrade` applies a changed payload to an undiverged destination
  cleanly, and produces standard conflict markers on a diverged one, using the
  installed payload as the merge base; `status` reports the installed flavor,
  its template version, and any diverged destinations.
- In a fresh instantiation with the TypeScript flavor installed and its
  dependencies present, `make check` runs the flavor's typecheck, lint and
  test, and is green.
- With the deliberately broken fixture added, `make check` exits non-zero and
  its output names the typecheck failure.
- `scripts/flavor-test.sh` prints an explicit `SKIP —` line naming what was
  missing and exits 0 when `node`/`npm` are absent **or** when the dependency
  install cannot reach a registry; it never reports a pass it did not run.
- `make check` on this repo invokes no network and no package manager: the
  flavor's integration test is reachable only through `make flavor-test`.
- Core-gate independence holds: an unflavored instantiation's `make check`
  output is identical with and without the `flavors/` tree and
  `scripts/seed-flavor` present.
- Install confinement holds: the set of paths changed by `install typescript`
  is exactly the manifest's destination set.
- `sh scripts/validate.sh` is green and `scripts/seed sync --check` reports no
  fan-out drift.
- `docs/handbook.md` documents install as a fresh-instantiation step and states
  the two-step upgrade story.
- `memory/LEARNINGS.md` and `memory/DEADENDS.md` carry this card's entries.
