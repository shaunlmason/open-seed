# Plan: v2 opinionated stack template flavors — mechanism decision + the TypeScript flavor (os-501a29c2)

Design §10 Q3 fixes the v1 core as language-agnostic: "The template's only
contract with the project's stack is `make check` (the fast backpressure
command) plus the hooks. Opinionated stack variants (e.g. a TypeScript flavor
with lint/test/typecheck pre-wired into `make check`) are v2 template flavors,
never the v1 core." This card builds that mechanism and its first flavor.

The card is explicit that the mechanism decision comes **before** any flavor,
and that the decision must state how flavors interact with the template
release/update surface (`.seed/template.lock`, `seed template upgrade`, §10 Q4)
so a flavored instantiation can still track template releases. Steps 1–2 settle
that; steps 3–6 build the TypeScript flavor against it.

## Decision to be recorded (step 1)

Three candidate mechanisms, from the card's own scope list:

1. **Template variant repos** — one repo per flavor. Rejected: each variant
   becomes a fork that must independently track upstream. `.seed/template.lock`
   carries exactly one `repo` line, so a flavored instantiation would track
   either the variant (and never see core releases) or the core (and never see
   flavor updates). That breaks the §10 Q4 update surface the card requires the
   decision to preserve, and multiplies the maintainer release checklist
   (`docs/handbook.md:428`) by the number of flavors.
2. **Engine-side `seed init --flavor`** — the flavor lives in the engine.
   Rejected: the engine is a separate Go repository shipping pinned release
   binaries (§7.5, `decisions/0001-engine-repo.md`), pinned by
   `.seed/engine.lock`, which advances on its own release train independent of
   `.seed/template.lock`. Flavor *content* there would version against the
   engine, not against the template it was installed into, so
   `seed template upgrade` could never reason about it. Engine work also
   happens in the other repo, which this card is not scoped to.
3. **Flavor directory in the core template plus an install step** — **adopted.**
   `flavors/<name>/` ships inside the core template and is applied once, into a
   fresh instantiation, by a template-side install step. One upstream repo, one
   `template.lock`: `seed template upgrade`'s three-way merge carries flavor
   updates exactly as it carries any other template content, and the files the
   install step wrote into the consumer's repo merge as ordinary local changes
   (conflicts as standard markers, per `docs/handbook.md:413`). No new release
   train, no fork, no engine dependency.

The consequence to state honestly in the ADR: a flavored instantiation's
`Makefile` is a *local modification* from `template upgrade`'s point of view.
An upstream change to the core `Makefile` and the flavor's replacement of it
will conflict, and the consumer resolves that conflict like any other. This is
the same contract the handbook already documents for locally-edited template
files; it is not a new limitation, but the flavor docs must say so rather than
implying flavored repos upgrade untouched.

## Interpreting "byte-identical"

The card's acceptance says "the unflavored template is byte-identical to today
(validate.sh green, fan-out drift check green)". Read literally, adding any
file would fail it, which would make shipping a flavor impossible under any of
the three mechanisms. The parenthetical names the checks that are meant, so
this plan reads it as: **no existing core file changes** — the `Makefile`,
`.seed/**`, `AGENTS.md`, `CLAUDE.md` and every `seed sync` fan-out output stay
byte-for-byte as they are on `main`, and `make check` on an unflavored
instantiation produces the same output it produces today. New files (the
`flavors/` tree, the install step, the ADR, docs) are additions. Step 6 proves
this mechanically rather than by assertion.

## Steps

1. **Record the mechanism decision as an ADR** at
   `decisions/0002-template-flavors.md`, following the shape of
   `decisions/0001-engine-repo.md` (title, `**Date:**`, `**Status:** accepted`,
   prose). Content: the adopted mechanism (flavor directory in the core
   template plus an install step), the two rejected alternatives with the
   reasons above, and the explicit statement of how flavors interact with the
   release/update surface — one upstream repo, one `.seed/template.lock`,
   flavor content carried by `seed template upgrade` like any other template
   content, flavor-written files in the consumer's repo merged as local
   changes, with the `Makefile` conflict named as the known cost. ADRs in that
   directory are append-only (`decisions/** merge=union` in `.gitattributes`):
   add a new file, never edit `0001`.

2. **Ship the flavor contract** as `flavors/README.md`: what a flavor is (a
   set of files applied once into a fresh instantiation, which pre-wires the
   project's real lint/test/typecheck into `make check`), what it may and may
   not touch, and the rule that keeps §10 Q3 true — **a flavor never changes
   the core template**; it only writes into the consumer's instantiation. State
   the required layout for `flavors/<name>/`: a `README.md`, a `manifest`
   listing the files the install step writes, and the payload files themselves.

3. **Ship the install step** as `scripts/seed-flavor` (POSIX `sh`, the idiom of
   `scripts/validate.sh` and `scripts/seed-dispatch-route`), with
   `seed-flavor install <name>` and `seed-flavor list`. Behaviour:

   - Refuse (non-zero, explicit message) when the target repo's `Makefile` is
     not byte-identical to the core template's shipped `Makefile`. A flavor
     install replaces the `Makefile`; running it over an already-customized or
     already-flavored repo would silently discard the consumer's work. Refusing
     and printing the manual steps is the honest behaviour (R9/"honesty over
     polish"): the install step is a fresh-instantiation scaffold, not an
     idempotent converger.
   - Refuse when any other file the manifest would write already exists.
   - On success, copy the manifest's files into place and print what it wrote
     plus the follow-up the consumer must run themselves (dependency install),
     which the script never runs: no network, no package manager, in the step
     itself.

   `scripts/**` is in `protected_paths` (`.seed/guardrails.yaml`) and owned in
   `CODEOWNERS`, so this lands as a reviewed control-surface change; that is
   expected, not a problem to route around.

4. **Ship the TypeScript flavor** under `flavors/typescript/`, the one the
   design names. Payload:

   - `Makefile` — the core `Makefile` with `check` extended so it runs
     `validate` and then the flavor's `typecheck`, `lint`, and `test` targets,
     failing on the first failure (the core `check: validate` recipe and the
     `validate`/`smoke` targets are preserved verbatim; only the placeholder
     `@echo "check: add your project's lint/test/typecheck here"` line is
     replaced). Keep the header comment's "keep it fast" instruction: `make
     check` is the term that multiplies at scale (R12).
   - `package.json` with `lint`, `test`, and `typecheck` scripts, and
     `tsconfig.json` with `strict` on. Prefer the lowest-dependency toolchain
     that satisfies the three verbs — TypeScript's own `tsc --noEmit` for
     typecheck and node's built-in `node:test` runner for test — so the flavor
     stays fast and its dependency surface stays small; a linter is the one
     dependency that has no built-in equivalent.
   - A minimal passing `src/` + test pair, so a freshly flavored repo is green
     out of the box (a flavor that instantiates red teaches agents to ignore
     `make check`).
   - `flavors/typescript/README.md`: what it wires, the dependency-install
     command the consumer runs after install, and the upgrade note from step 1
     (the `Makefile` is a local modification from `template upgrade`'s view).

5. **Ship the flavor's test** as `scripts/flavor-test.sh`, wired into
   `scripts/validate.sh` alongside the existing offline contract tests. It
   proves the card's acceptance mechanically: instantiate the template into a
   temp repo the way `scripts/smoke-loop.sh` does (`git archive HEAD | tar -x`
   into a `mktemp -d`, trapped for cleanup), run `scripts/seed-flavor install
   typescript`, then

   - assert `make check` is green on the instantiated flavored repo, and
   - drop the **deliberately broken fixture** (a `src/` file that fails
     `tsc --noEmit` under `strict`) and assert `make check` now fails, with a
     non-zero exit and the typecheck failure in its output.

   The test needs `node`/`npm` and a dependency install, which is network. Use
   the repo's established degradation idiom
   (`.seed/backends/beads/live-test.sh`, quoted in `scripts/validate.sh:84`):
   **self-skip with an explicit `SKIP —` message naming what was missing**,
   exit 0, so `make check` on a machine without node stays green and honest.
   Never let the skip masquerade as a pass. The install-refusal paths from
   step 3 are pure filesystem checks: assert those unconditionally, outside the
   node-gated section, so the mechanism keeps coverage even when the toolchain
   is absent.

6. **Prove the unflavored core is unchanged.** Add to `scripts/flavor-test.sh`
   an assertion that the core paths carry no diff against the merge-base:
   `git diff --quiet <merge-base> -- Makefile .seed AGENTS.md CLAUDE.md`. This
   is the mechanical form of the card's byte-identical criterion, and it fails
   the build the moment a future flavor leaks into the core.

7. **Document flavors for users.** Add a short subsection to `docs/handbook.md`
   §6 (next to the engine-upgrade and template-upgrade bullets, which are the
   surface flavors interact with): what a flavor is, `scripts/seed-flavor list`
   / `install <name>`, that it is a fresh-instantiation step, and the upgrade
   consequence. Add the `flavors/` row to the "Where everything lives" table in
   `docs/handbook.md` §7 and to the equivalent table in `AGENTS.md` **only if**
   the `AGENTS.md` table is not inside a `seed sync`-managed block — if it is,
   change the source and regenerate, never the fan-out (`seed sync --check`
   would otherwise fail).

8. **Append the durable insight** to `memory/LEARNINGS.md` (the mechanism
   choice and the one-`template.lock` reasoning that drove it) and the two
   rejected mechanisms to `memory/DEADENDS.md`, in this task's PR, per
   `AGENTS.md`.

## File Scope

New files:

- `decisions/0002-template-flavors.md`
- `flavors/README.md`
- `flavors/typescript/**` (README, manifest, `Makefile`, `package.json`,
  `tsconfig.json`, linter config, minimal `src/` + test)
- `scripts/seed-flavor`
- `scripts/flavor-test.sh`

Modified files:

- `scripts/validate.sh` — one block invoking `scripts/flavor-test.sh`
- `docs/handbook.md` — §6 flavor bullet, §7 table row
- `memory/LEARNINGS.md`, `memory/DEADENDS.md` — appends
- `AGENTS.md` — table row **only** if not `seed sync`-managed (see step 7)
- `CODEOWNERS` — a `/flavors/` entry if the review discussion wants flavors
  owner-reviewed; the default is that `flavors/` is *not* control surface
  (it never executes in the core repo's own gates beyond the flavor test), so
  the plan does not add one by default.

Explicitly **not** touched: the root `Makefile`, `.seed/**` (including
`guardrails.yaml`, `config.toml`, the port schema, and the engine/template
locks), `.github/**`, `CLAUDE.md`, `seed.yaml`, `seed.lock`. `scripts/**` is
protected control surface and is touched deliberately (steps 3, 5, 6): this PR
requires owner review under `CODEOWNERS`. Task PRs never touch `plans/**`.

## Acceptance Criteria

- `decisions/0002-template-flavors.md` exists, status accepted, and records:
  the adopted mechanism, both rejected alternatives with reasons, and how
  flavors interact with `.seed/template.lock` and `seed template upgrade` so a
  flavored instantiation can track template releases — including the honest
  statement that flavor-written files (notably the `Makefile`) merge as local
  changes and can conflict.
- `scripts/seed-flavor list` names `typescript`; `scripts/seed-flavor install
  typescript` into a fresh instantiation writes the flavor's files and exits 0.
- `scripts/seed-flavor install typescript` refuses, non-zero and with a message
  naming the reason, when the target `Makefile` differs from the core
  template's or when a manifest file already exists.
- In a fresh instantiation with the TypeScript flavor installed and its
  dependencies present, `make check` runs the flavor's typecheck, lint, and
  test, and is green.
- With the deliberately broken fixture added to that same repo, `make check`
  exits non-zero and its output names the typecheck failure.
- On a machine without `node`/`npm`, `scripts/flavor-test.sh` prints an
  explicit `SKIP —` line naming what was missing and exits 0; it never reports
  a pass it did not run. The install-refusal assertions still run.
- The unflavored template is unchanged: `git diff --quiet <merge-base> --
  Makefile .seed AGENTS.md CLAUDE.md` is clean (modulo step 7's `AGENTS.md`
  table row, which if taken must go through its `seed sync` source), `sh
  scripts/validate.sh` is green, and `scripts/seed sync --check` reports no
  fan-out drift.
- `docs/handbook.md` documents the flavor install as a fresh-instantiation
  step and states the `template upgrade` consequence.
- `memory/LEARNINGS.md` and `memory/DEADENDS.md` carry this card's entries.
