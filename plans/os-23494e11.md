# Plan: seed template upgrade — pull-based template updates (os-23494e11)

The other half of the R8 upgrade story. Engine pin upgrades are one
verified command (`seed upgrade`, os-4a347bd1); template updates are still
"diff against a newer tag and take what you want" — honest, but manual
enough that instantiated repos drift forever. `seed template upgrade`
mechanizes the pull: record where you came from, three-way merge what
changed upstream against what you changed locally, stage the result on a
branch, and leave the decision — the PR — to the human. The trust
direction is fixed by design (§7.1 amendment discussion, card body):
**consumer-initiated, review-gated, never a push from upstream into
downstream repos.**

## Steps

1. **`.seed/template.lock`** (new, control surface): engine.lock-style
   lines — `repo <owner/name>`, `version <tag>`, and an *optional*
   `commit <sha>` that is **stamped by the upgrade command, never
   authored at release time**: a release cannot record its own commit
   SHA (writing the SHA into the tree changes the tree, which changes
   the SHA), so the maintainer's release checklist sets `version` only,
   and the immutability of release tags — already part of the
   server-side tag protections — is what makes the recorded tag a
   reliable base. When `commit` is present (a previous
   `seed template upgrade` stamped the upstream commit it merged from —
   an *upstream* SHA, so no self-reference), it pins the base even if
   the tag later moves; otherwise the base is the recorded `version`
   tag resolved at fetch time. The template ships the lock pointing at
   its own repo; "Use this template" copies do not carry history, which
   is exactly why the base must be recorded in a file.
2. **Resolution** (engine, `internal/template`): the target is
   `--to <tag>` or the template repo's latest release, resolved exactly
   as `seed upgrade` does (no-follow redirect; URLs from the lockfile
   repo; semver enforced; the same TLS-or-loopback override rule, shared
   helpers extracted from `internal/upgrade` rather than duplicated).
3. **Fetch + three-way merge**: the engine drives **system git** (as
   everywhere): fetch the base and the target tag from the template
   repo into the local object store using the explicit tag refspec form
   (`git fetch <url> <base> tag <tag>` — a bare tag name is an
   unreliable refspec; `<base>` is the stamped commit when present,
   else `tag <version>`), then per file across the union of
   paths — base = recorded commit's tree, theirs = target tag's tree,
   ours = the working tree:
   - clean three-way result → staged;
   - conflicting → staged **with standard conflict markers** and listed
     in the envelope's `conflicts`;
   - locally deleted / upstream deleted → follow git's three-way
     semantics, surfaced in `deletions`.
   Two hard exclusions, never merged: `.seed/template.lock` itself is
   set to the new tag and stamped with its resolved upstream commit,
   and paths matching the consumer's own work products (`plans/**`,
   `receipts/**`, `memory/**`, `decisions/**`) are left untouched —
   upstream template history has no business in a consumer's work
   products. (Cards live on the state ref, which the merge never
   reaches.)
4. **Branch, not working tree; PR by the human**: results land as one
   commit on a new local branch `template-upgrade/<tag>` (created from
   the current HEAD; the working tree is left untouched). The command
   **never pushes and never opens a PR** — the envelope lists the
   branch, the merged/conflicted/deleted files, a `.seed/version` bump
   warning when the target changes it (engine upgrade required next),
   and the next steps: resolve conflicts on the branch, push, open the
   reviewed PR. `--check` reports current vs latest and the changed-path
   summary without creating anything.
5. **Exit map**: same shape as `seed upgrade` and documented in usage —
   0 ok (including "completed with conflicts staged"), 1 refusal
   (unparsable lock, target older than recorded base without `--to`,
   dirty working tree for the branch-creation step), 7 template host
   unreachable, 64 usage.
6. **Tests** (engine): fixture-based and fully offline — a local bare
   "template" repo with tagged versions stands in for the remote (the
   fetch step takes a URL; file paths are URLs to git). Cases: clean
   merge, genuine conflict (markers staged + reported), local-only file
   untouched, upstream-deleted file, work-product exclusion,
   template.lock advanced, `.seed/version`-bump warning, downgrade
   refusal, `--check` purity, dirty-tree refusal.
7. **Template + docs**: ship `.seed/template.lock`; handbook §6 rewrites
   the "Template updates" sentence into the two-command story mirroring
   the engine's; the release checklist (§6) gains the version-then-tag
   step (bump `version` in the lock, commit, tag that commit — the
   `commit` line is the upgrade command's to write, never the
   release's). Engine release + `seed upgrade`-performed pin bump (the
   ordinary path now), carried in this card's task PR.

## File Scope

- Engine repo: `internal/template/` (new), `internal/upgrade/` (shared
  resolution helpers extracted), `cmd/seed/`, `PROTOCOL` unchanged
- Template: `.seed/template.lock` (new), `.seed/engine.lock` (the new
  engine release pin, moved by `seed upgrade`), `docs/handbook.md`

## Acceptance Criteria

- A fixture upgrade with upstream and local edits produces: clean merges
  applied, conflicts staged with markers and reported, local-only and
  work-product files untouched, `template.lock` advanced (new `version`
  plus the stamped upstream `commit`) — all on a new branch with the
  working tree untouched.
- The command performs no push and opens no PR; its envelope names the
  branch and the reviewed-PR next steps; `--check` creates nothing.
- A target older than the recorded base refuses without `--to`; a
  `.seed/version` change in the target produces the engine-upgrade
  warning; an unreachable template host exits 7.
- The template ships `template.lock` and the handbook documents both the
  consumer flow and the maintainer's version-then-tag release step; the
  lock's `commit` line is only ever written by the upgrade command.

## Validation Commands

- `test -f .seed/template.lock`
- `SEED_UPGRADE_BASE_URL=http://127.0.0.1:9 scripts/seed template upgrade --check; test $? -eq 7`
- `grep -q "template upgrade" docs/handbook.md`
- `sh scripts/validate.sh`
