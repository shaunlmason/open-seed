# Plan: next — identity before every act, and a drill that enters its branch (os-eb35672a)

Two review findings on #194 (`os-378e44f3`), both verified and both
correct, arriving after that PR merged. A merged PR cannot track new
work, so they land fresh.

The fixes are small. What deserves a plan is the **second** one, because
of where it came from.

## The findings

| # | severity | defect |
|---|---|---|
| 1 | P1 | the loop's identity is checked once per iteration, so a rotation during the work step lets the settle and the exit sign as a new identity |
| 2 | P2 | the packet-unlink drill never enters the branch it is named for |

## Design decisions (binding for this task)

- **D1 — the identity check belongs in `act`, not at the top of
  `Step`.** Once per iteration is not once per act, and the gap between
  them is `Work.Do` — the longest thing in an iteration and so the
  likeliest moment for a rotation to land.

  The failure that gap allows is specific, not theoretical: a window
  opened by one actor and then settled, submitted or parked by another;
  or worse, left open because the exit refused. That is precisely the
  state the four deliberate exits exist to make impossible, so a check
  that stops short of covering the exits is checking the wrong thing.

  Cost, stated: one key read per act rather than one per iteration.
  That is a file read next to a network round-trip, and it buys the
  property the check exists for.

  Not chosen: pinning the signer for the iteration by reading the key
  once and passing material rather than a path. The CLI takes `--key
  <path>`, so pinning means copying private key material somewhere the
  Driver controls — a second copy on disk, which is a worse trade than
  a re-read.

- **D2 — a drill named for a failure path must ENTER it, and this one
  did not.** The packet-unlink drill was added in direct response to
  #193's finding that the behavior was unasserted. It ran a *successful*
  `writePacket`, checked the file existed, called the *success-path*
  cleanup, and passed — while both error-branch `remove()` calls could
  be deleted with no effect. Confirmed by deleting them.

  So the drill was named for a branch it never entered, written in
  response to a finding about exactly that. That makes it the seventh
  instance this cycle of a test agreeing with a convenient shape rather
  than the shipped one, and the most instructive, because being told
  about the class did not prevent the next member of it.

  The fix needs a **seam**: `f.Write` and `f.Close` cannot be made to
  fail against a real temp file without one. `writePacket` gains a
  package-level writer factory and an `InjectPacketWriter` helper,
  following the injection precedent `internal/transition` already sets
  (`InjectBudgetClass`, `InjectSpendingVerb`). The drill injects a
  writer that fails at `Write` and one that fails at `Close`, and
  asserts the created file is gone in each case.

  The seam is test-only in purpose and production-visible in fact,
  which is the honest trade: the alternative is a correctness claim
  nothing can check.

- **D3 — every fix is mutation-checked, and the mutation for the packet
  fix is the one that previously PASSED.** Deleting both error-branch
  unlinks must now fail the drill. That specific mutation is the
  acceptance evidence, not a general assurance that drills were run.

- **D4 — scope guard.** No new verb, no new projection, no admission
  change. The loop gains no capability: this card repairs what merged
  and adds nothing.

## Acceptance Criteria

1. The identity is re-derived and compared **before every act**, and a
   drill rotates the key from inside the work callback and asserts the
   iteration stops at the next act with no settle, submission or park
   reaching the verb seam.
2. The packet drill enters both post-creation failure branches via an
   injected failing writer and closer, and asserts the created file is
   unlinked in each.
3. **Deleting both error-branch unlinks fails that drill** — the exact
   mutation that previously passed, recorded as evidence.
4. Every other fix on this card is likewise mutation-checked, recorded
   per fix rather than claimed in aggregate.
5. `make check` green with coverage measured **cold**, at least three
   readings above the gate, and the drills pass unprivileged.

## A risk worth naming now

Coverage on this branch read 88.3% once and 91.1% otherwise. The low
reading is the known counter-loss flake (`os-cafba959`), identifiable
because the *whole package* reads implausibly low at once — `Step` at
31.8% where it measures ~97% on a good run — rather than the specific
new branches dropping.

The risk is treating that signature as licence to dismiss a real drop.
So the criterion is three cold readings above the gate, not one, and if
a reading is low the per-function breakdown decides which it is before
anything is pushed.
