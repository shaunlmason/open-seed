# Plan: handbook: add "publish a GitHub Release" to the cutting-a-template-release checklist (os-0f76f772)

The maintainer release checklist in the handbook is one step short. `seed
template upgrade` resolves its target release by following the
`/releases/latest` HTML redirect, and that redirect exists only once a
GitHub Release is **published**: a bare `git tag` does not create it. The
checklist at `docs/handbook.md:426` ("bump version, commit, tag") omits the
publish step, so a maintainer who follows it verbatim produces a tag that
consumers cannot resolve. This is a doc-only fix: add the publish step and
the reason it is load-bearing.

Discovered 2026-08-23 while closing `os-bb20001f`: with
`shaunlmason/open-seed` public and a GitHub Release `v0.1.0` published,
`/releases/latest` 302s to `tag/v0.1.0` and `seed template upgrade --check`
resolves cleanly. Before the release was published, the same endpoint 404s.

## Steps

1. **Edit the "Cutting a template release (maintainers)" bullet**
   (`docs/handbook.md:426`, §6). Insert the push-and-publish steps into the
   version-then-tag sequence, so it reads: bump `version` in
   `.seed/template.lock`, commit, tag that commit, **push the commit and the
   tag**, then **publish a GitHub Release for that tag**: e.g.
   `git push origin main && git push origin v0.1.0`, followed by
   `gh release create v0.1.0 -t v0.1.0 --verify-tag`. Keep the existing
   "version-then-tag" wording and the existing "do not write a `commit` line"
   rationale intact.

   The push and `--verify-tag` are load-bearing, not polish: when the tag
   exists only locally, `gh release create` silently creates one "from the
   latest state of the default branch", so a maintainer following the
   checklist verbatim can publish a Release anchored to a *different* commit
   than the version bump, and release tags are immutable under the §1
   protections, so that mistake cannot be corrected in place. `--verify-tag`
   makes the command fail instead of synthesising the wrong tag.

2. **State why the publish step is load-bearing.** Consumers resolve the
   release through the `/releases/latest` redirect, which GitHub serves only
   for a published Release, not for a bare tag. So the published Release, not the tag alone, is what `seed template upgrade` and any
   `/releases/latest`-based resolution follow. The new sentence should make
   this the stated reason the checklist is not complete without the publish
   step, and should cross-reference the §1 tag-protection note that already
   extends seed-anchor-style protections to release tags (line 430).

## Acceptance Criteria

- The "Cutting a template release (maintainers)" bullet names the push and
  publish-a-GitHub-Release steps as part of the release-cutting sequence

  `gh release create … --verify-tag` example.
- The bullet says why the tag must be pushed first and why `--verify-tag` is
  used: otherwise `gh release create` invents the tag from the default

- The bullet explains that the published Release, not the bare tag, is what
  `/releases/latest` (and therefore `seed template upgrade`) resolves, and
  cross-references the §1 release-tag protection note.
- The pre-existing "do not write a `commit` line" rationale and the
  version-then-tag ordering are preserved verbatim (or faithfully rephrased
  without loss).
- No other content in `docs/handbook.md` is altered.
