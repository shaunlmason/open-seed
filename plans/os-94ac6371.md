# Plan: fastcards backend — SQLite builtin (os-94ac6371)

A second builtin engine backend for single-machine throughput: the R4 write
ceiling exists because every filecards verb is a fetch→commit→push on one
shared ref. For a solo dev hammering the loop locally, that is pure
overhead. fastcards keeps coordination state in a local SQLite database with
transactional atomicity — same verbs, same evaluator, same card format —
trading state portability for speed, and saying so.

## Steps

1. **Store abstraction** (engine): extract the storage contract the task
   layer already uses (`Sync`, `ReadFile`, `ListDir`, `Halted`, `Mutate`
   with one-atomic-unit-per-verb semantics) into an interface implemented
   by the existing git state ref and by a new SQLite store. The SQLite
   store keeps the **same path-keyed layout** (`tasks/<id>.md` blobs,
   `run-log.jsonl` appends, `handoff/…`) so card parsing, effects, lint,
   and report code are reused unchanged; "head" is a monotonic transaction
   id. Pure-Go driver (`modernc.org/sqlite`, no CGO — the cross-compile
   matrix must not regress).
2. **Atomicity**: each verb runs in one `BEGIN IMMEDIATE` transaction —
   real atomic claims (the contention loser exits 2 without any push-wins
   emulation); leases and fencing behave identically to filecards.
3. **Wiring**: manifest `entry = "builtin"` with `name = "fastcards"`; the
   engine selects the builtin store by backend name. DB lives at
   `.git/seed-fastcards.db` (inside .git — never committed, no gitignore
   entry needed). `seed init` creates the schema.
4. **Declared variances** (backend README + capability manifest):
   `offline = "native"`, `atomic_claim = "native"`, but **state is
   machine-local** — it does not travel with clones, forks, or CI; the
   state-ref integrity story (anchors, HALT-by-lint, push-access trust) is
   replaced by local-filesystem trust; maintenance workflows that fetch
   the state ref see nothing (documented: fastcards is for local solo
   loops, not for repos where CI closes cards).
5. **Tests** (engine): the existing task-layer integration suite runs
   against both stores via the interface (claim contention, fencing,
   reap, cascade, lint where applicable); a throughput smoke asserts N
   sequential verbs complete without network; filecards suite unchanged.
6. **Handbook §6**: position fastcards on the ladder — below beads, for
   one machine; switching is a config line, and migrating cards out goes
   through the port like any backend swap.

## File Scope

- Engine repo: `internal/stateref/` (interface extraction),
  `internal/fastcards/` (new), `internal/task/`, `cmd/seed/`, `go.mod`
- Template: `.seed/backends/fastcards/backend.toml`,
  `.seed/backends.lock.json`, `docs/handbook.md`

## Acceptance Criteria

- The full task-layer suite passes against both stores; filecards
  behavior is byte-identical to before the interface extraction.
- Concurrent claims on the SQLite store produce exactly one winner via
  transactions (no retry loop needed).
- Cross-compilation stays CGO-free for all six targets.
- The machine-local variance is declared in manifest + README + handbook.

## Validation Commands

- `test -f .seed/backends/fastcards/backend.toml`
- `scripts/seed backend verify fastcards`
- `sh scripts/validate.sh`
