# Plan: skills manifest + lockfile + compose (os-6f3104db, D8)

Shared skills across instantiated repos (design D8 §147, §116): a
manifest (`seed.yaml`) names skill sources, a lockfile (`seed.lock`)
pins them (commit SHA + content sha256, skillfold semantics), and
`seed skills install --frozen` in CI makes the pins load-bearing —
the supply-chain rule §116 reserves for "once the manifest exists".
Compose (skillfold's, inspirations/05): a composed skill is a
*generated* skill built from an ordered `use:` list of other skills —
validated for existence, self-use, and cycles — installed alongside
the fetched ones under one managed directory; the existing
`seed sync` fan-out carries them all to every harness. Skill updates arrive as ordinary PRs whose diff shows the new
skill content — injection review happens in the review pane, never at
install time. Both files are control surface (§113 names them).

## Steps

1. **Manifest** (`seed.yaml`, template root): `schema_version`,
   `skills:` — a list of sources `{name, repo (owner/name or URL),
   ref (tag/branch), path (subdir of skills in that repo)}` — and
   `compose:` — generated skills `{name, description, use (ordered
   list of skill/compose names)}`. Ships with empty lists and a
   commented example; parsing is strict (unknown keys refused).
   Compose validation at parse time: every `use` entry must name an
   existing skill or compose entry, self-use is refused, and cycles
   are refused (DFS; compose-of-compose composes in topological
   order).
2. **Lockfile** (`seed.lock`): one entry per fetched skill — the full
   source coordinates `{name, repo, ref, path}` plus the resolution
   `{commit (40-hex, resolved from ref), sha256 (of the installed
   skill tree, file-order-independent)}` — so a lock entry alone
   reproduces the fetch and `--frozen` can detect any manifest edit
   (repo, ref, or path). Written only by the engine; hand edits fail
   verification. Composed skills are not locked: they are
   deterministic functions of locked inputs, regenerated at install.
3. **Engine `internal/skills`** + `seed skills <verb>`:
   - `lock`: fetch each source with system git (tag/branch → commit),
     hash the skill tree, rewrite `seed.lock` atomically. Network
     failures exit 7; a ref the source repo lacks is a refusal.
   - `install [--frozen]`: materialize each locked skill into
     `skills/managed/<name>/` — clone/fetch pinned commit, copy the
     subtree, verify the tree sha256 against the lock (mismatch =
     refusal, exit 1). `--frozen` additionally refuses when
     `seed.yaml` and `seed.lock` disagree (an unlocked manifest edit)
     or when any managed skill on disk drifts from its pin.
     **Managed-directory-only pruning**: install removes only
     `skills/managed/<name>` entries absent from the lock — local
     skills outside `skills/managed/` are never touched.
   - `install` then generates each `compose:` entry into
     `skills/managed/<name>/`: a `SKILL.md` whose body concatenates
     the used skills' bodies in declared order (each part's headings
     demoted under a root heading; fenced code blocks untouched),
     with the used skills' supporting files carried over so relative
     paths keep working. Removing a skill still referenced by a
     compose entry is a refusal.
   - `seed sync` picks managed skills up exactly like local ones
     (N fetched sources + generated compositions, one fan-out).
4. **CI**: check-validate gains a `skills install --frozen` step (the
   §116 rule) — drift or an unlocked edit fails the build. Offline
   safety: with an empty manifest the step is a no-op, so fresh
   instantiations stay green with zero configuration.
5. **Guardrails/docs**: `seed.yaml`/`seed.lock` are already named in
   the §113 control surface — the guardrails validator's list is
   checked to match; handbook §3 gains "Sharing skills between repos"
   (manifest → lock → install → review-the-diff), including the
   compose story and the injection-review posture.
6. **Tests** (engine, offline): local fixture repos as skill sources —
   lock resolution, tree-hash stability across file order, install
   round-trip, sha256-mismatch refusal, `--frozen` refusing unlocked
   manifest edits AND on-disk drift, managed-only pruning (a local
   skill survives; a removed lock entry's directory goes), empty
   manifest no-op; compose: ordered concatenation with heading
   demotion, supporting files carried over, unknown `use` refused,
   self-use refused, cycle refused (a→b→a), compose-of-compose in
   topological order, removal-while-used refused. Engine release + `seed upgrade` pin bump in the
   task PR.

## File Scope

- Engine repo: `internal/skills/` (new), `cmd/seed/`
- Template: `seed.yaml` (new), `seed.lock` (new),
  `.github/workflows/check-validate.yml` (the --frozen step),
  `docs/handbook.md`, `.seed/engine.lock` (release pin, moved by
  `seed upgrade`)

## Acceptance Criteria

- `seed skills lock` pins full source coordinates (repo, ref, path)
  plus commit + tree sha256 per skill; `install` refuses a hash
  mismatch; `--frozen` refuses unlocked manifest edits and on-disk
  drift; pruning never leaves the managed directory.
- Skills from two fixture repos install side by side; a `compose:`
  entry generates a skill from its ordered inputs (cycle and
  missing-input refusals covered); all of it flows through
  `seed sync` to the fan-outs.
- An empty manifest keeps every existing check green with no
  configuration.
- CI runs the `--frozen` check; the handbook documents the flow and
  the injection-review posture.

## Validation Commands

- `test -f seed.yaml`
- `sh scripts/seed skills install --frozen`
- `grep -q "skills install --frozen" .github/workflows/check-validate.yml`
- `sh scripts/validate.sh`
