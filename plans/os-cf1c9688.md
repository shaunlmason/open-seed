# Plan: next — the six lane fragments, and the obligations that make them checkable (os-cf1c9688)

Phase 9 item 1, first of three cards (1b: dispatcher least-capability
and the injection corpus; 1c: the worker loop made executable with
exhaustion parking). This card delivers what III.J's first row asks
for and nothing else:

> Role definitions exist for all six lanes as grants + conventions,
> **composable from ordered fragments, resolved and checked by
> validation**.

Plus the four obligations `docs/next-build-plan.md` item 1 binds onto
every fragment (added by os-68ea0b2d, #180).

## The failure mode this exists to prevent

A role file is prose, and prose is where conformance goes to die. v1
already has four of them under `.seed/agents/`, and nothing checks
that what they tell an agent to run exists, or that the verbs they
name are the ones the boundary accepts. That is survivable in v1,
where a human reads the file. It is not survivable for Seed, whose
promotion criterion 1 is *"a lane runs … entirely through Seed verbs,
orienting from one position-stamped read"* — a property of the LANE,
asserted by whoever wrote the file, checked by nobody.

So the deliverable is not six documents. It is six documents **whose
claims are decidable**, each claim checked against a table that
already exists rather than against a new authority. Every check below
either passes today's tables or fails; none of them introduces a new
source of truth.

## Design decisions (binding for this task)

- **D1 — a lane is a manifest plus an ORDERED fragment list; the
  fragments are the prose.** `next/lanes/<lane>.yaml` declares the
  lane's grants, its four obligations, and `fragments: [...]` — an
  explicit ordered list of files under `next/lanes/fragments/`.
  Resolution is concatenation in that order, and `seed lane show
  <name>` prints the resolved text. Ordering is declared, never
  inferred from filenames or directory order: III.J says *ordered*
  fragments, and a resolution whose order comes from a filesystem
  listing is a resolution that changes when someone renames a file.

  Composability is the point of the split: the one-inbox doctrine,
  the escalation shape and the deliberate-exit rule are written ONCE
  and included by all six lanes, so a change to a shared convention
  cannot drift between them. A convention that appears in six files
  is a convention with six versions.

- **D2 — the four obligations are DECLARED FIELDS, not paragraphs.**
  Each manifest carries:

  | field | obligation |
  | --- | --- |
  | `orients_from` | the single position-stamped read on wake |
  | `acts_through` | the loop verbs the lane uses |
  | `liveness_from` | which of the lane's OWN steps emit observations |
  | `inbox` | the one-inbox declaration |

  Prose can restate them; validation reads the fields. An obligation
  a validator cannot find is an obligation the next fragment omits.

- **D3 — every field is checked against an existing table, and this
  is the whole design.** No check below consults a list this card
  invents:

  | check | authority consulted |
  | --- | --- |
  | `grants` name real capabilities | `internal/keyring`'s capability constants |
  | every capability a lane's verbs accept is granted to it | `keyring.AcceptedCapabilities` per verb |
  | `acts_through` names real loop verbs | `cmd/seed`'s loop-verb table (`next/spec/loop-verbs.md`'s seven acts) |
  | `orients_from` names a real read surface with real flags | the `situation` flag set |
  | no fragment file is missing or orphaned | the filesystem, against the manifests |
  | resolution is deterministic | resolving twice, byte-compared |

  The middle row is the one that earns the card. A lane that declares
  `budget settle` and is granted only `observer` is a lane whose loop
  refuses on its first spend, and `keyring.AcceptedCapabilities` already
  knows it. That is Phase 8's principle — one rule set, two consumers —
  applied to role definitions.

- **D4 — the forbidden heartbeat is checked as a PROPERTY, not a
  spelling.** The build plan forbids "a verb whose only purpose is to
  report liveness", and a check for the string `obs emit` would be a
  spelling rule that the next synonym walks past. The decidable form:
  every step named in `liveness_from` must also appear in
  `acts_through`, so an observation is only ever emitted BY a step
  that does work. A lane that wants a heartbeat has to declare a
  work verb it does not perform, and the capability check above then
  asks it for the grant.

  This is why `liveness_from` names steps rather than verbs: the
  obligation is that liveness rides the work, and a field that named
  verbs directly could satisfy itself.

- **D5 — the dispatcher's least-capability posture is ASSERTED here
  and drilled in 1b.** The manifest for the dispatcher declares its
  grants like every other lane, and validation checks the ordering
  property III.J states: the dispatcher's grant set is a proper
  subset of every other lane's, or more precisely holds no capability
  that authors, verdicts, or seals. The hostile-corpus suite that
  proves its INPUT HANDLING is 1b's; this card only makes the
  standing claim checkable.

- **D6 — the six lanes are the charter's six, named as the charter
  names them** (§11): dispatcher, planner, implementer, verifier,
  curator, maintenance. Not the seven capability rows: a lane is a
  role, a capability is a grant, and the mapping between them is
  exactly what the manifests record. `curator` holds no ledger-writing
  grant at all in v0 (§12: it proposes everything and approves
  nothing), which the manifest states rather than leaves to be
  noticed.

- **D7 — v1 is untouched.** `.seed/agents/`, `scripts/validate.sh` and
  the v1 role fan-out do not change. Seed's lanes live under
  `next/lanes/`, and their validation is a Go drill plus a `seed lane`
  read verb in `next/cmd/seed`, exactly like every other Seed surface.
  The two role systems coexist because the two systems coexist; the
  build plan's §0 integration points do not include this one.

- **D8 — scope guard.** No lane becomes EXECUTABLE here: no loop
  runs, no agent is spawned, no exhaustion parking is wired (1c). No
  hostile corpus (1b). No new ledger verb, no new projection, no
  admission change, and nothing under `next/internal/` outside the
  new package and its drills.

## Steps

1. `next/lanes/` — six manifests and the fragment set: the shared
   fragments (the one-inbox doctrine, the orienting read, the
   deliberate-exit rule, escalation) and the lane-specific ones.
   Fragment prose states the conventions; the manifest states the
   four declarations and the grants.
2. `next/internal/lane` — the manifest type, the resolver (ordered
   concatenation), and `Validate`, which runs every D3 check and
   returns findings naming the manifest, the field and the authority
   that refused. No policy of its own: the capability questions go to
   `internal/keyring`, the verb questions to the loop-verb table.
3. `next/cmd/seed/lane.go` — `seed lane list`, `seed lane show
   <name>`, `seed lane validate`, in the envelope, read-only,
   journaling nothing (reads are not admission attempts).
4. Drills (`next/internal/lane`, `next/cmd/seed`): resolution is
   ordered and byte-stable; a missing fragment, an orphaned fragment,
   an unknown capability, a verb the lane's grants do not accept, a
   `liveness_from` step absent from `acts_through`, and a dispatcher
   granted an authoring capability each fail with their own finding;
   the six shipped manifests validate clean.
5. `next/spec/lanes.md` — the surface: what a lane is, what a fragment
   is, the four declarations and why each is a field rather than
   prose, and the conformance mapping to III.J's first and second
   rows.
6. `next/docs/progress.md`, `next/docs/decisions.md`, memory; receipt;
   evidence; review.

## Acceptance Criteria

1. Six manifests exist under `next/lanes/`, one per charter §11 lane,
   each declaring grants and all four obligation fields, each
   composed from an explicitly ordered fragment list.
2. `seed lane show <name>` resolves fragments in declared order and is
   byte-identical across runs; `seed lane list` names the six.
3. `seed lane validate` is green on the shipped set, and each of the
   six failure shapes in step 4 produces a distinct finding naming the
   manifest, the field, and what refused it.
4. Every capability check consults `internal/keyring`; every verb
   check consults the loop-verb table. A grep of the new package finds
   no hand-written list of capability names or verb names outside the
   manifests themselves.
5. A lane whose `acts_through` names a verb its `grants` do not
   satisfy fails validation, named by verb and by the capabilities
   that verb accepts.
6. A `liveness_from` step absent from `acts_through` fails: liveness
   rides the work, checked as a property rather than as a spelling.
7. The dispatcher holds no authoring, verdict or sealing capability,
   and validation says so by name if it ever does.
8. No file outside `next/**` changes except `receipts/` and `memory/`;
   `.seed/agents/` and `scripts/validate.sh` are untouched.
9. `make check` green, coverage gate ≥90% held.

## Open questions deliberately settled here

- **Why not reuse `.seed/agents/`?** Because Seed work never modifies
  v1 surfaces except the integration points the build plan names, and
  this is not one of them. The two systems coexist until promotion,
  and a shared role directory would make the v1 fan-out and Seed's
  validator fight over one file format.
- **Why manifests in YAML and fragments in Markdown?** The
  declarations are data a validator reads; the conventions are prose
  an agent reads. Putting the declarations in frontmatter would work
  and is how v1 does it, but it makes a fragment both a document and
  a record, and the ordered-composition rule then has to say which
  fragment's frontmatter wins. Separating them means a fragment is
  only ever prose and the merge question never arises.
- **Why no `seed lane resolve --write`?** A resolved role is not a
  projection: it derives from checked-in files rather than from the
  ledger, so it has no position to stamp and no rebuild semantics. It
  is computed on demand and printed. Writing it would create a second
  copy that can go stale, which is the exact failure the ordered
  fragment list exists to prevent.
