## Design: enforcement in three layers

A static lint cannot decide "this call writes under a projection root"
in general, and file modes alone cannot stop replacement: on POSIX,
rename-over and unlink-plus-recreate need only **parent-directory**
permission, so read-only files with writable directories leave the
boundary open to any code that obtains a published path through the
legitimate read seam (`project.Current` returns build paths by design —
views exist to be found and read) and renames a fresh file over a view
(review finding on #107). The boundary therefore closes with two source
lints plus mechanical prevention of replacement itself:

1. **Lint A: the vocabulary rule.** No non-test Go file under `next/`
   outside `next/internal/project/**` may contain the publication
   vocabulary literals (exactly `"CURRENT"`, `"projection.json"`,
   `"builds"`): nobody constructs projection paths by hand. Test files
   stay exempt (drills read the layout to assert it; reading is not a
   violation).
2. **Lint B: seam/write separation.** A non-test Go file outside the
   engine that imports `next/internal/project` must contain **no
   filesystem-write calls** (the `os` write family: `WriteFile`,
   `Create`, `OpenFile`, `Rename`, `Remove`/`RemoveAll`, `Mkdir`/
   `MkdirAll`, `Chmod`, `Truncate`, `Link`/`Symlink`), so the file
   that can obtain a published path is a file that cannot write one.
   This passes the tree today: in `cmd/seed`, the one importer
   (`project.go`) performs no writes and the writers import no
   projection seam. Both lints live in one `go/parser` test in
   `next/internal/project` — a test in the suite is wired into
   `check-next` by construction — and both are self-checked against
   synthetic fixtures (a planted violation must be flagged, a clean
   file must not), so a lint that fails to fire is itself a test
   failure.
3. **Read-only publication, directories included.** Published build
   trees lock **files at `0444` and directories at `0555`**, and the
   projection root (`<name>/`, holding `CURRENT` and `builds/`) locks
   at `0555` between rebuilds. Rename-over, unlink-plus-recreate, and
   new-entry creation inside the published tree then fail at the
   operating system for every non-engine code path, however the path
   was obtained — replacement is prevented, not merely undetected.
   The engine unlocks (`chmod +w`) exactly the directories it must
   touch for its own swap/prune window and relocks afterwards; a
   crash inside the window leaves at worst writable directories and
   an orphan partial — never a broken view — and the next rebuild
   relocks everything.

**The deletion story moves into the engine.** With directories
read-only, a bare `rm -rf` needs a mode walk first, so the sanctioned
one-command recovery is what it always was: `seed project rebuild`,
whose engine handles pre-existing locked trees itself (unlock, prune,
relock). Rebuildability is unharmed — the drill deletes via the
documented mode walk and rebuilds byte-identically — and the spec says
plainly why easy in-place mutation lost to mechanical prevention.

**Residual risk, named.** The lints bind single files; deliberately
splitting seam access and writes across files, or writing through
`syscall` directly, evades them — and an owner can always `chmod`.
The modes stop the former; nothing stops a root-privileged actor, and
the spec says so: the boundary enforces seed's own code-path
discipline (III.D's claim), while authority safety continues to rest
on non-authoritativeness, stamps, and rebuildability, not on file
modes as a security boundary.

## Steps

1. **Publication modes.** In `next/internal/project`: lock published
   trees (files `0444`, directories `0555`, the projection root
   included); unlock/relock around the engine's own swap, prune,
   same-id discard, and partial-cleanup paths; verify repeat rebuilds
   and interruption recovery over locked trees.
2. **The lint test.** `boundary_lint_test.go` in
   `next/internal/project`: walk `next/`, parse non-test files with
   `go/parser`; enforce Lint A (vocabulary literals) and Lint B
   (importers of the engine make no `os` write-family calls), each
   reporting file:line; self-check both detectors against synthetic
   violating and clean fixtures parsed from memory.
3. **Boundary drills.** After a rebuild, from outside the engine:
   renaming a prepared file over a view file fails; deleting a view
   file fails; creating a new file inside a build tree fails;
   renaming over `CURRENT` fails — and in every case the published
   bytes and the resolved view are unchanged. The engine's own
   repeat-rebuild, same-id discard, prune, and interrupted-publication
   drills stay green over locked trees; the deletion drill removes
   the output via the documented mode walk and the next rebuild
   reproduces it byte-identically with modes relocked.
4. **Spec.** Extend `next/spec/projections.md` with a "Write boundary"
   section: the three layers, both lints' exact rules and exemptions,
   the locked-tree modes and the engine's unlock window, the deletion
   story (rebuild is the recovery command), the named residual risks,
   and the conformance-mapping update marking III.D's lint row
   implemented as code-path discipline.

## Acceptance Criteria

**Boundary set (new, shown working):**

- Lint A refuses publication-vocabulary literals and Lint B refuses
  write-calls in engine-importing files, in non-test code outside the
  engine — each with a self-check proving the detector fires on a
  planted violation and stays quiet on clean source, and both passing
  over the real tree.
- Published trees carry `0444` files and `0555` directories including
  the projection root; from outside the engine, rename-over,
  deletion, in-tree creation, and `CURRENT` replacement all fail
  without changing published bytes or the resolved view.
- The engine's existing drills (repeat rebuild, same-id discard,
  interrupted publication, prune) pass unchanged over locked trees,
  relocking after every window.
- Deleting the output through the documented mode walk followed by one
  rebuild reproduces the tree byte-identically with modes relocked —
  rebuild remains the one-command recovery.

**Retention set (existing, shown unharmed):**

- All existing verb suites pass unchanged
  (`cd next && go test ./internal/... ./cmd/... -count=1`).
- The repo-wide gate stays green with the ≥90% coverage gate
  (`make check`), which is what "lint wired into `check-next`" means
  here: the lint is a test in the suite `check-next` already runs.
