# Plan: next — `ledger show --position <missing>` must stamp the position it established (os-fa69345e)

Review finding on #168. `runLedgerShow` with `--position` opens the
ledger read-only, scans it to completion, and then returns `not_found`
from the `found == nil` branch **without setting `Position`** —
although the scan visited every record and therefore established the
count.

## Why this is a defect rather than a stylistic gap

[`next/spec/envelope.md`](../next/spec/envelope.md) states the rule:
"Every response that reached the ledger stamps it; a refusal raised
**before a tip was ever read** (a malformed invocation, an unreadable
ledger directory) carries `null` rather than inventing a position,
because a fabricated stamp would break exactly the detection this
field exists for."

This refusal reached the ledger. It read every record there is. The
missing stamp is not a fabricated position withheld; it is a known
position discarded.

And the cost is exactly what the field exists for. A caller asking for
position N on a chain of length N has asked for a record that may
appear at any moment. With the stamp they learn the chain is at N-1
and can re-ask; without it, `not_found` is indistinguishable from
`not_found` on a chain of length 10,000 where the position never will
exist. The one refusal where concurrency is most likely is the one
that withholds the means to detect it.

## Design decisions (binding for this task)

- **D1 — count during the scan already running, never a second pass.**
  The callback is invoked once per record with its position; tracking
  the highest position seen costs one assignment and no extra I/O.
  `show` is the read surface that "never writes" and must stay cheap;
  a second `store.Tip()` call to recover a number the scan already had
  would be the wrong fix.
- **D2 — stamp through `stampTip`, not by hand.** The helper takes a
  count and stamps `count-1`, and it already declines to stamp when the
  count is zero. That gives the empty-chain case the right answer for
  free: an empty ledger establishes no position, so the refusal
  correctly stays `null`, and no branch has to say so.
- **D3 — the `chain_invalid` branch is untouched.** A scan that failed
  partway established nothing trustworthy: the count it reached is a
  count of records read before an error, not a statement about the
  chain. Stamping it would assert a position the failure disproves.
  That branch keeps `null`, and the drill pins it so a future
  "consistency" cleanup does not extend the stamp there.
- **D4 — no spec change.** The rule already covers this; the code
  disagreed with it. Restating the rule would imply it was ambiguous.
- **D5 — no envelope, exit-code or journal change.** Still exit 4,
  still `not_found`, still the same message. `show` is a read surface
  and journals nothing, before and after.

## Steps

1. `next/cmd/seed/ledger.go`: track the scanned count inside the
   existing `store.Records` callback and return the `found == nil`
   refusal through `stampTip(..., count)`.
2. Drills in `next/cmd/seed/ledger_test.go`: a `not_found` on a
   non-empty chain carries the tip ordinal; the same refusal on an
   empty chain carries `null`; a successful `show --position` still
   carries the requested position (unchanged); and the `chain_invalid`
   branch still carries `null`.
3. `next/docs/decisions.md` and memory if the fix teaches anything
   durable; receipt; evidence; review.

## Acceptance Criteria

1. `ledger show --ledger <dir> --position <missing>` on a non-empty
   chain returns exit 4 / `not_found` with `position` set to the tip
   ordinal (`count-1`), the message unchanged.
2. The same invocation against an empty chain carries `position: null`.
3. A successful `show --position` is byte-identical to today's
   response.
4. A `chain_invalid` scan failure still carries `position: null`, and a
   drill pins it.
5. No second scan and no second `Tip()` call: the count comes from the
   iteration already running.
6. `make check` green, coverage gate ≥90% held.
