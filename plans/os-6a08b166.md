# Plan: next — small-team and fleet end-to-end fixtures (os-6a08b166)

Phase 9 item 4 of `docs/next-build-plan.md`, and the **last item in the
phase**. It pays the charter's III.J closing row:

> *"Small-team mode (one **principal** operating a minimal set of actor
> identities — at least an implementing actor and a distinct verifying
> actor, so verdict key disjointness holds even when one person runs
> everything) and fleet mode (disjoint actors per lane) both run the
> full loop in CI."*

The three convergence arms the build plan requires are all buildable
now, which is why this item comes last: the loop verbs landed in item
5c, the middle arm is already implemented in `internal/loop` (the
`!s.Holds(subject)` branch, whose comment names it as the build plan's
middle arm), and the third landed in item 2, where `claim.parked`
carries the boundary's `code` and `message` verbatim in the packet's
findings.

## What already exists, measured against the tree

- **`cmd/seed/loop_e2e_test.go`'s `remoteWorkLedger`** is the working
  shape: a bare remote, a signed genesis, enrolled keys, an intent, a
  specified contract, and a live offer. It builds ONE worker. This card
  generalizes it rather than writing a second one.
- **`internal/loop` is structurally wakeless.** Its `Verbs` interface is
  the single method `Run(args ...string) Result`, and `New`'s options
  are `WithSince`, `WithRepo`, `WithBase`, `WithObservations`. There is
  no wake seam to disable, so "no wake channel at all" is a property to
  **pin**, not a switch to turn off (D5).
- **`Step` never retries.** One iteration attempts each act exactly
  once; every refusal ends it as `Idle`, `Parked` or `Submitted`. So
  "converges within one retry" is a property of **consecutive
  iterations**, and the drill has to be written across them (D4).
- **The lane manifests carry `grants`** (not `capabilities`):
  implementer and planner `claim`, dispatcher `dispatch`, verifier
  `verdict`, maintenance `maintenance,operator`, curator **none**.
  That table is the fleet's identity plan, already checked in (D2).
- **Verdict disjointness is an admission rule**, not a convention:
  `admit.go`'s `verdict` rule refuses `s.PriorClaimants[actor]` with
  `NotIndependentError{Role: "a claimant, past or present"}` and refuses
  `actor == s.Submission.Signer` with `Role: "the bound submission's
  signer"`. So disjointness can be **proven by a refusal** rather than
  asserted by a `!=` between two key paths (D7).

## Design decisions (binding for this task)

- **D1 — the fixtures live in `next/cmd/seed`, and `next/fixtures/`
  stays unused.** Build plan §0's layout names `next/fixtures/` for
  drill fixtures; no card has ever created it, and the three packages
  that needed fixture data (`internal/classify`, `internal/ledger`,
  `internal/admit`) each used Go's own `testdata/` convention instead.

  The decisive reason is not convention but reach: these fixtures must
  drive the **real CLI**, and `cmd/seed` is the only package where the
  CLI seam is reachable through `runEnv`. #202 established the lesson at
  a smaller scale — a drill against a double proves nothing about the
  boundary, and the drill that finally crossed the seam found a real
  defect. An end-to-end fixture that did not cross it would be the same
  mistake at the scale where it matters most.

  So: `cmd/seed/modes_e2e_test.go`. The plan records that §0's slot
  remains unused and why, rather than creating a tree nothing else uses
  in order to look conformant.

- **D2 — one builder, two identity plans: the MODE IS DATA.** Small-team
  and fleet are two configurations of one fixture function, not two
  hand-written drills. Two drills that mean to be the same run drift,
  and a difference that drifts in is invisible.

  The builder takes an identity plan — a list of (lane, actor name) —
  and reads `next/lanes/<lane>.json`'s `grants` to decide which
  `actor.granted` events that key receives. It never carries its own
  capability table. That is what the card asks for, and it has teeth: a
  manifest that stops describing its lane fails **here**, because the
  key it provisions stops being able to act.

  Answers open question 2: yes, shared; yes, it reads `next/lanes/`.

  The curator's empty `grants` is not a gap to paper over — it is a case
  the fleet plan must carry, and the drill asserts the curator key is
  provisioned, reads, and **cannot write**. A fixture that quietly
  skipped the one lane with no grants would be hiding the case most
  likely to be wrong.

- **D3 — setup may use the raw seam; every ASSERTED property must be
  produced by an ADMITTED act.** This is the plan's sharpest rule, and
  it is easy to violate without noticing.

  `ledger append` does **not** run admission. Verified: `admit.Check` is
  called from `cmd/seed/loop.go` (the loop verbs), `offer.go`, `seal.go`,
  `verdict.go`, and `remote.go`'s shared `pushDraft`. `ledger.go` calls
  it nowhere — it is the raw dev seam, and `remoteWorkLedger` already
  uses it for enrolment, grants, intents and contracts, which is honest
  **setup**.

  The trap is staging a fact the drill then claims to have proven. A
  `verdict.rendered` written with `ledger append` is signed and folded
  and looks exactly like an admitted one — and proves nothing about the
  verdict rule, because no rule ran. So: background facts ride the raw
  seam, and every property in the acceptance criteria rides a path that
  calls `admit.Check`.

- **D4 — convergence is asserted from a TRANSCRIPT, across iterations.**
  Because `Step` never retries, "within one retry" means: the refusal in
  iteration *N* is answered in iteration *N+1*.

  A recording wrapper around `loop.Verbs` logs, per attempt, the act
  name, the `position` the envelope was stamped at, and the refusal
  `code`. It wraps the **real** `loopVerbs{}` and only observes — the
  `rotatingVerbs` shape from #202, which is the one way to instrument a
  loop without replacing the boundary it is being tested against.

  Three assertions over the transcript:
  1. every refusal is answered on the next iteration by one of the three
     arms — an admitting act, a refreshed read showing the act is no
     longer owed (`Idle` at step `orient`), or a park whose packet
     carries the refusal;
  2. **the blind-retry detector**: no (subject, act, code) refusal
     repeats on consecutive iterations from a position that did not
     advance. Same act, same knowledge, same answer is a spin, and it is
     the fourth outcome named as forbidden;
  3. every refusal that closed a window appears **verbatim** in that
     window's packet findings, read back from the ledger rather than
     from the loop's report of itself.

  Answers open question 3. The detector is the part that matters: the
  first two assertions describe good behavior and would pass on a loop
  that never met a refusal at all, which is exactly the failure D5 is
  about.

- **D5 — anti-vacuity: each arm must be EXERCISED, and an unexercised
  arm fails the drill.** The most likely way this card ships something
  worthless is a fixture where no refusal ever happens: every
  convergence assertion then passes vacuously, the drill is green, and
  it is testing nothing.

  So each arm is planted deliberately — the admitting arm by a rival
  release, the middle arm by a concurrent reap between a claim's push
  and the lane's next read, the third by an exhausted budget — and the
  transcript must show **all three**. The drill fails if any arm went
  unexercised. This is the criterion that makes the other three mean
  something.

  Wakelessness is pinned the same way, since it is an absence: the
  fixtures wire no wake channel of any kind, and a surface pin asserts
  `loop.Verbs` has exactly one method and `loop`'s exported option set
  is exactly the four that exist — the `TestExitVerbsMatchTheTable`
  shape. Adding a wake seam then fails a test that names the doctrine,
  rather than passing unnoticed. Answers "the one-inbox doctrine
  asserted rather than asserted about".

- **D6 — small-team runs on the LOCAL posture, fleet on the REMOTE one,
  and neither is a convenience.** `openLoopSession` branches on
  `--remote` versus `--ledger`, so the loop verbs reach both.

  Fleet mode **requires** the remote: genuine contention between two
  workers racing `claim take` needs the optimistic push loop
  (`remote.go`'s `AppendLoop` with per-attempt re-derivation).
  `ledger.Store.Append` has no such loop — it compares the signed
  `Prev` against the reconciled tip and returns `ErrWrongPrev` when
  they differ, full stop. So a local fleet would not produce ordinary
  contention that converges; it would produce hard append errors, which
  is a different thing wearing the same name. The build plan names the
  `claim take` race as the middle arm's common case, so a local fleet
  would be a fleet with the contention taken out.

  Small-team mode **requires** the local posture to finish: `verdict
  render` takes `--ledger <dir>` and defines no `--remote` flag, so the
  verdict — the whole reason the charter row names small-team mode — is
  reachable end to end only there. One principal on one machine is
  exactly the deployment where that is honest.

  Answers open question 1's remainder and open question 4's posture
  half.

- **D6.5 — the consequence, stated rather than buried: fleet mode cannot
  render its verdict, and this card REPORTS that rather than fixing
  it.** `verdict render` is local-only, so the verifier lane cannot act
  against a shared remote ledger at all.

  It is not a small widening. The verdict payload carries `submission:
  "<position>"` — a **derived** value — so a remote render needs
  `pushDraft`'s `recheck` seam and per-attempt re-derivation, which is
  precisely the defect class `plans/os-9b3f3ef3.md` D1 records ("a
  derived value is re-examined against the refreshed tip and refused
  rather than replaced"). Absorbing that into an end-to-end fixtures
  card would be widening a test card into a protocol card.

  So fleet mode's drill runs the worker lanes to `submission.made` and
  asserts the review state and the fleet's disjointness properties; the
  verdict half is **carded**, and the plan says plainly that III.J's
  closing row is met for small-team mode and met-to-submission for
  fleet. Naming the remainder is the point — the alternative is a green
  suite over a row that is not actually met, which is the failure this
  whole phase keeps guarding against.

  **Scope guard: this card does not add `--remote` to `verdict render`.**

- **D7 — small-team disjointness is PROVEN BY A REFUSAL, never by
  distinct key paths.** The minimal identity set is two: an implementing
  actor (`claim`) and a verifying actor (`verdict`), both operated by
  one principal. That is the charter's own floor.

  Asserting `implKey != verifyKey` would prove only that the fixture
  wrote two files. The property is that the boundary **enforces** it, so
  the drill runs `verdict render` twice: once with the implementing key,
  which must refuse with `NotIndependentError` naming the claimant or
  the bound submission's signer, and once with the verifying key, which
  must be admitted. A one-principal deployment that wired one key for
  both would then be refused by Seed rather than by a convention.

  Answers open question 4.

## Acceptance Criteria

1. Small-team mode runs the **full** loop on one principal's two
   identities and ends with an admitted `verdict.rendered`, asserted by
   reading the chain back rather than from the verb's report.
2. The implementing key's `verdict render` is **refused** by admission
   naming the claimant or the bound submission's signer, and the
   verifying key's is admitted. Both directions, so it cannot pass by
   refusing everything (D7).
3. Fleet mode provisions one identity per shipped lane with grants read
   from `next/lanes/`, runs two workers against one remote, and reaches
   `submission.made`. The curator key reads and **cannot write** (D2).
4. **All three convergence arms are exercised**, each asserted from the
   transcript, and the drill **fails if any arm went unexercised** (D5).
   This criterion is what stops the rest being vacuous.
5. The blind-retry detector fires: a (subject, act, code) refusal
   repeating on consecutive iterations from an unadvanced position fails
   the drill (D4).
6. Every refusal that closed a window appears **verbatim** in that
   window's packet findings, read from the ledger (D4).
7. Neither fixture wires a wake channel, and the surface pin fails if
   `loop.Verbs` gains a method or `loop` gains an option (D5).
8. **Mutation evidence, per property.** Each must fail a drill:
   dropping an arm from the fixture so it goes unexercised; removing the
   blind-retry detector's position comparison so a spin passes; letting
   the builder carry its own grant table instead of reading the
   manifests; staging the verdict with `ledger append` so no rule runs
   (D3); and allowing the implementing key's verdict to stand.
9. `make check` green with coverage measured **cold**, at least three
   readings above the gate, and the suites pass unprivileged.

## A risk worth naming now

The risk is not that a fixture fails. It is that both fixtures **pass
while meeting no refusal**, and every convergence assertion in this plan
is then true of a run that proved nothing. D5 exists for exactly that,
and it is the criterion most likely to be quietly weakened during
implementation, because planting a refusal is fiddly and the drill is
green without it.

The check that keeps it honest is not "did the tests pass" but "does the
transcript show all three arms", which is why the arm inventory is an
assertion rather than a comment.

The second risk is subtler and is the one #203's review taught: a
premise that names something the tree does not have. Every conjunct here
cites a function or a file — `openLoopSession`'s posture branch,
`admit.Check`'s five call sites, the `verdict` rule's two
`NotIndependentError` returns, `runVerdictRender`'s flag set with no
`--remote` — so each can be checked in one grep rather than trusted. If
one of them turns out to be wrong, the decision resting on it is wrong,
and that is the intended failure mode: visible.
