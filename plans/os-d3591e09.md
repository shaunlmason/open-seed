# Plan: next Phase 2.3 — enforced posture, seed-admit pre-receive hook (os-d3591e09)

Implements [`docs/next-build-plan.md`](../docs/next-build-plan.md) Phase 2
item 3: the enforced self-hosted posture — a `pre-receive` hook binary
that makes the validator the ledger ref's sole writer. Design authority:
[`SEED-NEXT.md`](../SEED-NEXT.md) Part II (admission boundary) and
conformance III.B: the hook refuses invalid pushes, force-updates, and
deletions of the ledger ref, and is **stateless** — every decision is
rebuilt from the repository it guards, so a killed and replaced hook
host loses nothing (the kill-and-replace drill itself lands in 2.5).
The hook imports 2.1's `internal/admit` unchanged: same rules as the
cooperative client, different enforcement point.

## Steps

1. **The binary.** `next/cmd/seed-admit`: a git `pre-receive` hook. It
   reads `<old> <new> <ref>` update lines from stdin; refs other than
   the guarded ledger ref (default `refs/seed/ledger`, overridable via
   `SEED_ADMIT_REF`) pass through untouched. It runs inside the bare
   repository it guards (git sets the cwd), reading objects with
   `git --git-dir` invocations only: no config files, no caches, no
   state outside the repo.
2. **Ref-shape refusals.** A deletion of the guarded ref (all-zero new
   id) refuses. A non-fast-forward update (old is not an ancestor of
   new, checked with `merge-base --is-ancestor`) refuses: history behind
   the verified tip is append-only, so a force-update is a rewrite by
   definition. An initial push (all-zero old id) is admitted through the
   same content path with genesis rules applying at position 0.
3. **Content admission, stateless and rule-shared.** Materialize the
   pushed tree (`git archive <new>`), open it as a ledger store, and
   verify the whole stream from genesis; then every record beyond the
   old tip's count must pass the same `admit` rule set against the
   context at its own position (halt windows and upgrades inside the
   push apply to the records after them). Implementation replays
   per-record context (correctness over speed until Phase 12 budgets);
   any helper this needs lands in `internal/admit` as an addition, not
   a rework. Commit ancestry does not make tree contents append-only,
   so the admitted range is pinned at the record level: the new stream
   must hold at least the old count (a fast-forward commit that
   truncates the ledger refuses as dropping admitted records) and its
   record at the old boundary must hash-equal the old tip — hash-chain
   equality makes the whole prefix identical, so any rewrite of
   admitted records refuses even on a descendant commit.
4. **Refusal surface.** Refusals print one line to stderr and exit
   non-zero, which refuses the whole push atomically; git relays the
   line to the pusher as a `remote:` message, which is exactly what the
   cooperative client's exit-11 `remote_rejected` message carries. The
   line names the refusing check per the division of labor: the
   admission-only rules name their shared `admit` rule (`halted`,
   `shape`, `classification`), while refusals owned by the full replay
   (forged signature, unresolvable actor, version discipline, upgrade
   schema, linkage) carry the positioned verification reason
   (`rule verify: position N: <reason>: <detail>`), the same reasons
   `seed ledger verify` reports. One rule set still decides admission;
   verification-owned refusals are not re-derived hook-locally just to
   rename them. Admitted pushes exit 0 silently.
5. **Tests** (driving the real hook under a bare remote): build the
   binary with `go build` in the test setup and install it as
   `hooks/pre-receive`; a valid cooperative append through
   `gitref.AppendLoop` lands end to end; direct raw-git pushes of
   invalid streams refuse with the rule named — a forged signature, a
   classification-hostile payload, a non-lift event on a halted chain,
   a wrong-version event after an upgrade, and a schema-broken upgrade;
   a force-update rewriting an admitted record refuses; deleting the
   ledger ref refuses; a push carrying several new records validates
   each at its own position; an unrelated ref (e.g. a docs branch)
   passes untouched; every refusal leaves the remote ref exactly where
   it was.

## Acceptance Criteria

**Boundary set (new, shown working):**

- With the hook installed, the validator is the guarded ref's sole
  writer: no invalid stream, force-update, or deletion lands, however
  the push is produced (cooperative loop or raw git).
- The hook runs the same `admit.Default()` rule set as the client — no
  hook-local rule derivation — and names the refusing check to the
  pusher: the `admit` rule name for admission-only rules, the positioned
  verification reason for replay-owned ones.
- Record-level append-only-ness is pinned by tests for both shapes: a
  descendant commit that rewrites admitted records refuses, and a
  descendant commit that truncates them refuses.
- Statelessness: the hook process reads nothing but the repository it
  guards; a fresh process on a fresh copy of the bare repo makes the
  same decisions (pinned by running the refusal suite through
  re-installed hooks; the full kill-and-replace drill is 2.5).
- Non-guarded refs are untouched in both directions.

**Retention set (existing, shown unharmed):**

- `internal/admit`, `internal/gitref`, and all Phase 1 suites pass
  unchanged (`cd next && go test ./internal/... ./cmd/... -count=1`).
- The repo-wide gate stays green with the ≥90% coverage gate
  (`make check`).
