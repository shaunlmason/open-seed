# Plan: the capability card's signature is verified, and its canonical form is RFC 8785 (os-f11601e0)

Charter authority: [`SEED-NEXT.md`](../SEED-NEXT.md) III.N (the
A2A-shaped cross-organization boundary). Spec:
[`next/spec/boundary.md`](../next/spec/boundary.md). The boundary landed
with Phase 13 item 5 (#279, `plans/os-40ed0ca0.md`); this card closes two
gaps a read-only review of the tree at `bfa01638` found in it. Tier:
standard. Plan-first.

## What the tree actually shows

Both defects are confirmed by reading, and the second by running.

**(1) No production path verifies the signature.** `boundary.Verify`
exists and is correct, but its only caller is an optional flag.
`cmd/seed/boundary.go:169` runs it only `if *pub != ""`, and
`Makefile:51` runs `seed boundary check` with no `--pubkey`, so the
repository's own gate compares the card's *canonical bytes* against a
re-render of the declaration and reports `"verified": false` as a
success. A card whose signature is absent, truncated, or made by an
entirely different key passes that gate, because `check` strips
`Signer` and `Signature` before comparing (`boundary.go:154-155`).

The reader's half is missing outright. `boundary check` requires
`--config <file> --name <name>`: it verifies a card against *a local
declaration that renders it*. A stranger who fetched a card from
`GET /card` has no such declaration, only the card bytes and an
operator key given out of band, so the spec's "a reader verifies the
signature against the operator key it was given out of band"
(`plans/os-40ed0ca0.md` D1) is reachable by no verb this build ships.

**(2) `Canonical()` is not RFC 8785.** Its doc comment says
"JCS-canonical bytes", but the body is `encoding/json` with
`SetEscapeHTML(false)`. Go's encoder escapes U+2028 and U+2029
unconditionally; JCS emits them literally. Measured against
`github.com/gowebpki/jcs` v1.0.1, the library `internal/event` already
uses at `event.go:58`:

    Canonical():    {"name":"open seed x","protocol":"seed/8"}
    jcs.Transform:  {"name":"open<U+2028>seed<U+2029>x","protocol":"seed/8"}

A card carrying either character in `name`, `ingress.through`, or a
squad name is therefore signed over bytes an independent JCS verifier
never reconstructs, and a valid signature is rejected. The two
canonicalizers in one tree disagreeing is the defect; the narrow
trigger is why it has not bitten.

## Design decisions

### D1. The gate verifies against a pinned key, and drift and forgery refuse differently

`Makefile:51` gains a `--pubkey`, so the repository's own gate proves
the checked-in card is signed by the key it should be. The key is
public, so it is checked in beside the card as `next/boundary/operator.pub`
(hex, one line), and `boundary check` learns `--pubkey-file` so the
Makefile names a path rather than pasting a key into a recipe.

Two refusals stay distinct, because they mean different things: a card
that does not match the declaration is `card_drift` (re-render it), and
a card whose signature does not verify is the boundary refusal
`Verify` already returns (re-sign it, or refuse the key). Neither is
folded into the other.

**Explicitly not in scope**: sourcing the key from the ledger keyring.
The gate runs with no ledger, and the boundary's premise is a key
given out of band; a pinned file is that premise, written down.

### D2. The reader's path is its own verb, and takes no declaration

Add `seed boundary verify --card <file> --pubkey <hex>|--pubkey-file
<path>`, which parses the card, calls `boundary.Verify`, and reports
the signer. It requires no `--config` and no `--name`, because the
stranger has neither. It is the only reader-side verb, so a stranger's
whole flow is: fetch the card, verify it against the key received out
of band, then file through the ingress it names.

`boundary check` keeps its shape for the publisher: declaration in,
drift out, signature verified when a key is given. Its `--pubkey`
becomes non-optional in the Makefile's invocation but stays optional
in the verb, since a publisher re-rendering a card before signing it
has no signature to check yet.

### D3. `Canonical()` routes through the same JCS transform as the event model

Replace the hand-rolled encoder with `jcs.Transform` over the marshaled
bytes, the exact shape `event.Canonical` uses. One canonicalizer, one
dependency already in `go.mod`, no new module.

**This can invalidate existing signatures**, and the checked-in card is
signed. A card whose fields carry no U+2028 or U+2029 canonicalizes
identically under both, so in practice the tree's card is unaffected;
the plan proves that rather than assuming it, by asserting the current
card's bytes are unchanged across the switch and that it still verifies.
If any signed artifact did change, re-signing is the operator's act and
this card would stop and say so rather than re-sign on its own.

### D4. A property test pins the two canonicalizers together

The regression class is "two canonicalizers in one tree disagree", so
the drill is a property: over a corpus of card values including the
hostile characters, `Card.Canonical()` equals `jcs.Transform` of the
same value with the signature removed. A future hand-rolled
optimization fails here by name.

## Steps

1. **`Canonical()` through `jcs.Transform`** in
   `next/internal/boundary/boundary.go`, matching `event.Canonical`'s
   shape, with the doc comment made true.
2. **The property drill**: `Canonical()` equals `jcs.Transform` over a
   corpus including U+2028, U+2029, non-ASCII and an empty squad list;
   plus a fixed-vector test that the current `boundary/card.json`
   canonicalizes to the same bytes as before the change and still
   verifies under its signer.
3. **`boundary verify`**: the reader-side verb, its usage line, its
   registration in `cmd/seed/catalog.go`, and `--pubkey-file` on both
   it and `boundary check`.
4. **The gate**: `Makefile:51` gains `--pubkey-file next/boundary/operator.pub`;
   the key file is added, derived from the key that signed the card and
   asserted to match its `signer` fingerprint.
5. **The drills**: a forged card (valid shape, signature by another
   key) refuses at the gate and at `boundary verify`; a card with a
   truncated or absent signature refuses; the two-organization drill
   gains the reader's verify step before it files its request.
6. **The record**: `next/spec/boundary.md` (the reader's verb, the
   canonical form named as RFC 8785, the gate's key), the handbook's
   boundary lines, `next/docs/decisions.md`, `memory/LEARNINGS.md`,
   and the receipt.

## Acceptance Criteria

1. `Card.Canonical()` equals `jcs.Transform` of the card's marshaled
   bytes without `signature`, over a corpus including U+2028 and
   U+2029, proven by a property test rather than a single example.
2. The checked-in `boundary/card.json` canonicalizes to the same bytes
   before and after the change and still verifies under its signer, so
   no existing signature is invalidated silently.
3. `seed boundary verify --card <file> --pubkey <hex>` verifies a card
   with no declaration and no name, and reports the signer.
4. A card signed by a different key, one with a truncated signature,
   and one with no signature each refuse at `boundary verify` and at
   `boundary check --pubkey`, with the boundary refusal, distinct from
   `card_drift`.
5. `make check` runs `boundary check` with a key, so a card that drifts
   and a card that is forged both fail CI, and the success envelope
   reports `"verified": true`.
6. The two-organization drill verifies the fetched card against the
   out-of-band key before filing its request.
7. `make check` green, the coverage gate held at 90%, generated docs
   drift-free.
