# Plan: seed upgrade — move the engine pin against tagged releases (os-4a347bd1)

R8's promised command, currently a hand edit: upgrading the engine means
manually rewriting `.seed/engine.lock` with a version and six checksums
copied off a release page. `seed upgrade` makes that one verified command —
resolve the target release, fetch and cross-check its checksums, rewrite
the lockfile — while keeping the human gate exactly where it is: the
command **never commits or pushes**; `engine.lock` is control surface and
lands only through a reviewed PR, which the command's output walks you
through.

## Steps

1. **Release resolution** (engine, `internal/upgrade`): the target is
   `--to vX.Y.Z` when given, otherwise the repo's latest release, resolved
   without any API token via the `releases/latest` redirect — read from
   the 3xx `Location` header with a **no-follow client**
   (`ErrUseLastResponse`; Go's default client would follow to a 200 and
   discard the header), and every subsequent URL is constructed from the
   lockfile's `repo` line, never from the redirect's host. Tags must
   parse as semver; an unparsable tag is a refusal. The base-URL
   override (`SEED_UPGRADE_BASE_URL`) exists solely so tests run against
   a local fake: **non-HTTPS values are refused unless the host is
   loopback**, so no plaintext endpoint can ever supply the hashes that
   rewrite a control-surface file.
2. **Checksum fetch + validation**: download `checksums.txt` for the
   target tag over TLS (Go's net/http, standard roots — the same trust
   the bootstrap shim already places in the release host). Match the six
   **exact asset filenames the shims download** —
   `seed_<ver>_<os>_<arch>.tar.gz` for linux/darwin, `.zip` for windows
   (`scripts/seed` vs `scripts/seed.ps1`) — refusing duplicates; a
   missing platform is a hard refusal (the cross-compile matrix is a
   release invariant, and a partial lockfile would strand that
   platform's users). Each sum must be 64 hex chars and is **normalized
   to lowercase** before writing (the POSIX shim compares byte-for-byte
   against lowercase `sha256sum` output).
   **Protocol preflight**: releases also ship a `protocol.txt` asset
   (the `.seed/version` values the engine supports; the release
   pipeline adds it from this task forward). Before writing, `upgrade`
   fetches it for the target and refuses an incompatible release with
   template-upgrade/rollback remediation — the alternative is a pin
   whose every `scripts/seed` invocation (including `upgrade` itself)
   exits 10 until the lockfile is hand-reverted. A release without the
   asset (predating this task) is a warning plus an explicit
   `--assume-protocol-ok` to proceed. Covered in the fake-release
   tests.
3. **Lockfile rewrite**: update `version` and the six `sha256_*` lines in
   `.seed/engine.lock` **preserving everything else byte-for-byte**
   (comments, `repo`, any `vendor` line). Preconditions before any
   write: the lockfile must carry exactly one `version`, one `repo`, and
   one line per platform hash — anything else (a hand-damaged or partial
   lock) is a refusal, never a silent repair. The write is **atomic**: a
   same-directory temp file and rename, so truncation or an I/O failure
   leaves the original intact. Downgrades are compared **semver-aware**
   (`v0.10.0` > `v0.9.0`; multi-digit components in the tests) and
   refused unless the target was named explicitly with `--to` (rollback
   is legitimate; silent downgrade is not). `--check` reports
   `up_to_date` only when the version AND all six hashes match the
   target release — a stale or edited hash at the right version is
   out-of-date. When the lockfile carries a `vendor` line, `upgrade`
   still rewrites the pin but warns that the shim will keep dispatching
   the vendored binary until that line is removed — the two-command
   story is scoped to non-vendored lockfiles.
4. **The human gate, stated by the tool**: on success the command prints
   the exact follow-up — diff the lock, run the shim once so the new
   binary is fetched and hash-verified locally, commit on a branch, open
   the reviewed PR (control surface, owner review). It also surfaces the
   release URL so the reviewer reads the release notes. Attestation
   verification (`gh attestation verify`, design §7.5's stricter mode)
   is documented in the output as an optional manual step — depending on
   an authenticated `gh` from inside the engine is out of scope.
5. **Tests** (engine): an `httptest` fake serving the redirect and
   checksums — latest-resolution, explicit `--to`, lockfile rewrite
   preserving comments/vendor lines, downgrade refusal without `--to`,
   missing-platform refusal, malformed-sum refusal, `--check` both ways.
   No test touches the network.
6. **Release + pin + docs**: cut the engine release carrying the command;
   template bumps `.seed/engine.lock` to it. **Bootstrap, explicitly**:
   the pinned engine predates the command, so the shim would dispatch a
   binary without it — the first bump downloads the new release binary,
   verifies it against the release's `checksums.txt` by hand once, and
   runs it via the existing `SEED_ENGINE=<path>` override
   (`SEED_ENGINE=... scripts/seed upgrade`); the rewritten pin is then
   re-verified by the ordinary shim path. Every later upgrade is the
   plain two-command story, which is what handbook §6's "Upgrading the
   engine" bullet becomes (`scripts/seed upgrade`, then the reviewed
   PR).

## File Scope

- Engine repo: `internal/upgrade/` (new), `cmd/seed/`, `VERSION`
- Template: `.seed/engine.lock` (the new release pin — written by the
  command itself), `docs/handbook.md` (§6 upgrade bullet)

## Acceptance Criteria

- `seed upgrade --check` reports current vs latest and `up_to_date`
  (version + all six hashes) correctly against the fake; `seed upgrade`
  rewrites only the `version` and `sha256_*` lines, atomically,
  byte-preserving the rest of the lockfile, and refuses a damaged or
  partial lockfile.
- The latest-tag resolution captures the redirect Location without
  following it; non-HTTPS endpoints are refused except loopback; an
  incompatible `protocol.txt` is refused with remediation.
- A downgrade without explicit `--to` is refused via semver comparison
  (multi-digit components covered); with `--to` it proceeds (rollback
  path).
- A checksums file missing any of the six platforms, or carrying a
  malformed sum, is a hard refusal — no partial lockfile is ever
  written.
- The command performs no git operations; its output names the reviewed-
  PR follow-up and the release URL.
- The template's engine pin advances to the release carrying the
  command, and the shim fetch-verifies it (hash match) locally.

## Validation Commands

- `scripts/seed version`
- `SEED_UPGRADE_BASE_URL=http://127.0.0.1:9 scripts/seed upgrade --check; test $? -eq 7`
- `grep -q "seed upgrade" docs/handbook.md`
- `sh scripts/validate.sh`

The second command is the executable proof the pinned engine actually
carries `upgrade` and classifies an unreachable release host correctly —
offline and CI-safe (127.0.0.1 is loopback, so the HTTP override is
permitted, and port 9 is the discard port so nothing listens). `upgrade`
is not a port verb, so it does not borrow the port's reserved exit
codes: it documents its own map in the usage text — 0 ok, 1 refusal
(incompatible protocol, downgrade without --to, malformed or incomplete
checksums, damaged lockfile), **7 release host unreachable**, 64 usage —
and the validation above asserts the 7. The full behavioral suite (fake
server, redirect capture, rewrite atomicity, semver downgrade, protocol
preflight, refusals) runs in the engine repo's CI and gates the release
itself.
