# Plan: Claude Code plugin/marketplace channel (os-221f5929, §10 Q4, R8)

R8 is template drift after clone: an instantiated repo freezes open-seed's
capabilities at instantiation time. §10 Q4 names the mitigation the template
repo alone cannot provide: the evolving parts additionally ship through a
Claude Code plugin, "plugin carrying capabilities, template carrying
structure", with `.seed/version` + lockfiles as the update surface on both
paths.

The reconciliation the card asks for (one drift story, not two) falls out of
making the plugin package a **generated fan-out**, exactly like
`.claude/agents/` and `.agents/skills/` already are: `seed sync` renders
`plugin/**` and the root `.claude-plugin/marketplace.json` from the same
sources, and `seed sync --check` (already in `validate.sh` and CI) detects
drift offline. The version on both channels is the single `version` line in
`.seed/template.lock` that os-23494e11 already made the template's release
coordinate; a new `seed plugin status --check` refuses when the marketplace
ref a consumer pinned disagrees with it, which is the cross-channel half of
the same detector, also offline and also from checked-in files only.

Verified against the Claude Code plugin docs (2026-08): a plugin is a
directory with `.claude-plugin/plugin.json` and `skills/`, `agents/`,
`commands/`, `hooks/` at its **root** (never inside `.claude-plugin/`); a
marketplace is a git repo with `.claude-plugin/marketplace.json` whose plugin
entries may use `"source": "./path"` relative to the marketplace root; and a
repo declares the channel for its team in `.claude/settings.json` via
`extraKnownMarketplaces` + `enabledPlugins`, applied once the folder is
trusted.

Two findings this work has to absorb rather than paper over:

- **Roles are invisible to Claude Code today, and that is a D8 conformance
  gap.** D8 already binds `.seed/agents/*.md` to be **dual-format** ("Claude
  Code subagent fields + sub-agents-skills' `run-agent`/`permission`/`##
  Done When`") and **"fanned out unchanged"** to `.claude/agents/`. The four
  role files carry only seed's half (`role`, `run-agent`, `permission`);
  Claude Code requires `name` and `description` on a subagent and **silently
  skips** a file missing either (the error goes to the debug log, not the
  session). So the existing fan-out ships four files Claude Code discards,
  and a plugin shipping them would too. The fix is to make the sources
  comply with D8, not to change the fan-out: `.seed/agents/*.md` gain
  `name:` and `description:` alongside the seed keys, and every fan-out
  stays byte-identical. Claude Code ignores frontmatter keys it does not
  recognize, and seed's role lint hashes the body only, so the two halves
  coexist exactly as D8 intended. No design amendment is needed here: this
  is conformance to a binding decision, and sync's byte-identical contract
  is preserved untouched.
- **A plugin's `workflows/` is not a seed workflow.** Claude Code's plugin
  `workflows/` holds dynamic-workflow JavaScript; `.seed/workflows/*.yaml`
  are DAGs the engine runs (`seed workflow run`), and reaching them from a
  plugin cache would couple the engine to a harness-owned path. Seed
  workflow DAGs are structure, so they stay on the template channel, where
  `seed template upgrade` already three-way-merges `.seed/**`. §10 Q4's
  "skills, roles, workflows" is amended in `docs/design-options.md` to say
  so with this rationale rather than diverging silently.

Additive by construction: `plugin/**` and `.claude-plugin/marketplace.json`
are inert files until a repo opts in, open-seed's own
`.claude/settings.json` does not opt in, and `seed plugin status --check`
passes trivially when the channel is off.

## Steps

1. **Plugin render (`internal/plugin`, engine).** One function producing the
   channel's desired file set from a repo root, so sync, `--check`, and the
   tests all share it:
   - `plugin/.claude-plugin/plugin.json`: `name` `open-seed`, `description`,
     `version` (the `.seed/template.lock` `version` line with its leading
     `v` stripped), `repository` (from that file's `repo` line), `author`,
     `license`, `keywords`. Deterministic key order, trailing newline.
   - `plugin/skills/<name>/**`: every `skills/<name>/` directory **except
     `skills/managed/`**. Managed skills are third-party content pinned by
     the consumer's own `seed.yaml`/`seed.lock` (os-6f3104db); republishing
     them under open-seed's manifest would misattribute provenance and
     bypass the lock's hash pinning. The exclusion is asserted by a test and
     stated in the handbook.
   - `plugin/agents/<role>.md`: the role body with harness frontmatter (see
     step 2).
   - `.claude-plugin/marketplace.json` at the repo root: `name` `open-seed`,
     `owner`, `description`, and one `plugins` entry
     `{name: open-seed, source: "./plugin", description}`. **No `version` in
     the entry**: the docs warn that `plugin.json` always wins and a stale
     entry version silently masks it, so the version lives in exactly one
     place.
2. **Make the role sources D8-dual-format (`.seed/agents`, `internal/validate`).**
   - `.seed/agents/*.md` gain `name:` (the subagent identifier, matching the
     existing `role:` value) and `description:` (one line, "when to delegate
     to this role") alongside the seed keys already there.
   - `seed validate`'s role lint requires both keys on every role file and
     requires `name:` to be a valid subagent identifier (lowercase letters
     and hyphens, no `:`, no leading `-`), so the D8 dual-format contract
     stops depending on nobody forgetting it.
   - **No change to `internal/sync`'s copy semantics.** Fan-out stays
     byte-identical for `.claude/agents/`, and `plugin/agents/` is the same
     byte-identical copy: the "fanned out unchanged" half of D8 is
     preserved, and sync's package contract needs no exception.
   - Role-variant body-hash identity (§6) is unaffected: the change is
     frontmatter only.
3. **Wire into `seed sync`.** `Plan()` appends the step-1 actions, so
   `seed sync` writes them and `seed sync --check` fails on drift with the
   existing "edit the source tree, never the fan-out" message. No new
   command, no second drift story; `validate.sh` and CI pick it up unchanged.
4. **`seed plugin <verb>` (opt-in surface, `cmd/seed/plugin_cmd.go`).**
   Offline, no network, edits only `.claude/settings.json`:
   - `enable`: merge `extraKnownMarketplaces["open-seed"] = {source:
     {source: "github", repo: <template.lock repo>, ref: <template.lock
     version>}}` and `enabledPlugins["open-seed@open-seed"] = true` into
     `.claude/settings.json`, preserving every other key and formatting as
     2-space JSON. Idempotent. **The doubled `source` key is the real Claude
     Code schema, not a typo**: the value of `extraKnownMarketplaces.<name>`
     is an object whose `source` field is itself an object with its own
     `source` discriminator (`"github"`, `"directory"`, `"url"`, …). A test
     asserts the exact nesting so it cannot be quietly "fixed" into a
     flatter shape.
   - `disable`: remove exactly those two entries (and the containing objects
     when they empty), leaving the rest intact.
   - `status [--check]`: report enabled/not, the pinned ref, and the
     `.seed/template.lock` version. `--check` exits 1 when the channel is
     enabled and the pinned ref differs from that version (the two channels
     have drifted apart); exits 0 when the channel is off. `.claude/**` is
     control surface, so the write lands in a reviewed PR like any other
     edit there: the command composes the JSON, a human merges it.
5. **Guardrails, CODEOWNERS + validators.** Both new paths are control
   surface and both need the local *and* server-side halves of D4.1:
   - `.seed/guardrails.yaml` `protected_paths` gains **`.claude-plugin/**`
     and `plugin/**`**. `plugin/**` matters most: it is the shipped
     capability payload, so a clone whose L3 `auto_merge_allowlist` matched
     it could auto-merge changes to the skills and roles it distributes.
     The existing validator rule (allowlist may intersect neither the
     control surface nor `plans/**`) then covers both automatically.
   - `CODEOWNERS` gains `/.claude-plugin/` and `/plugin/` entries, so the
     server-side owner review D4.1 requires actually applies. Guardrails
     without the CODEOWNERS line is a local-only guarantee (R9).
   - `scripts/validate.sh` gains `sh scripts/seed plugin status --check`
     alongside the other engine-backed lints, degrading with the same
     warning when the engine cannot bootstrap.
6. **Template artifacts.** Commit the generated `plugin/**` and
   `.claude-plugin/marketplace.json` (checked-in fan-outs, same as
   `.claude/agents/`), add the "do not edit here" README marker under
   `plugin/`, add `description:` to the four role files, and regenerate
   `.claude/agents/*.md`. open-seed's own `.claude/settings.json` stays
   opt-out: proof that template-only users are unaffected.
7. **Docs.** `docs/handbook.md` §6 gains "Two distribution channels": what
   each carries (structure vs capabilities), when each is right, the exact
   `extraKnownMarketplaces`/`enabledPlugins` snippet, `seed plugin enable`,
   how drift is caught on both halves, and the honest limits: a git-based
   **marketplace** source pins by `ref` only (no `sha`), so the channel is
   tag-trust, not hash-trust, unlike `seed.lock`; and enabling the channel
   means Claude Code clones the marketplace repo at folder-trust time.
   `docs/design-options.md`: amend §10 Q4 and the R8 line with the
   workflows-stay-on-the-template-channel rationale from the preamble.
8. **Tests (engine, offline).** Golden render of `plugin.json` +
   `marketplace.json` from a fixture root; version/repo sourced from
   `template.lock`; `skills/managed/` excluded while local skills are
   included; both fan-outs of a role are byte-identical to
   `.seed/agents/<role>.md`, dual-format keys and all; `sync --check` fails
   when a generated file is hand-edited and passes after `sync`; role lint
   rejects a missing `name`/`description` and an invalid `name`;
   `plugin enable` writes the doubled-`source` nesting exactly, is
   idempotent, and preserves unrelated settings keys; `disable` restores the
   original file; `status --check` passes when off, passes when ref matches,
   exits 1 on mismatch.
   Cut an engine release and move the pin with `seed upgrade` in the task PR.

## File Scope

- Engine repo: `internal/plugin/` (new), `internal/sync/sync.go`,
  `internal/validate/validate.go`, `cmd/seed/plugin_cmd.go` (new), tests
- Template: `.claude-plugin/marketplace.json` (new, generated), `plugin/**`
  (new, generated), `.seed/agents/*.md`, `.claude/agents/*.md`
  (regenerated), `.seed/guardrails.yaml`, `scripts/validate.sh`,
  `docs/handbook.md`, `docs/design-options.md`, `.seed/engine.lock`

## Acceptance Criteria

- `seed sync` renders the plugin package and the marketplace manifest from
  the existing sources; `seed sync --check` fails on any hand edit to them,
  offline, and passes in CI after a sync. No second drift mechanism is
  introduced.
- The plugin's version and the marketplace's repo/ref come from the single
  `.seed/template.lock` coordinate os-23494e11 established;
  `seed plugin status --check` refuses when an enabled channel's pinned ref
  disagrees with it.
- A fresh instantiation can install the channel: `seed plugin enable` writes
  a valid `extraKnownMarketplaces` + `enabledPlugins` declaration, and
  `claude plugin validate .` reports the marketplace and plugin manifests
  clean.
- Roles shipped through either fan-out are actually loadable as Claude Code
  subagents (`name` + `description` present in the **source**, per D8's
  dual-format rule); every fan-out remains byte-identical to its source;
  `seed validate` fails a role file missing either key or carrying an
  invalid `name`.
- `.claude-plugin/**` and `plugin/**` are both in `protected_paths` **and**
  `CODEOWNERS`, so neither the local nor the server-side half of D4.1 is
  missing for the new control surface.
- `skills/managed/**` never appears in the plugin package.
- With the channel not enabled, `make check` and `sh scripts/validate.sh`
  behave exactly as before.
- The handbook documents both channels, when each is right, and the
  ref-only pinning limit; §10 Q4 records the workflows decision.
