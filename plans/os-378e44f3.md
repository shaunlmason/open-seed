# Plan: next — four review fixes for the worker loop (os-378e44f3)

Four Codex findings on #191 (Phase 9 item 1c), all verified against the
code and all correct, arriving after that PR merged. A merged PR cannot
track new work, so they land as a fresh change.

The findings themselves are most of the specification. What needs
deciding — and what this plan is for — is the **shape** of two of the
fixes, where the obvious repair and the right one differ.

## The findings, verified

| # | severity | defect |
|---|---|---|
| 1 | P1 | the loop's actor is supplied beside its key instead of derived from it |
| 2 | P1 | a claim reaped between the take and the post-claim read turns contention into an error |
| 3 | P2 | `claim take` is a declared liveness source but is never observable under the fence it opened |
| 4 | P2 | packet temp files are never unlinked |

## Design decisions (binding for this task)

- **D1 — the actor is DERIVED from the key, and the parameter is
  removed.** The obvious repair is to cross-check a supplied actor
  against the key and refuse a mismatch. That is worse: it keeps a
  parameter whose only correct value is computable, so every caller
  gets a chance to be wrong and the check exists to catch them.

  Deriving removes the class. `New` reads the key, fingerprints it, and
  that fingerprint is what the loop polls with — so poll, act and
  observe cannot disagree about who is working. The failure this
  prevents is quiet and bad: selecting work under one identity's
  eligibility, signing under a second, and writing liveness under a
  third, while the classifier — which keys the stream by the holder —
  reads silence from a worker that is working.

  Cost, stated: `New` now does file IO and can fail for a new reason.
  That is the right place for it, since a loop that cannot read its own
  key cannot do anything else either, and failing at construction beats
  failing mid-window.

- **D2 — a reaped claim is IDLE, not a park.** The window is gone, so
  there is nothing to exit; parking would refuse for want of an active
  claim, and the reserve before it would refuse first. This is the
  build plan's middle convergence arm reached exactly as written: *a
  refreshed position-stamped read showing the act is no longer owed.*

  The rule this does NOT weaken: every path out of an **open** window is
  still a deliberate exit. The read is what establishes the window is
  not open, and acting on a refreshed authoritative read is the
  opposite of abandoning a claim.

- **D3 — the fence comes from the act that opened it.** `claim take`
  already returns `{"subject", "fence"}`, the fence being the admitted
  position. The loop adopts a fence any act's result names, before
  observing. Generalizing to "any act that names one" rather than
  special-casing the claim keeps the rule small and keeps it true if a
  second window-opening act ever exists.

  Why it matters beyond tidiness: the gap it closes is precisely the
  stall window. A worker that takes a claim and then hangs before
  reserving is the case the expiry classification exists to catch, and
  until this fix its claim emitted nothing the classifier could see.

- **D4 — packets are removed once the verb has consumed them**, on
  every path including refusals. An unattended lane runs indefinitely,
  so one file per iteration is a slow leak of both temporary storage
  and the packet contents, which are work product rather than scratch.

- **D5 — two DRILLS were wrong and are corrected here**, which is the
  part of this card worth reviewing hardest:

  1. The e2e liveness assertion hard-coded a shorter `liveness_from`
     copied from a unit fixture. It passed only because finding 3 meant
     `claim take` never emitted at all — a drill agreeing with the bug
     it should have caught. It now derives the expected set from the
     **shipped manifest**.
  2. The fence drill's pre-claim `situation` returned a window that a
     pre-claim read cannot have. That pre-populated `d.fence`, so the
     drill passed without the fix; reverting the fix did not fail it.
     The pre-claim read now correctly reports no window.

  Both were found by mutation-testing the fixes rather than by reading,
  and the second was found *only* because the mutation did not fail.

- **D6 — coverage is this card's problem, not a follow-up.** The new
  error paths dropped the gate reading below 90% on the branch where
  the fixes were written. Every added branch is a real behavior
  (an unreadable key, an unparseable key, a reaped claim, a packet that
  cannot be written), so they are drilled rather than exempted, and
  coverage is measured **cold and repeatedly** before submission, per
  the lesson already in `memory/LEARNINGS.md`.

- **D7 — scope guard.** No new verb, no new projection, no admission
  change, no spec change beyond recording what the fixes establish. No
  new loop capability: this card repairs the loop that merged and adds
  nothing to it.

## Acceptance Criteria

1. The loop's actor is derived from its signing key, with no parameter
   to supply one; a drill asserts the polled fingerprint is the key's,
   and that an unreadable or unparseable key refuses at construction.
2. A post-claim read reporting no window ends the iteration idle, with
   no reserve and no park attempted, and a drill proves it.
3. `claim take` is observable under the fence it opened, drilled with a
   pre-claim read that reports **no** window, so the fence can only
   have come from the act's own result.
4. No packet file outlives the verb that consumed it, on the submission
   path and the park path both.
5. The e2e liveness assertion derives its expectation from the shipped
   manifest rather than restating a list.
6. Every fix is mutation-checked: reverting it fails its drill. This is
   recorded per fix, not claimed in aggregate.
7. `make check` green with coverage measured cold at least three times,
   all readings above the gate.

## A risk worth naming now

Two of the four defects were invisible to their own drills, and the
drills were mine. The pattern in both was the same: the test agreed
with a convenient shape rather than the shipped one — a fixture's
`liveness_from` in the first case, a window a pre-claim read cannot
have in the second.

So the review question for every drill this card touches is not "does
it pass" but **"does reverting the fix make it fail?"** Each of the four
answers that explicitly, and a fix whose mutation does not fail its
drill does not ship.
