# Plan: next Phase 1.3 — genesis: `seed init` writes the signed genesis (os-d636299d)

Implements [`docs/next-build-plan.md`](../docs/next-build-plan.md) Phase 1
item 3: a ledger begins with a signed `system.genesis` naming the initial
governance root and the protocol version. Design authority:
[`SEED-NEXT.md`](../SEED-NEXT.md) Part II §1 (genesis and halt) and
Appendix B; builds on `next/internal/event` (os-aa146827) and
`next/internal/ledger` (os-ead12024). Conformance: III.A — "a genesis event
names the governance root and protocol version; version mismatch refuses
with a distinct exit code."

## Steps

1. **Genesis payload.** `system.genesis` payload schema: `protocol`
   (`seed/0`) and `governance_root` (list of `{fingerprint, public_key}`
   operator entries, raw keys hex-encoded, at least one required); subject
   `system`; `prev` = the empty hash; signed by one of the named root keys
   (the operator running init). Payload helpers + schema check live beside
   the event package's verb catalog groundwork (`internal/genesis` or
   `internal/event` extension: smallest home wins, recorded in the decision
   log).
2. **CLI verb.** `seed init --ledger <dir> --key <openssh-ed25519-private>
   [--operator <openssh-ed25519-public>]...` writes the genesis record via
   `ledger.Store.Append` into an **empty** store: a non-empty ledger refuses
   (distinct error code in the envelope, exit per spec table); the signing
   key's fingerprint is always part of the governance root. Success envelope
   carries the genesis hash and position 0; from this verb on, ledger-aware
   verbs stamp `position`.
3. **Version discipline, upgrade-safe.** Per `next/spec/protocol.md`
   ("Protocol version"): every event carries the version *active at its
   position*; the active version starts as the genesis-named version and
   changes only at a `system.protocol.upgraded` event (which carries the
   old version and names the new one). Verification takes a declared
   **supported-versions set** and accepts a chain when each event's `v`
   equals the active-at-position version and every active version is
   supported, so a valid `seed/0` prefix still verifies after a future
   upgrade. `version_mismatch` (exit 10) is reserved for an event whose `v`
   breaks the active-at-position rule or an active version outside the
   supported set; wired into store verification so it holds everywhere,
   not per-verb.
4. **Tests** (conformance III.A): init on an empty dir yields a one-event
   chain that `VerifyFromGenesis` accepts; re-init refuses non-empty; the
   genesis names root fingerprints and `seed/0`; an event whose `v`
   differs from the active-at-position version refuses with the distinct
   code, and a chain whose active version is unsupported refuses with the
   same code while a supported-prefix fixture (old version up to a
   `system.protocol.upgraded`, new version after) verifies; envelope shape
   for init passes the schema-stability test pattern.

## Acceptance Criteria

- `seed init` on an empty ledger dir writes a signed, verifying genesis
  naming `seed/0` and the governance root; the signer is provably one of
  the named root keys.
- Init against a non-empty ledger refuses with a structured envelope and a
  documented exit code; nothing is written.
- A `v` mismatch anywhere in verification refuses with the distinct
  version-mismatch code (exit 10 per `next/spec/envelope.md`).
- Coverage gate (≥90% on `next/internal/...`) holds; `make check` green.
