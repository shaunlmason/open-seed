# Plan: next Phase 2.2 — cooperative posture, client self-validation (os-895bf828)

Implements [`docs/next-build-plan.md`](../docs/next-build-plan.md) Phase 2
item 2: the cooperative posture — the client self-validates via the
admission library before pushing. Design authority:
[`SEED-NEXT.md`](../SEED-NEXT.md) Part II (admission boundary) and the
Phase 2 binding default that both postures run the **same rule set**:
2.1's `internal/admit` already exposes the `Validate()` adapter shaped
for `gitref.AppendLoop`'s validate seam; this task gives that seam a
real client — a remote mode for the `seed ledger append` dev tool — and
maps every push outcome to a typed envelope. Cooperative means the named
consequence is honest: a client that skips validation can still push
(2.3's enforced posture closes that hole); what this task proves is that
the *cooperating* client refuses its own invalid drafts locally, before
any bytes reach the remote.

## Steps

1. **The remote client.** `seed ledger append` grows `--remote <url>`
   and `--ref <ref>` (default `refs/seed/ledger`) plus `--state <dir>`
   (the `gitref.Client` state dir holding the persisted verified head;
   default under the user cache dir). In remote mode the flow is: lint
   the payload (the existing exit-9 fast path), fetch and verify the
   remote stream (`gitref.Client.Fetch` + materialize), derive the
   active protocol version from the verified stream (the #85 review
   discipline), sign the draft at it, then run `AppendLoop` with
   `admit.Validate(...)` wired into the validate seam — self-validation
   against the refreshed tip on every attempt, before every push.
   `AppendLoop` grows a trailing variadic `...ledger.VerifyOption`
   (backward compatible; existing call sites unchanged) so its per-attempt
   stream re-verification honors the same supported-version set as the
   pre-flight, instead of hard-coding the build default. The pre-flight's
   verified tip is persisted before the loop runs: `gitref` exports
   `RecordVerifiedHead(commit)` (the caller's statement that it verified
   this fetched tip) and the client calls it right after the pre-flight
   replay succeeds, closing the window where a fresh client verifies tip
   A, the remote rolls back to an ancestor, and the loop's own fetch,
   holding no persisted head yet, would accept the regression.
   Local-dir mode is untouched.
2. **Outcome mapping, all typed.** `admit.Refusal` unwraps to its
   underlying error and keeps the existing exit map (halted 7,
   chain_invalid 8, classification_refused 9, version_mismatch 10).
   New mappings for the loop's own refusals: `ErrRetriesSpent` maps to
   exit 2 `contention` (another writer kept winning); `ErrUnavailable`
   maps to exit 5. Two new codes land in `next/spec/envelope.md` per its
   lowest-unused rule, each mirrored as a tested constant in
   `internal/envelope`, one meaning per code: `remote_rejected` at exit
   11 (`ErrRemoteRejected`: the remote's own policy refusal, e.g. 2.3's
   hook; the porcelain output rides in the error message so the pusher
   sees the hook's reason verbatim) and `head_regression` at exit 12
   (`ErrHeadRegression`: a freshness refusal, distinct from failed chain
   verification, so a rollback is never misread as corrupt ledger
   data).
3. **Result envelope.** A won race returns ok with the appended hash,
   the landed position (stamped), the pushed commit id, and the attempt
   count, so drills can assert a real race was survived through the CLI.
4. **Tests** (CLI-level, against bare file remotes): a clean remote
   append lands, verifies from genesis on a fresh materialization, and
   stamps the position; hostile drafts refuse **locally with the remote
   tip unchanged** — a halted remote chain (exit 7), a
   classification-hostile payload (exit 9), and a version-stale draft
   against an upgraded remote (exit 10) — the cooperative posture's
   whole point, asserted by comparing the remote ref before and after;
   a rival writer landing between fetch and push forces a retry that
   still lands (attempts > 1 in the result); perpetual rivals exhaust at
   exit 2; a declining pre-receive hook surfaces exit 11 with the hook's
   words in the message; a vanished remote ref after a verified head
   refuses at exit 12 `head_regression`; and the pre-flight window is
   drilled: a remote rolled back to an ancestor mid-invocation (after
   the pre-flight verify, via a push-time hook) refuses at exit 12
   instead of appending over the regression.

## Acceptance Criteria

**Boundary set (new, shown working):**

- Remote appends run the same `admit.Default()` rule set the hook will
  run, through `admit.Validate` — no client-side re-derivation of any
  rule.
- Every invalid draft refuses locally with nothing pushed (remote tip
  byte-identical before and after), with the rule-typed exit code.
- Race outcomes are typed end to end: retry-and-land reports attempts,
  exhaustion exits 2, remote policy refusal exits 11 carrying the
  remote's reason, head regression exits 12 — including a rollback
  landing between the pre-flight verify and the loop's own fetch.
- Exits 11 and 12 are allocated in the spec table and mirrored by tested
  constants, one meaning per code.

**Retention set (existing, shown unharmed):**

- Local-dir `seed ledger append` behavior is unchanged (existing CLI
  suite passes as-is).
- `internal/gitref`, `internal/admit`, and all Phase 1 suites pass
  unchanged (`cd next && go test ./internal/... ./cmd/... -count=1`).
- The repo-wide gate stays green with the ≥90% coverage gate
  (`make check`).
