Found by the target-scale contention benchmark (os-a00d3f34) on 2026-09-03/04, the second of three 200-writer storms on a 4-core Linux host (seed perf run --writers 200 --history 40, the seed-admit hook enforcing on a bare remote). Runs 1 and 3 landed every writer with no lost update (run 1: contention 970948 ms, attempts per append 51.07). Run 2 failed after 15m30s: '1 of 200 writers failed to land; the first: writer 157: push rejected by the remote (a policy refusal, not a race): remote: seed-admit: rule verify: position 558: bad_prev: prev b692fec4bc38 does not cite tip 2492338b3552 ... [remote rejected] (pre-receive hook declined)'. The hook verified the PUSHED chain from genesis (admitUpdate materializes newID): the chain held records 0..557 with 557 = 2492..., and the writer's own record at 558 cited b692... (the hash of 556). So the client built and pushed a tree containing a newer record it did not link to, and gitref.Push classified the hook's refusal as policy (not one of the race shapes), so the writer gave up instead of re-linking; the storm's no-lost-updates assertion then failed the run (correctly: a writer's append did not land).

What run 2 had that runs 1 and 3 did not: it crossed midnight UTC (23:46 to 00:02), so the history's segment was 2026-09-03.jsonl and every append after 00:00 opened 2026-09-04.jsonl (Store.segmentForAppend names the segment by the wall clock, not the record's ts). Ruled out by reading: Store.Tip reconciles from the segment scan and never trusts HEAD; segmentNames sorts, so a two-segment chain scans in order; Append re-checks prev against the reconciled tip, so the client's OWN store held tip b692 when it appended; each writer has its own git dir and index; AppendLoop uses a fresh temp dir per attempt. Not yet explained: how the pushed tree (git add -A over the temp dir with the client's persistent index, write-tree, commit-tree on the fetched tip) carried record 557 the client's store did not reconcile, or how the hook's materialization differed from the client's tree. Suspects, in order: the index entry for the newly opened 2026-09-04.jsonl from a previous attempt of the same writer (a stale blob retained by git add -A across attempts when the file's stat matches), and git archive or tar of a two-segment tree.

Expected shape: a deterministic drill first, two writers through gitref.AppendLoop against a bare remote with the ledger's WithClock crossing midnight between attempts, asserting the pushed chain verifies at the hook; then the fix where the drill points; and, whatever the cause, Push should not classify a bad_prev refusal whose cited tip is not the tip this attempt fetched as policy: it is a moved tip or a client defect, and re-linking is the loop's answer to both (loop.go's comment lists the race shapes; a hook's bad_prev at the new record's position is a seventh). The failing chain was not kept (the measurer removes its work dir); the drill should keep the pushed tree on failure. Tier: standard (gitref and ledger are the hot path; a chain violation at the door is the thing the benchmark exists to catch). Evidence: /home/user/wt/perf-200-run2-failed.log on the session host (the envelope quoted above); the storm's history and drafts carry ts 2026-09-02T00:00:00Z while the segments are named by the clock.
