P1 because it makes the D3/D4.5 receipt gate unusable: every task PR verify can fail on a correct receipt, and no amount of local verification predicts it. Four PRs are red on this right now (#308, #311, #313, #314).

THE BUG. seed receipt generate hashes the output of git diff verbatim. git writes "index <old>..<new>" lines using an abbreviation length it derives from the repository object count, so the SAME tree hashes differently in different clones. Demonstrated on seed/os-aaec6a3c, identical content both times:

  core.abbrev=7    62e70a6e5cfd4fc3c05fee7f
  core.abbrev=12   9076b22e5d2a3e0f84edc33a

An agent generates the receipt in its worktree; CI regenerates in its own clone and compares. The hashes disagree, and verify fails with "receipt mismatch". It cannot reproduce locally, because generate and verify share one clone there, which is why this burned several hours of misdiagnosis (a runner flake, then the stale-plan rule, then the engine pin) before the mechanism was found.

HOW THE OTHER CAUSES WERE RULED OUT. internal/receipt/receipt.go gives each failure its own message: a non-zero validation exit prints "validation command failed (exit N)", a stale plan prints "plan changed since branch base (D3 stale-plan rule)". CI printed NEITHER, only "receipt mismatch", so in CI all validation commands exited 0 and the plan was current. The mismatch switch then leaves only DiffSHA256 / DiffFiles.

THE FIX IS WRITTEN AND UNRELEASED. open-seed-engine c57e748 ("receipt: hash the diff with full blob ids, independent of the clone") adds --full-index. Source-level confirmation: v0.15.2 internal/receipt/receipt.go:88 is repo.Git("diff", mb, head, ...); main:94 is repo.Git("diff", "--full-index", mb, head, ...). It is the ONLY commit after v0.15.2, and .seed/engine.lock pins v0.15.2, so CI and every agent run the buggy hash.

WHAT THIS CARD OWES, in order:
1. open-seed-engine: bump VERSION to v0.15.3 on a PR. Merging mints the tag via the release workflow. Note this is a release action and the classifier blocked an agent from doing it unattended, so it wants a human hand or an explicit grant.
2. open-seed: bump .seed/engine.lock to v0.15.3. Protected path, so owner review regardless.
3. Regenerate the four receipts under the new engine and confirm verify passes in CI.

WHY THE PIN BUMP MATTERS BEYOND THIS. Until it lands, a green local verify means nothing about CI, and a red CI verify means nothing about the receipt. The gate is not measuring what it claims to measure.
