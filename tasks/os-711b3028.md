Found while implementing os-c4e8b57a (review finding on #184).

gitref.NewClient inits a private bare git dir at <stateDir>/gitdir and writes no config, so outside a test binary that repository runs under stock git auto-gc. The dir is client-owned, ephemeral transport state: a detached gc mutating it after the CLI has exited serves nobody, and a caller that removes its state dir (a CI job cleaning a workspace) hits the same unlinkat-directory-not-empty failure the drills hit.

os-c4e8b57a covered it for tests via a process-wide GIT_CONFIG_GLOBAL in TestMain, deliberately, because that plan's D4 forbids production changes. This card is the production question it excluded: whether NewClient should write gc.auto=0, gc.autoDetach=false and receive.autoGC=false into the git dir it creates, at init, before its first object.

If taken, TestClientGitDirHasNoAutoGC in internal/gitref can then query --local and assert the repository-local property rather than the effective one, which is what the review asked for.

Not urgent: no production failure has been observed, only the test-side one.
