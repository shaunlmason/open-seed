Found while implementing os-6a08b166 (Phase 9 item 4, the small-team
and fleet end-to-end fixtures), and deliberately NOT taken there: that
card's file scope declares next/lanes/** read-only.

Two capabilities the contract lifecycle requires are granted by no lane
manifest in next/lanes/:

- offer.published accepts [supervise, operator]. No lane grants
  supervise.
- merge.observed accepts [observer, operator]. No lane grants observer.

The six shipped lanes grant: curator none, dispatcher dispatch,
implementer claim, maintenance maintenance+operator, planner claim,
verifier verdict.

Why it matters rather than being tidy-up: a deployment assembled purely
from the shipped lanes can neither publish the offer its own workers
poll for, nor record the merge that ends the loop. Both are steps in
the ordinary path - offers are how the dispatch lane invites work
(next/spec/offers.md), and merge.observed is the terminal step of the
reconciliation chain (next/spec/reconciliation.md). Only the
maintenance lane can reach either, through operator, which is not its
job: that lane's whole posture is that it holds no private powers and
does defined maintenance acts, not routing and not forge observation.

The fixtures for os-6a08b166 stage a supervisor and an observer as
BACKGROUND identities outside the mode's identity plan, precisely so
the plan's grants assertion keeps measuring only lane-derived
identities. That is honest for a fixture and wrong as a shipped
posture: it means the modes the charter's III.J row describes are not
buildable from the lane set alone.

Open questions for the plan:

1. Two new lanes (supervisor, observer), or two grants added to
   existing ones? next/spec/lanes.md and the six fragments under
   next/lanes/fragments/ are the surface either way, and
   internal/lane's validation obliges a lane holding CapClaim to
   declare acts_through - neither of these would.
2. The dispatcher lane grants dispatch and publishes nothing. Is
   publishing an offer the dispatch lane's act (and offer.published's
   accepted set is what is wrong), or a supervisor's? offers.md calls
   it "the supervisor's invitation", so the capability table may be
   right and the lane set simply incomplete.
3. Does the curator's empty grants set stay empty? It is the one lane
   with no write path at all, which is deliberate (it proposes through
   a grant-gated path that does not exist yet), so it likely does.

Scope: next/lanes/** (manifests and fragments), next/spec/lanes.md,
possibly internal/keyring's accepted-capability rows if question 2
resolves the other way, and a drill asserting every capability the
ordinary contract path requires is granted by some shipped lane -
which is the assertion whose absence let this reach Phase 9.

Above L1: plan first at plans/<id>.md via its own PR.
