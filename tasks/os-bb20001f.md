`seed template upgrade` resolves the target release by following https://github.com/<repo>/releases/latest and reading the redirect. That HTML endpoint 404s for a private repo even with a Bearer token (github.com HTML does not honor token auth the way api.github.com does), so with shaunlmason/open-seed private the command exits template_host_unreachable regardless of credentials.

Confirmed 2026-08-23 after publishing the v0.1.0 release (os-62b64ce8): the release is correct and api.github.com/repos/shaunlmason/open-seed/releases/latest returns tag_name v0.1.0, but the HTML redirect probe returns 404. Public control: open-seed-engine (public) redirects 302 -> tag/v0.13.2, which is why the engine bootstrap and `seed upgrade` work today.

Two candidate resolutions (pick one, they are not exclusive):
1. Make the template repo public — it is the artifact consumers are meant to pull from, and the handbook already documents pull-based upgrades against it.
2. Have the engine resolve via api.github.com with an optional token, falling back to the HTML redirect — needed anyway for anyone running open-seed from a private fork.

Also: docs/handbook.md 'Cutting a template release (maintainers)' says bump version, commit, tag that commit. It omits publishing a GitHub Release, which the resolution path actually requires — a tag alone is not enough. Update the checklist.
