Found while diagnosing a red verify on #314 (os-f262585a). Cost five separate probes to narrow what one line of output could have said.

WHAT IT PRINTS. On any disagreement between the committed receipt and the regenerated one, seed receipt verify fails with a single line: "receipt mismatch — the regenerated receipt is authoritative (CI is the author of record, R11); the committed copy is forged or stale". It names no field.

WHY THAT IS EXPENSIVE. The receipt carries merge_base, head, plan_path, plan_sha256, diff_files, diff_sha256 and a validation array of command/exit pairs. Any one of them can differ, and the causes are entirely unlike each other: a stale plan_sha256 means the plan moved, a diff_sha256 change means the tree moved, a validation exit means a command failed in the verifying environment and not the generating one. head in particular differs on EVERY honest receipt, because the generate-then-commit sequence records head N and commits as N+1, so a reader who suspects head has to rule it out by experiment rather than by reading.

To narrow #314 I had to: run verify without --run from the branch (passed, so structure is fine); fetch refs/pull/314/merge and run verify there (passed, so CI checkout is not it); run verify --run from the branch (passed); run verify --run from the merge worktree, which is exactly what CI runs (passed); and read the check job log to get the CI coverage reading (91.6%, so not the gate). Every one of those was an attempt to learn which field, and the tool knows.

WHAT IT SHOULD PRINT. The differing keys, with both values, and for the validation array the command whose exit differed and the two exits. The message can keep its R11 sentence; it just needs the diff appended. A structured envelope field would be better still, since the verb already emits seed-envelope/0 and a machine caller has the same problem.

Note the message also asserts a disjunction it cannot know: "forged or stale". A validation command that failed transiently in CI makes the committed copy neither.
