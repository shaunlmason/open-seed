Phase 9 item 4 of docs/next-build-plan.md, and the last item in the
phase. Above L1: plan first at plans/<id>.md via its own PR.

Scope, quoted from the plan: "Small-team mode and fleet mode end-to-end
fixtures. Both run with NO wake channel at all (the one-inbox doctrine
asserted rather than asserted about), and every refusal a lane meets in
them converges within one retry, in one of three ways: an admitting act
on its next attempt, a refreshed position-stamped read showing the act
is no longer owed, or an escalation carrying that refusal's code and
message."

The three convergence arms are all now buildable, which is why this
item comes last in the phase:

- an admitting act: the loop verbs (item 5c).
- a refreshed read showing the act is no longer owed: internal/loop
  already implements this arm and next/spec/loop-verbs.md's "Contention
  is ordinary" section describes it - a claim reaped between its own
  push and the loop's next read leaves a window that is already gone,
  and the iteration ends idle rather than parking what it never held.
- an escalation carrying the refusal's code and message: landed in
  Phase 9 item 2 (next/spec/escalation.md), where claim.parked already
  carries the boundary's code and message VERBATIM in the packet's
  findings.

What is forbidden is the fourth outcome: a blind retry, a silent loop,
or a bare "failed". A refusal a correct lane can do nothing with is a
bug here, exactly as a listed-but-refused verb is one in Phase 8.

The charter's III row this pays: "Small-team mode (one PRINCIPAL
operating a minimal set of actor identities - at least an implementing
actor and a distinct verifying actor, so verdict key disjointness holds
even when one person runs everything) and fleet mode (disjoint actors
per lane) both run the full loop in CI."

Existing material to drive rather than reinvent:

- internal/loop is a LIBRARY precisely so these fixtures can drive it
  with no model and no wake channel; loop-verbs.md names them as its
  consumers. cmd/seed/loop_e2e_test.go's remoteWorkLedger is the
  working shape of a real remote ledger fixture.
- The shipped lane manifests in next/lanes/ define who acts through
  what; the fixtures should read those rather than carry their own, so
  a manifest that stops describing its lane fails here.

Open questions for the plan to decide and record:

1. Where do the fixtures live - cmd/seed e2e tests, a new
   next/fixtures/ tree the build plan's layout section names, or a
   package of their own? The plan's §0 mentions next/fixtures/ for
   drill fixtures.
2. Fleet mode needs disjoint actors per lane, which means several
   enrolled keys with different capabilities. Is that a shared fixture
   builder, and does it read next/lanes/ to decide which capability
   each lane needs?
3. How is "converges within one retry" ASSERTED rather than described?
   The three arms are distinguishable in the ledger and in the
   envelope; the drill must fail on the fourth outcome, which means
   detecting a blind retry rather than trusting its absence.
4. Small-team mode requires verdict key disjointness with one
   principal. What is the minimal identity set, and does the fixture
   prove the disjointness holds rather than assuming the keys differ?
