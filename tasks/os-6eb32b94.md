os-221f5929 shipped the plugin channel and, after review, stopped 'seed plugin status --check' from forbidding a deliberate capability-only ref: aligned/ahead/floating pass, only a stale 'behind' pin fails. Two gaps remain.

1. There is no COMMAND that advances the plugin ref. 'seed plugin enable --ref <tag>' sets one, but a consumer wanting the newest capabilities has to know what tag to name; there is no 'seed plugin upgrade' that resolves the latest release of the marketplace repo and re-pins (the equivalent of 'seed upgrade' for the engine). Until it exists the capability-only path is manual.

2. There is no release FLOOR. 'plugin enable' pins whatever tag template.lock names, including a release cut before the channel existed, which carries no .claude-plugin/marketplace.json for Claude Code to read. The opt-in is then silently broken while status --check reports healthy. The engine should know the first template release that shipped the channel and refuse (or warn on) a pin below it.

Both are additive to what landed and neither blocks the current channel: the aligned default always names a release that has the channel once the first such release is cut.

## Comment cm-9c8896e5 (shaunlmason, 2026-08-24T03:03:01Z)

Add to scope (from review on open-seed-engine#6): the offline check cannot tell an immutable non-semver tag (e.g. release-2026) from a branch, so such a pin is reported as 'floating' and never flagged as stale even though it can never advance. A network-aware re-pin command resolves what the ref actually points at and can classify it. Commit-SHA refs are already refused at enable (a marketplace source has no sha field).
